Simule rede lenta e perda de pacotes em testes Playwright

O Playwright consegue deixar uma página offline e deixar o Chromium lento pelo DevTools. O pacote beannetworktester no npm deixa lenta a rede de verdade, abaixo do navegador: latência, perda de pacotes, limite de velocidade ou uma queda total, para o servidor com que o seu teste fala. Chromium, Firefox e WebKit ficam lentos do mesmo jeito, WebSockets incluídos. O pacote traz o programa do Bean Network Tester e o executa durante o teste, no Windows e no Linux. Ele sai com cada versão estável a partir da 1.1.0.

Instalação

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Precisa de Windows x64 ou Linux x64 (glibc 2.39 ou mais nova, como Ubuntu 24.04) e Node 20 ou mais novo. O npm instala o programa do seu sistema como dependência opcional, então não deixe as dependências opcionais de fora.

Mudar a rede exige direitos de administrador no Windows: abra o terminal com "Executar como administrador". No Linux exige root, ou um usuário que possa usar sudo sem senha, e então só o programa roda com sudo. Os runners Windows hospedados pelo GitHub rodam com privilégios elevados e os runners Ubuntu permitem sudo, então um workflow não precisa de nenhum passo extra.

Um teste numa rede lenta

Salve isto como tests/slow.spec.js e rode npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

O teste passa porque a página chega mesmo mais tarde: cada pacote para esse servidor e vindo dele espera 500 ms. Quando o teste termina, a rede volta ao normal. Medido no Windows com latency: 200: uma requisição ao servidor no alvo foi de 0,8 ms para 404 ms, porque a requisição e a resposta esperam, e uma página no Chromium de 13 ms para 416 ms. Outro servidor local, fora do alvo, respondia enquanto isso em 1,6 ms.

Sem os direitos à mão? badNetwork({ simulate: true, latency: 500 }) roda o programa com tráfego inventado e não muda nada na rede. Isso verifica que o pacote está instalado direito, sem deixar nada lento.

A fixture badNetwork

Importe test e expect de beannetworktester/playwright em vez de @playwright/test. badNetwork inicia uma sessão quando você a chama e resolve assim que a rede está lenta. A sessão para quando o teste termina, tenha ele passado, falhado ou travado, e o resumo do programa é anexado ao relatório do teste como bad-network. Para mudar as condições no meio do teste, pare a primeira sessão antes de iniciar a próxima:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Fora do Playwright Test, badNetwork de require('beannetworktester') inicia a mesma sessão: const session = await badNetwork({ ... }), e await session.stop() a encerra e devolve o resumo.

Para onde uma sessão aponta

Toda sessão aponta para algo, e só esse tráfego muda. Uma sessão sem alvo deixaria lenta cada conexão da máquina, inclusive a do próprio executor de testes, por isso ela não inicia.

  • server: 'http://localhost:3000' deixa lenta cada conexão a esse endereço e porta, vinda do navegador, do seu servidor de API ou de qualquer outro programa. 'db.local:5432' e uma lista de servidores também funcionam. É a primeira escolha, e é exata no Windows e no Linux.
  • process: 'self' deixa lento o worker de testes e cada programa que ele iniciou, como o navegador dele. Um processo que o próprio teste iniciou é passado como o seu ChildProcess.
  • dstPort, dstIp e target são os alvos do próprio programa, escritos na sintaxe dele, para uma API numa porta ou num endereço conhecidos. Eles alcançam tudo o que combina: dstPort: 443 é cada conexão HTTPS da máquina, inclusive as do seu editor, e target: 'node' cada programa com "node" no nome.

Alvos dados juntos estreitam um ao outro: server com process: 'self' deixa lentas só as conexões deste worker com esse servidor. No Linux, process e target alcançam uma conexão nova até cerca de 0,2 segundo depois de ela abrir, então aponte para o servidor quando a primeira requisição conta.

O que uma sessão pode fazer

Cada ajuste é uma das opções de linha de comando do programa. latency: 300 soma 300 ms a cada pacote, jitter: 100 varia esse atraso, loss: 5 descarta 5 % dos pacotes, down e up limitam a velocidade em KB/s, e loss: 100 corta o servidor. preset: 'presets.3g' é um perfil de link inteiro, e seed: 42 faz as mesmas escolhas aleatórias em cada execução. Um cenário muda as condições conforme os segundos passam: scenario: 'scenarios/cafe-wifi.json'. Um passo do cenário pode mudar como a rede se comporta, mas não para onde a sessão aponta.

Workers em paralelo e limites

  • Uma de cada vez. Duas sessões sobre o mesmo tráfego se somariam, então os workers em paralelo se revezam, cada um esperando até wait segundos (600 se você não der outro valor). Uma segunda sessão no mesmo teste é recusada na hora.
  • Ela termina com o teste. Se o worker de testes morrer, o programa percebe e para na hora. duration (300 segundos se você não der outro valor) é, em qualquer caso, o máximo que uma sessão pode durar.
  • Ela avisa quando não fez nada. Uma sessão que não deixou nada lento, porque nada chegou ao seu alvo, termina com um BadNetworkWarning. O comum é o app falar com outro endereço que não o alvo, como um contêiner.
  • macOS. O programa roda no Windows e no Linux. Num Mac, rode os testes num contêiner ou numa máquina virtual Linux x86_64, ou num runner de CI.

O README do pacote no GitHub lista cada opção e explica cada mensagem.
