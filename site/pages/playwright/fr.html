Simuler un réseau lent et des pertes de paquets dans Playwright

Playwright sait mettre une page hors ligne et ralentir Chromium via DevTools. Le paquet beannetworktester sur npm ralentit plutôt le vrai réseau, sous le navigateur : latence, perte de paquets, limite de débit ou coupure complète, pour le serveur auquel parle votre test. Chromium, Firefox et WebKit sont ralentis de la même façon, WebSockets compris. Le paquet contient le programme de Bean Network Tester et le lance le temps d'un test, sous Windows et Linux. Il sort avec chaque version stable à partir de la 1.1.0.

Installation

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Il faut Windows x64 ou Linux x64 (glibc 2.39 ou plus récente, comme Ubuntu 24.04) et Node 20 ou plus récent. npm installe le programme pour votre système comme dépendance optionnelle, donc n'excluez pas les dépendances optionnelles.

Modifier le réseau demande les droits d'administrateur sous Windows : ouvrez le terminal avec « Exécuter en tant qu'administrateur ». Sous Linux, il faut root, ou un utilisateur qui peut lancer sudo sans mot de passe, et seul le programme tourne alors sous sudo. Les runners Windows hébergés par GitHub tournent avec des droits élevés et ses runners Ubuntu autorisent sudo, donc un workflow n'a besoin d'aucune étape de plus.

Un test sur un réseau lent

Enregistrez ceci sous tests/slow.spec.js et lancez npx playwright test :

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

Le test passe parce que la page arrive vraiment plus tard : chaque paquet vers ce serveur et depuis lui attend 500 ms. À la fin du test, le réseau redevient normal. Mesuré sous Windows avec latency: 200 : une requête vers le serveur visé est passée de 0,8 ms à 404 ms, parce que la requête et la réponse attendent toutes les deux, et une page dans Chromium de 13 ms à 416 ms. Un autre serveur local, hors de la cible, répondait pendant ce temps en 1,6 ms.

Pas de droits sous la main ? badNetwork({ simulate: true, latency: 500 }) lance le programme sur un trafic inventé et ne change rien au réseau. Cela vérifie que le paquet est bien installé, sans rien ralentir.

La fixture badNetwork

Importez test et expect depuis beannetworktester/playwright au lieu de @playwright/test. badNetwork démarre une session quand vous l'appelez et se résout une fois le réseau ralenti. La session s'arrête à la fin du test, qu'il ait réussi, échoué ou planté, et le résumé du programme est joint au rapport du test sous le nom bad-network. Pour changer les conditions en cours de test, arrêtez la première session avant de lancer la suivante :

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Hors de Playwright Test, badNetwork depuis require('beannetworktester') démarre la même session : const session = await badNetwork({ ... }), et await session.stop() l'arrête et renvoie le résumé.

Ce que vise une session

Chaque session vise quelque chose, et seul ce trafic change. Une session sans cible ralentirait toutes les connexions de la machine, y compris celles du lanceur de tests, donc elle ne démarre pas.

  • server: 'http://localhost:3000' ralentit chaque connexion vers cette adresse et ce port, depuis le navigateur, depuis votre serveur d'API ou depuis tout autre programme. 'db.local:5432' et une liste de serveurs marchent aussi. C'est le premier choix, et il est exact sous Windows et Linux.
  • process: 'self' ralentit le worker de test et chaque programme qu'il a lancé, comme son navigateur. Un processus que votre test a lancé lui-même se donne sous la forme de son ChildProcess.
  • dstPort, dstIp et target sont les cibles propres du programme, écrites dans sa syntaxe, pour une API sur un port ou une adresse connus. Elles atteignent tout ce qui correspond : dstPort: 443 est chaque connexion HTTPS de la machine, y compris celles de votre éditeur, et target: 'node' chaque programme dont le nom contient « node ».

Des cibles données ensemble se restreignent l'une l'autre : server avec process: 'self' ne ralentit que les connexions de ce worker vers ce serveur. Sous Linux, process et target atteignent une nouvelle connexion jusqu'à environ 0,2 seconde après son ouverture, donc visez le serveur quand la première requête compte.

Ce que peut faire une session

Chaque réglage est une des options en ligne de commande du programme. latency: 300 ajoute 300 ms à chaque paquet, jitter: 100 fait varier ce délai, loss: 5 perd 5 % des paquets, down et up limitent le débit en Ko/s, et loss: 100 coupe le serveur. preset: 'presets.3g' est un profil de liaison complet, et seed: 42 refait les mêmes tirages à chaque exécution. Un scénario change les conditions au fil des secondes : scenario: 'scenarios/cafe-wifi.json'. Une étape du scénario peut changer le comportement du réseau, mais pas ce que vise la session.

Workers parallèles et limites

  • Une à la fois. Deux sessions sur le même trafic s'additionneraient, donc les workers parallèles passent chacun leur tour, en attendant jusqu'à wait secondes (600 si vous n'en donnez pas d'autre). Une deuxième session dans le même test est refusée tout de suite.
  • Elle finit avec le test. Si le worker de test meurt, le programme le voit et s'arrête tout de suite. duration (300 secondes si vous n'en donnez pas d'autre) est dans tous les cas la durée maximale d'une session.
  • Elle dit quand elle n'a rien fait. Une session qui n'a rien ralenti, parce que rien n'a atteint sa cible, se termine par un BadNetworkWarning. Le plus souvent, l'application parle à une autre adresse que la cible, comme un conteneur.
  • macOS. Le programme tourne sous Windows et Linux. Sur un Mac, lancez les tests dans un conteneur ou une machine virtuelle Linux x86_64, ou sur un runner de CI.

Le README du paquet sur GitHub liste chaque option et explique chaque message.
