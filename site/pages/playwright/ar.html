محاكاة شبكة بطيئة وفقدان الحزم في اختبارات Playwright

يستطيع Playwright فصل صفحة عن الشبكة وإبطاء Chromium عبر DevTools. أما حزمة beannetworktester على npm فتبطئ الشبكة الحقيقية نفسها، تحت المتصفح: تأخير، أو فقدان حزم، أو حد للسرعة، أو انقطاع كامل، للخادم الذي يتحدث إليه اختبارك. يتباطأ Chromium وFirefox وWebKit بالطريقة نفسها، بما في ذلك WebSocket. تحمل الحزمة برنامج Bean Network Tester نفسه وتشغّله طوال مدة الاختبار، على Windows وLinux. تُنشر الحزمة مع كل إصدار مستقر بدءًا من 1.1.0.

التثبيت

npm install -D @playwright/test beannetworktester
npx playwright install chromium

تحتاج إلى Windows x64 أو Linux x64 (glibc 2.39 أو أحدث، مثل Ubuntu 24.04) وإلى Node 20 أو أحدث. يثبّت npm البرنامج الخاص بنظامك كاعتمادية اختيارية، لذا لا تستبعد الاعتماديات الاختيارية.

تغيير الشبكة يحتاج إلى صلاحيات المسؤول على Windows: افتح الطرفية عبر "تشغيل كمسؤول". وعلى Linux يحتاج إلى root، أو إلى مستخدم يستطيع تشغيل sudo دون كلمة مرور، وعندها لا يعمل تحت sudo إلا البرنامج. مشغّلات Windows التي يستضيفها GitHub تعمل بصلاحيات مرتفعة، ومشغّلات Ubuntu لديه تسمح بـ sudo، لذا لا يحتاج سير العمل إلى أي خطوة إضافية.

اختبار على شبكة بطيئة

احفظ هذا باسم tests/slow.spec.js وشغّل npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

ينجح الاختبار لأن الصفحة تصل فعلًا متأخرة: كل حزمة ذاهبة إلى ذلك الخادم أو آتية منه تنتظر 500 ms. عند انتهاء الاختبار تعود الشبكة إلى طبيعتها. القياس على Windows مع latency: 200: ارتفع طلب إلى الخادم المستهدف من 0.8 ms إلى 404 ms، لأن الطلب والرد ينتظران كلاهما، وارتفعت صفحة في Chromium من 13 ms إلى 416 ms. وفي الأثناء كان خادم محلي آخر خارج الهدف يرد في 1.6 ms.

لا تملك الصلاحيات الآن؟ badNetwork({ simulate: true, latency: 500 }) يشغّل البرنامج على حركة مختلقة ولا يغيّر شيئًا في الشبكة. إنه يتحقق من أن الحزمة مثبتة كما يجب، ولا يبطئ شيئًا.

الـ fixture المسمى badNetwork

استورد test وexpect من beannetworktester/playwright بدلًا من @playwright/test. يبدأ badNetwork جلسة عند استدعائه، ويكتمل حالما تصبح الشبكة بطيئة. تتوقف الجلسة عند انتهاء الاختبار، سواء نجح أو فشل أو تعطّل، ويُرفق ملخص البرنامج بتقرير الاختبار باسم bad-network. لتغيير الظروف في منتصف الاختبار، أوقف الجلسة الأولى قبل أن تبدأ التالية:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

خارج Playwright Test، يبدأ badNetwork من require('beannetworktester') الجلسة نفسها: const session = await badNetwork({ ... })، ثم ينهيها await session.stop() ويعيد الملخص.

ما الذي تستهدفه الجلسة

كل جلسة تستهدف شيئًا ما، ولا يتغير إلا تلك الحركة. الجلسة التي بلا هدف كانت ستبطئ كل اتصال في الجهاز، بما فيها اتصالات مشغّل الاختبارات نفسه، لذلك لا تبدأ أصلًا.

  • server: 'http://localhost:3000' يبطئ كل اتصال بهذا العنوان وهذا المنفذ، من المتصفح أو من خادم API لديك أو من أي برنامج آخر. ويصلح أيضًا 'db.local:5432' وقائمة من الخوادم. هذا هو الخيار الأول، وهو دقيق على Windows وLinux.
  • process: 'self' يبطئ عامل الاختبار وكل برنامج بدأه، مثل متصفحه. أما العملية التي بدأها اختبارك بنفسه فتُمرَّر على هيئة ChildProcess الخاص بها.
  • dstPort وdstIp وtarget هي أهداف البرنامج نفسه، تُكتب بصيغته، وهي لواجهة API على منفذ أو عنوان معروف. تصل إلى كل ما يطابقها: dstPort: 443 هو كل اتصال HTTPS في الجهاز، بما فيها اتصالات المحرر لديك، وtarget: 'node' هو كل برنامج في اسمه "node".

الأهداف المعطاة معًا يضيّق بعضها بعضًا: server مع process: 'self' يبطئ فقط اتصالات هذا العامل بذلك الخادم. على Linux لا يبدأ process وtarget بالتأثير في اتصال جديد إلا بعد فتحه بنحو 0.2 ثانية في أقصى حد، لذا استهدف الخادم حين يهم الطلب الأول.

ما الذي تستطيعه الجلسة

كل إعداد هو أحد خيارات سطر الأوامر في البرنامج. latency: 300 يضيف 300 ms إلى كل حزمة، وjitter: 100 يجعل هذا التأخير متفاوتًا، وloss: 5 يُسقط 5 % من الحزم، وdown وup يحدّان السرعة بالكيلوبايت في الثانية، وloss: 100 يقطع الخادم. preset: 'presets.3g' ملف تعريف كامل للاتصال، وseed: 42 يعيد الاختيارات العشوائية نفسها في كل تشغيل. أما السيناريو فيغيّر الظروف مع مرور الثواني: scenario: 'scenarios/cafe-wifi.json'. يمكن لخطوة في السيناريو أن تغيّر سلوك الشبكة، لكن لا يمكنها تغيير ما تستهدفه الجلسة.

العمّال المتوازيون والحدود

  • واحدة في كل مرة. جلستان على الحركة نفسها ستتراكمان، لذلك ينتظر العمّال المتوازيون دورهم، وينتظر كل منهم حتى wait ثانية (600 ما لم تحدد قيمة أخرى). وتُرفض الجلسة الثانية في الاختبار نفسه فورًا.
  • تنتهي مع الاختبار. إذا مات عامل الاختبار، يلاحظ البرنامج ذلك ويتوقف فورًا. وduration (300 ثانية ما لم تحدد قيمة أخرى) هو أطول ما يمكن أن تستمر فيه الجلسة في كل الأحوال.
  • تخبرك حين لا تفعل شيئًا. الجلسة التي لم تبطئ شيئًا، لأن شيئًا لم يصل إلى هدفها، تنتهي بتحذير BadNetworkWarning. السبب المعتاد أن التطبيق يتحدث إلى عنوان غير الهدف، مثل حاوية.
  • macOS. يعمل البرنامج على Windows وLinux. على جهاز Mac، شغّل الاختبارات في حاوية أو آلة افتراضية بنظام Linux x86_64، أو على مشغّل CI.
