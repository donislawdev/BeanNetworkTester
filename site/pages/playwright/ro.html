Simulează o rețea lentă și pierderi de pachete în Playwright

Playwright poate scoate o pagină offline și poate încetini Chromium prin DevTools. Pachetul beannetworktester de pe npm încetinește în schimb rețeaua reală, sub browser: latență, pierderi de pachete, o limită de viteză sau o întrerupere totală, pentru serverul cu care vorbește testul tău. Chromium, Firefox și WebKit sunt încetinite la fel, inclusiv WebSocket-urile. Pachetul conține programul Bean Network Tester și îl rulează cât durează un test, pe Windows și Linux. Apare cu fiecare versiune stabilă începând cu 1.1.0.

Instalare

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Are nevoie de Windows x64 sau Linux x64 (glibc 2.39 sau mai nou, de exemplu Ubuntu 24.04) și Node 20 sau mai nou. npm instalează programul pentru sistemul tău ca dependență opțională, deci nu lăsa deoparte dependențele opționale.

Schimbarea rețelei cere drepturi de administrator pe Windows: deschide terminalul cu „Executare ca administrator”. Pe Linux cere root sau un utilizator care poate rula sudo fără parolă, și atunci doar programul rulează cu sudo. Runnerele Windows găzduite de GitHub rulează cu drepturi ridicate, iar runnerele Ubuntu permit sudo, deci un workflow nu are nevoie de niciun pas în plus.

Un test pe o rețea lentă

Salvează asta ca tests/slow.spec.js și rulează npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

Testul trece pentru că pagina chiar ajunge mai târziu: fiecare pachet spre acel server și dinspre el așteaptă 500 ms. Când testul se termină, rețeaua revine la normal. Măsurat pe Windows cu latency: 200: o cerere către serverul din țintă a crescut de la 0,8 ms la 404 ms, pentru că așteaptă și cererea, și răspunsul, iar o pagină în Chromium de la 13 ms la 416 ms. Un alt server local, în afara țintei, răspundea între timp în 1,6 ms.

Nu ai drepturile la îndemână? badNetwork({ simulate: true, latency: 500 }) rulează programul pe trafic inventat și nu schimbă nimic în rețea. Verifică faptul că pachetul e instalat corect și nu încetinește nimic.

Fixture-ul badNetwork

Importă test și expect din beannetworktester/playwright în loc de @playwright/test. badNetwork pornește o sesiune când îl apelezi și se rezolvă imediat ce rețeaua e lentă. Sesiunea se oprește când testul se termină, fie că a trecut, a picat sau s-a prăbușit, iar rezumatul programului e atașat la raportul testului ca bad-network. Ca să schimbi condițiile la jumătatea testului, oprește prima sesiune înainte s-o pornești pe următoarea:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

În afara Playwright Test, badNetwork din require('beannetworktester') pornește aceeași sesiune: const session = await badNetwork({ ... }), iar await session.stop() o încheie și întoarce rezumatul.

Spre ce țintește o sesiune

Fiecare sesiune țintește ceva și doar acel trafic se schimbă. O sesiune fără țintă ar încetini fiecare conexiune a mașinii, inclusiv pe cele ale rulatorului de teste, așa că nu pornește.

  • server: 'http://localhost:3000' încetinește fiecare conexiune către acea adresă și acel port, din browser, din serverul tău de API sau din orice alt program. Merg și 'db.local:5432' și o listă de servere. Aceasta e prima alegere și e exactă pe Windows și Linux.
  • process: 'self' încetinește workerul de teste și fiecare program pornit de el, de exemplu browserul lui. Un proces pornit chiar de test se dă ca ChildProcess-ul lui.
  • dstPort, dstIp și target sunt țintele proprii ale programului, scrise în sintaxa lui, pentru un API pe un port sau o adresă cunoscute. Ele ajung la tot ce se potrivește: dstPort: 443 înseamnă fiecare conexiune HTTPS a mașinii, inclusiv cele ale editorului tău, iar target: 'node' fiecare program cu „node” în nume.

Țintele date împreună se restrâng una pe alta: server cu process: 'self' încetinește doar conexiunile acestui worker către acel server. Pe Linux, process și target ajung la o conexiune nouă până la circa 0,2 secunde după deschiderea ei, așa că țintește serverul când contează prima cerere.

Ce poate face o sesiune

Fiecare setare este una dintre opțiunile din linia de comandă ale programului. latency: 300 adaugă 300 ms fiecărui pachet, jitter: 100 face să varieze acea întârziere, loss: 5 aruncă 5 % din pachete, down și up limitează viteza în KB/s, iar loss: 100 taie serverul. preset: 'presets.3g' e un profil de legătură întreg, iar seed: 42 face aceleași alegeri aleatorii la fiecare rulare. Un scenariu schimbă condițiile pe măsură ce trec secundele: scenario: 'scenarios/cafe-wifi.json'. Un pas din scenariu poate schimba cum se comportă rețeaua, dar nu și spre ce țintește sesiunea.

Workeri în paralel și limite

  • Câte una. Două sesiuni pe același trafic s-ar aduna, așa că workerii în paralel își așteaptă rândul, fiecare până la wait secunde (600 dacă nu dai altă valoare). O a doua sesiune în același test e refuzată imediat.
  • Se termină odată cu testul. Dacă workerul de teste moare, programul observă și se oprește imediat. duration (300 de secunde dacă nu dai altă valoare) e, în orice caz, cel mai mult cât poate rula o sesiune.
  • Spune când n-a făcut nimic. O sesiune care n-a încetinit nimic, pentru că nimic n-a ajuns la ținta ei, se încheie cu un BadNetworkWarning. De obicei aplicația vorbește cu altă adresă decât ținta, de exemplu un container.
  • macOS. Programul rulează pe Windows și Linux. Pe un Mac, rulează testele într-un container sau o mașină virtuală Linux x86_64 ori pe un runner de CI.

README-ul pachetului de pe GitHub enumeră fiecare opțiune și explică fiecare mesaj.
