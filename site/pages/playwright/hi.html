Playwright टेस्ट में धीमा नेटवर्क और पैकेट लॉस

Playwright किसी पेज को ऑफ़लाइन कर सकता है और DevTools के ज़रिए Chromium को धीमा कर सकता है। npm का beannetworktester पैकेज इसके बजाय ब्राउज़र के नीचे असली नेटवर्क को धीमा करता है: लेटेंसी, पैकेट लॉस, स्पीड लिमिट या पूरा आउटेज, उस सर्वर के लिए जिससे आपका टेस्ट बात करता है। Chromium, Firefox और WebKit एक ही तरह धीमे होते हैं, WebSocket समेत। पैकेज में Bean Network Tester का अपना प्रोग्राम है, और वह इसे टेस्ट की अवधि तक Windows और Linux पर चलाता है। यह 1.1.0 से हर स्थिर रिलीज़ के साथ प्रकाशित होता है।

इंस्टॉल करें

npm install -D @playwright/test beannetworktester
npx playwright install chromium

इसके लिए Windows x64 या Linux x64 (glibc 2.39 या नया, जैसे Ubuntu 24.04) और Node 20 या नया चाहिए। npm आपके सिस्टम का प्रोग्राम वैकल्पिक निर्भरता के रूप में इंस्टॉल करता है, इसलिए वैकल्पिक निर्भरताओं को बाहर न छोड़ें।

Windows पर नेटवर्क बदलने के लिए एडमिनिस्ट्रेटर अधिकार चाहिए: टर्मिनल को "व्यवस्थापक के रूप में चलाएँ" से खोलें। Linux पर root चाहिए, या ऐसा उपयोगकर्ता जो बिना पासवर्ड sudo चला सके, और तब sudo के तहत सिर्फ़ प्रोग्राम चलता है। GitHub के होस्ट किए गए Windows रनर ऊँचे अधिकारों के साथ चलते हैं और उसके Ubuntu रनर sudo की अनुमति देते हैं, इसलिए workflow को किसी अतिरिक्त कदम की ज़रूरत नहीं।

धीमे नेटवर्क पर एक टेस्ट

इसे tests/slow.spec.js के रूप में सहेजें और npx playwright test चलाएँ:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

टेस्ट पास होता है क्योंकि पेज सचमुच देर से पहुँचता है: उस सर्वर तक जाने और वहाँ से आने वाला हर पैकेट 500 ms रुकता है। टेस्ट ख़त्म होने पर नेटवर्क सामान्य हो जाता है। Windows पर latency: 200 के साथ मापा गया: लक्ष्य वाले सर्वर को भेजा गया अनुरोध 0.8 ms से 404 ms हो गया, क्योंकि अनुरोध और जवाब दोनों रुकते हैं, और Chromium में एक पेज 13 ms से 416 ms। इस दौरान लक्ष्य से बाहर का एक दूसरा लोकल सर्वर 1.6 ms में जवाब देता रहा।

अधिकार अभी हाथ में नहीं? badNetwork({ simulate: true, latency: 500 }) प्रोग्राम को गढ़े हुए ट्रैफ़िक पर चलाता है और नेटवर्क में कुछ नहीं बदलता। यह जाँचता है कि पैकेज ठीक से सेट है, और कुछ भी धीमा नहीं करता।

badNetwork fixture

test और expect को @playwright/test के बजाय beannetworktester/playwright से इंपोर्ट करें। badNetwork को बुलाने पर सेशन शुरू होता है, और नेटवर्क धीमा होते ही वह पूरा हो जाता है। टेस्ट ख़त्म होने पर सेशन रुक जाता है, चाहे टेस्ट पास हुआ, फ़ेल हुआ या क्रैश हुआ, और प्रोग्राम का सारांश टेस्ट की रिपोर्ट में bad-network नाम से जुड़ जाता है। टेस्ट के बीच में हालात बदलने के लिए, अगला सेशन शुरू करने से पहले पहला सेशन रोकें:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Playwright Test के बाहर, require('beannetworktester') का badNetwork वही सेशन शुरू करता है: const session = await badNetwork({ ... }), और await session.stop() उसे ख़त्म करके सारांश लौटाता है।

सेशन किस पर निशाना साधता है

हर सेशन किसी चीज़ पर निशाना साधता है, और सिर्फ़ वही ट्रैफ़िक बदलता है। बिना लक्ष्य वाला सेशन मशीन के हर कनेक्शन को धीमा कर देता, टेस्ट रनर के अपने कनेक्शन समेत, इसलिए वह शुरू ही नहीं होता।

  • server: 'http://localhost:3000' उस पते और पोर्ट तक के हर कनेक्शन को धीमा करता है, चाहे ब्राउज़र से हो, आपके API सर्वर से या किसी भी दूसरे प्रोग्राम से। 'db.local:5432' और सर्वरों की सूची भी चलती है। यह पहली पसंद है, और Windows और Linux पर सटीक है।
  • process: 'self' टेस्ट worker को और उसके शुरू किए हर प्रोग्राम को धीमा करता है, जैसे उसका ब्राउज़र। जो प्रोसेस आपके टेस्ट ने ख़ुद शुरू किया, उसे उसके ChildProcess के रूप में दें।
  • dstPort, dstIp और target प्रोग्राम के अपने लक्ष्य हैं, उसके सिंटैक्स में लिखे जाते हैं, और किसी जाने-पहचाने पोर्ट या पते पर चल रहे API के लिए हैं। ये हर मिलती-जुलती चीज़ तक पहुँचते हैं: dstPort: 443 मशीन का हर HTTPS कनेक्शन है, आपके एडिटर का भी, और target: 'node' हर वह प्रोग्राम जिसके नाम में "node" है।

साथ दिए गए लक्ष्य एक-दूसरे को संकरा करते हैं: server के साथ process: 'self' सिर्फ़ इस worker के उस सर्वर तक के कनेक्शन धीमे करता है। Linux पर process और target किसी नए कनेक्शन पर उसके खुलने के लगभग 0.2 सेकंड बाद तक असर करना शुरू करते हैं, इसलिए जब पहला अनुरोध मायने रखता हो तो सर्वर पर निशाना साधें।

सेशन क्या कर सकता है

हर सेटिंग प्रोग्राम के कमांड-लाइन विकल्पों में से एक है। latency: 300 हर पैकेट में 300 ms जोड़ता है, jitter: 100 उस देरी को ऊपर-नीचे करता है, loss: 5 5 % पैकेट गिराता है, down और up स्पीड को KB/s में सीमित करते हैं, और loss: 100 सर्वर को काट देता है। preset: 'presets.3g' एक पूरा लिंक प्रोफ़ाइल है, और seed: 42 हर बार वही रैंडम चुनाव करता है। एक सिनेरियो सेकंड बीतने के साथ हालात बदलता है: scenario: 'scenarios/cafe-wifi.json'। सिनेरियो का कोई कदम नेटवर्क का बर्ताव बदल सकता है, पर यह नहीं कि सेशन किस पर निशाना साधता है।

समानांतर worker और सीमाएँ

  • एक बार में एक। एक ही ट्रैफ़िक पर दो सेशन जुड़ जाते, इसलिए समानांतर worker बारी-बारी से चलते हैं, हर एक wait सेकंड तक रुकता है (कोई और मान न दें तो 600)। उसी टेस्ट में दूसरा सेशन तुरंत ठुकरा दिया जाता है।
  • टेस्ट के साथ ख़त्म होता है। अगर टेस्ट worker मर जाए, तो प्रोग्राम यह देखकर तुरंत रुक जाता है। duration (कोई और मान न दें तो 300 सेकंड) हर हाल में किसी सेशन का सबसे लंबा समय है।
  • कुछ न करने पर बताता है। जिस सेशन ने कुछ भी धीमा नहीं किया, क्योंकि उसके लक्ष्य तक कुछ नहीं पहुँचा, वह BadNetworkWarning के साथ ख़त्म होता है। आम वजह यह होती है कि ऐप लक्ष्य के बजाय किसी दूसरे पते से बात कर रहा है, जैसे किसी कंटेनर से।
  • macOS. प्रोग्राम Windows और Linux पर चलता है। Mac पर टेस्ट किसी Linux x86_64 कंटेनर या वर्चुअल मशीन में, या किसी CI रनर पर चलाएँ।
