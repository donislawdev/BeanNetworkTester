Simula una red lenta y pérdida de paquetes en pruebas Playwright

Playwright puede dejar una página sin conexión y ralentizar Chromium mediante DevTools. El paquete beannetworktester de npm ralentiza en cambio la red real, por debajo del navegador: latencia, pérdida de paquetes, un límite de velocidad o un corte total, para el servidor con el que habla tu prueba. Chromium, Firefox y WebKit se ralentizan igual, WebSockets incluidos. El paquete lleva el programa de Bean Network Tester y lo ejecuta mientras dura la prueba, en Windows y Linux. Se publica con cada versión estable a partir de la 1.1.0.

Instalación

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Necesita Windows x64 o Linux x64 (glibc 2.39 o más reciente, como Ubuntu 24.04) y Node 20 o más reciente. npm instala el programa para tu sistema como dependencia opcional, así que no dejes fuera las dependencias opcionales.

Cambiar la red requiere derechos de administrador en Windows: abre la terminal con «Ejecutar como administrador». En Linux requiere root, o un usuario que pueda usar sudo sin contraseña, y entonces solo el programa corre con sudo. Los runners de Windows alojados por GitHub corren con privilegios elevados y sus runners de Ubuntu permiten sudo, así que un workflow no necesita ningún paso extra.

Una prueba en una red lenta

Guarda esto como tests/slow.spec.js y ejecuta npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

La prueba pasa porque la página de verdad llega más tarde: cada paquete hacia ese servidor y desde él espera 500 ms. Cuando la prueba termina, la red vuelve a la normalidad. Medido en Windows con latency: 200: una petición al servidor del objetivo pasó de 0,8 ms a 404 ms, porque esperan tanto la petición como la respuesta, y una página en Chromium de 13 ms a 416 ms. Otro servidor local, fuera del objetivo, respondía mientras tanto en 1,6 ms.

¿No tienes los derechos a mano? badNetwork({ simulate: true, latency: 500 }) ejecuta el programa con tráfico inventado y no cambia nada en la red. Comprueba que el paquete está bien instalado y no ralentiza nada.

El fixture badNetwork

Importa test y expect desde beannetworktester/playwright en lugar de @playwright/test. badNetwork inicia una sesión cuando lo llamas y se resuelve en cuanto la red está lenta. La sesión se detiene cuando termina la prueba, haya pasado, fallado o se haya caído, y el resumen del programa se adjunta al informe de la prueba como bad-network. Para cambiar las condiciones a mitad de la prueba, detén la primera sesión antes de iniciar la siguiente:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Fuera de Playwright Test, badNetwork de require('beannetworktester') inicia la misma sesión: const session = await badNetwork({ ... }), y await session.stop() la termina y devuelve el resumen.

A qué apunta una sesión

Cada sesión apunta a algo, y solo ese tráfico cambia. Una sesión sin objetivo ralentizaría todas las conexiones de la máquina, incluidas las del propio ejecutor de pruebas, así que no arranca.

  • server: 'http://localhost:3000' ralentiza cada conexión a esa dirección y ese puerto, desde el navegador, desde tu servidor de API o desde cualquier otro programa. También sirven 'db.local:5432' y una lista de servidores. Es la primera opción, y es exacta en Windows y Linux.
  • process: 'self' ralentiza el worker de pruebas y cada programa que inició, como su navegador. Un proceso que tu prueba inició por su cuenta se pasa como su ChildProcess.
  • dstPort, dstIp y target son los objetivos propios del programa, escritos en su sintaxis, para una API en un puerto o una dirección conocidos. Alcanzan todo lo que coincida: dstPort: 443 es cada conexión HTTPS de la máquina, incluidas las de tu editor, y target: 'node' cada programa con «node» en el nombre.

Los objetivos dados juntos se acotan entre sí: server con process: 'self' ralentiza solo las conexiones de este worker a ese servidor. En Linux, process y target alcanzan una conexión nueva hasta unos 0,2 segundos después de abrirse, así que apunta al servidor cuando cuenta la primera petición.

Qué puede hacer una sesión

Cada ajuste es una de las opciones de línea de comandos del programa. latency: 300 añade 300 ms a cada paquete, jitter: 100 hace variar ese retardo, loss: 5 descarta el 5 % de los paquetes, down y up limitan la velocidad en KB/s, y loss: 100 corta el servidor. preset: 'presets.3g' es un perfil de enlace completo, y seed: 42 repite las mismas elecciones al azar en cada ejecución. Un escenario cambia las condiciones a medida que pasan los segundos: scenario: 'scenarios/cafe-wifi.json'. Un paso del escenario puede cambiar cómo se comporta la red, pero no a qué apunta la sesión.

Workers en paralelo y límites

  • Una a la vez. Dos sesiones sobre el mismo tráfico se sumarían, así que los workers en paralelo se turnan, cada uno esperando hasta wait segundos (600 si no indicas otro valor). Una segunda sesión en la misma prueba se rechaza al instante.
  • Termina con la prueba. Si el worker de pruebas muere, el programa lo nota y se detiene al instante. duration (300 segundos si no indicas otro valor) es en todo caso lo máximo que puede durar una sesión.
  • Avisa cuando no hizo nada. Una sesión que no ralentizó nada, porque nada llegó a su objetivo, termina con un BadNetworkWarning. Lo habitual es que la aplicación hable con otra dirección distinta del objetivo, como un contenedor.
  • macOS. El programa funciona en Windows y Linux. En un Mac, ejecuta las pruebas en un contenedor o una máquina virtual Linux x86_64, o en un runner de CI.

El README del paquete en GitHub enumera cada opción y explica cada mensaje.
