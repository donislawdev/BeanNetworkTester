Langsames Netz und Paketverlust in Playwright-Tests simulieren

Playwright kann eine Seite offline schalten und Chromium über DevTools drosseln. Das Paket beannetworktester auf npm verlangsamt stattdessen das echte Netz, unterhalb des Browsers: Latenz, Paketverlust, ein Tempolimit oder ein ganzer Ausfall, für den Server, mit dem Ihr Test spricht. Chromium, Firefox und WebKit werden gleich verlangsamt, WebSockets eingeschlossen. Das Paket enthält das Programm von Bean Network Tester und führt es für die Dauer eines Tests aus, unter Windows und Linux. Es erscheint mit jeder stabilen Version ab 1.1.0.

Installation

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Es braucht Windows x64 oder Linux x64 (glibc 2.39 oder neuer, etwa Ubuntu 24.04) und Node 20 oder neuer. npm installiert das Programm für Ihr System als optionale Abhängigkeit, lassen Sie optionale Abhängigkeiten also nicht weg.

Das Netz zu verändern braucht unter Windows Administratorrechte: Öffnen Sie das Terminal mit „Als Administrator ausführen“. Unter Linux braucht es root oder einen Benutzer, der sudo ohne Passwort ausführen darf, und dann läuft nur das Programm unter sudo. Die gehosteten Windows-Runner von GitHub laufen mit erhöhten Rechten und die Ubuntu-Runner erlauben sudo, ein Workflow braucht also keinen zusätzlichen Schritt.

Ein Test in einem langsamen Netz

Speichern Sie das als tests/slow.spec.js und führen Sie npx playwright test aus:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

Der Test besteht, weil die Seite wirklich später ankommt: Jedes Paket zu diesem Server und von ihm wartet 500 ms. Wenn der Test endet, ist das Netz wieder normal. Gemessen unter Windows mit latency: 200: Eine Anfrage an den Server im Ziel stieg von 0,8 ms auf 404 ms, weil Anfrage und Antwort beide warten, und eine Seite in Chromium von 13 ms auf 416 ms. Ein anderer lokaler Server außerhalb des Ziels antwortete währenddessen in 1,6 ms.

Keine Rechte zur Hand? badNetwork({ simulate: true, latency: 500 }) führt das Programm mit erfundenem Verkehr aus und ändert nichts am Netz. Es prüft, ob das Paket richtig eingerichtet ist, und verlangsamt nichts.

Die Fixture badNetwork

Importieren Sie test und expect aus beannetworktester/playwright statt aus @playwright/test. badNetwork startet eine Sitzung, wenn Sie es aufrufen, und kehrt zurück, sobald das Netz langsam ist. Die Sitzung endet mit dem Test, ob er bestanden hat, fehlgeschlagen oder abgestürzt ist, und die Zusammenfassung des Programms hängt als bad-network am Bericht des Tests. Um die Bedingungen mittendrin zu ändern, beenden Sie die erste Sitzung, bevor Sie die nächste starten:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Außerhalb von Playwright Test startet badNetwork aus require('beannetworktester') dieselbe Sitzung: const session = await badNetwork({ ... }), und await session.stop() beendet sie und gibt die Zusammenfassung zurück.

Worauf eine Sitzung zielt

Jede Sitzung zielt auf etwas, und nur dieser Verkehr ändert sich. Eine Sitzung ohne Ziel würde jede Verbindung des Rechners verlangsamen, auch die des Testrunners selbst, deshalb startet sie gar nicht.

  • server: 'http://localhost:3000' verlangsamt jede Verbindung zu dieser Adresse und diesem Port, vom Browser, von Ihrem API-Server oder von jedem anderen Programm. 'db.local:5432' und eine Liste von Servern gehen auch. Das ist die erste Wahl, und sie ist unter Windows und Linux exakt.
  • process: 'self' verlangsamt den Test-Worker und jedes Programm, das er gestartet hat, etwa seinen Browser. Einen Prozess, den Ihr Test selbst gestartet hat, übergeben Sie als seinen ChildProcess.
  • dstPort, dstIp und target sind die eigenen Ziele des Programms, geschrieben in seiner Syntax, für eine API an einem bekannten Port oder einer bekannten Adresse. Sie erreichen alles, was passt: dstPort: 443 ist jede HTTPS-Verbindung des Rechners, auch die Ihres Editors, und target: 'node' jedes Programm mit „node“ im Namen.

Zusammen angegebene Ziele engen einander ein: server mit process: 'self' verlangsamt nur die Verbindungen dieses Workers zu diesem Server. Unter Linux erreichen process und target eine neue Verbindung bis zu etwa 0,2 Sekunden nach ihrem Öffnen, zielen Sie also auf den Server, wenn die erste Anfrage zählt.

Was eine Sitzung kann

Jede Einstellung ist eine der Befehlszeilenoptionen des Programms. latency: 300 fügt jedem Paket 300 ms hinzu, jitter: 100 lässt diese Verzögerung schwanken, loss: 5 verwirft 5 % der Pakete, down und up begrenzen das Tempo in KB/s, und loss: 100 schneidet den Server ab. preset: 'presets.3g' ist ein ganzes Verbindungsprofil, und seed: 42 trifft bei jedem Lauf dieselben Zufallsentscheidungen. Ein Szenario ändert die Bedingungen im Lauf der Sekunden: scenario: 'scenarios/cafe-wifi.json'. Ein Schritt im Szenario darf ändern, wie sich das Netz verhält, aber nicht, worauf die Sitzung zielt.

Parallele Worker und Grenzen

  • Eine nach der anderen. Zwei Sitzungen auf demselben Verkehr würden sich addieren, deshalb wechseln sich parallele Worker ab und warten jeweils bis zu wait Sekunden (600, wenn Sie nichts anderes angeben). Eine zweite Sitzung im selben Test wird sofort abgelehnt.
  • Sie endet mit dem Test. Stirbt der Test-Worker, bemerkt das Programm es und hält sofort an. duration (300 Sekunden, wenn Sie nichts anderes angeben) ist in jedem Fall die längste Laufzeit einer Sitzung.
  • Sie sagt, wenn sie nichts getan hat. Eine Sitzung, die nichts verlangsamt hat, weil nichts ihr Ziel erreichte, endet mit einer BadNetworkWarning. Meist spricht die App dann mit einer anderen Adresse als dem Ziel, etwa mit einem Container.
  • macOS. Das Programm läuft unter Windows und Linux. Auf einem Mac führen Sie die Tests in einem Linux-x86_64-Container, in einer virtuellen Maschine oder auf einem CI-Runner aus.

Das README des Pakets auf GitHub nennt jede Option und erklärt jede Meldung.
