Een traag netwerk en pakketverlies simuleren in Playwright-tests

Playwright kan een pagina offline zetten en Chromium vertragen via DevTools. Het pakket beannetworktester op npm vertraagt in plaats daarvan het echte netwerk, onder de browser: latentie, pakketverlies, een snelheidslimiet of een volledige storing, voor de server waarmee je test praat. Chromium, Firefox en WebKit worden even sterk vertraagd, WebSockets inbegrepen. Het pakket bevat het programma van Bean Network Tester en draait het zolang een test duurt, op Windows en Linux. Het verschijnt met elke stabiele versie vanaf 1.1.0.

Installeren

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Het heeft Windows x64 of Linux x64 nodig (glibc 2.39 of nieuwer, zoals Ubuntu 24.04) en Node 20 of nieuwer. npm installeert het programma voor jouw systeem als optionele afhankelijkheid, dus laat optionele afhankelijkheden niet weg.

Het netwerk veranderen vraagt op Windows beheerdersrechten: open de terminal met "Als administrator uitvoeren". Op Linux vraagt het root, of een gebruiker die sudo zonder wachtwoord mag gebruiken, en dan draait alleen het programma onder sudo. De gehoste Windows-runners van GitHub draaien met verhoogde rechten en de Ubuntu-runners staan sudo toe, dus een workflow heeft geen extra stap nodig.

Een test op een traag netwerk

Sla dit op als tests/slow.spec.js en draai npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

De test slaagt omdat de pagina echt later aankomt: elk pakket naar die server en terug wacht 500 ms. Als de test eindigt, is het netwerk weer normaal. Gemeten op Windows met latency: 200: een verzoek aan de server in het doel ging van 0,8 ms naar 404 ms, omdat verzoek en antwoord allebei wachten, en een pagina in Chromium van 13 ms naar 416 ms. Een andere lokale server, buiten het doel, antwoordde intussen in 1,6 ms.

Geen rechten bij de hand? badNetwork({ simulate: true, latency: 500 }) draait het programma op verzonnen verkeer en verandert niets aan het netwerk. Het controleert of het pakket goed is ingesteld en vertraagt niets.

De fixture badNetwork

Importeer test en expect uit beannetworktester/playwright in plaats van uit @playwright/test. badNetwork start een sessie als je het aanroept en is klaar zodra het netwerk traag is. De sessie stopt als de test eindigt, of die nu slaagde, faalde of crashte, en de samenvatting van het programma hangt als bad-network aan het testrapport. Om halverwege de omstandigheden te veranderen, stop je de eerste sessie voordat je de volgende start:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Buiten Playwright Test start badNetwork uit require('beannetworktester') dezelfde sessie: const session = await badNetwork({ ... }), en await session.stop() beëindigt hem en geeft de samenvatting terug.

Waar een sessie op mikt

Elke sessie mikt ergens op, en alleen dat verkeer verandert. Een sessie zonder doel zou elke verbinding van de machine vertragen, ook die van de testrunner zelf, dus die start niet.

  • server: 'http://localhost:3000' vertraagt elke verbinding met dat adres en die poort, vanuit de browser, vanuit je API-server of vanuit elk ander programma. 'db.local:5432' en een lijst van servers werken ook. Dit is de eerste keuze, en die is exact op Windows en Linux.
  • process: 'self' vertraagt de testworker en elk programma dat die startte, zoals zijn browser. Een proces dat je test zelf startte, geef je mee als zijn ChildProcess.
  • dstPort, dstIp en target zijn de eigen doelen van het programma, geschreven in zijn syntaxis, voor een API op een bekende poort of een bekend adres. Ze bereiken alles wat overeenkomt: dstPort: 443 is elke HTTPS-verbinding van de machine, ook die van je editor, en target: 'node' elk programma met "node" in de naam.

Doelen die samen zijn opgegeven, beperken elkaar: server met process: 'self' vertraagt alleen de verbindingen van deze worker met die server. Op Linux bereiken process en target een nieuwe verbinding tot ongeveer 0,2 seconde na het openen, dus mik op de server als het eerste verzoek telt.

Wat een sessie kan

Elke instelling is een van de opdrachtregelopties van het programma. latency: 300 voegt 300 ms toe aan elk pakket, jitter: 100 laat die vertraging variëren, loss: 5 laat 5 % van de pakketten vallen, down en up beperken de snelheid in KB/s, en loss: 100 snijdt de server af. preset: 'presets.3g' is een volledig verbindingsprofiel, en seed: 42 maakt bij elke run dezelfde willekeurige keuzes. Een scenario verandert de omstandigheden naarmate de seconden verstrijken: scenario: 'scenarios/cafe-wifi.json'. Een stap in het scenario mag veranderen hoe het netwerk zich gedraagt, maar niet waar de sessie op mikt.

Parallelle workers en grenzen

  • Eén tegelijk. Twee sessies op hetzelfde verkeer zouden optellen, dus parallelle workers wachten op hun beurt, elk tot wait seconden (600 als je niets anders opgeeft). Een tweede sessie in dezelfde test wordt meteen geweigerd.
  • Hij eindigt met de test. Als de testworker sterft, ziet het programma dat en stopt het meteen. duration (300 seconden als je niets anders opgeeft) is in elk geval het langste dat een sessie mag duren.
  • Hij zegt het als hij niets deed. Een sessie die niets vertraagde, omdat niets zijn doel bereikte, eindigt met een BadNetworkWarning. Meestal praat de app dan met een ander adres dan het doel, zoals een container.
  • macOS. Het programma draait op Windows en Linux. Draai de tests op een Mac in een Linux-x86_64-container of virtuele machine, of op een CI-runner.
