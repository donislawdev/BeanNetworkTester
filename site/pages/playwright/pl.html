Wolna sieć i utrata pakietów w testach Playwright

Playwright potrafi odciąć stronę od sieci i spowolnić Chromium przez DevTools. Pakiet beannetworktester z npm spowalnia zamiast tego prawdziwą sieć, pod przeglądarką: opóźnienie, utrata pakietów, limit prędkości albo całkowita awaria, dla serwera, z którym rozmawia test. Chromium, Firefox i WebKit zwalniają tak samo, razem z WebSocketami. Pakiet zawiera program Bean Network Tester i uruchamia go na czas testu, na Windows i Linuksie. Wychodzi z każdym stabilnym wydaniem od 1.1.0.

Instalacja

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Wymaga Windows x64 albo Linuksa x64 (glibc 2.39 lub nowsza, na przykład Ubuntu 24.04) i Node 20 lub nowszego. npm instaluje program dla Twojego systemu jako zależność opcjonalną, więc nie pomijaj zależności opcjonalnych.

Zmiana sieci wymaga uprawnień administratora na Windows: otwórz terminal przez „Uruchom jako administrator”. Na Linuksie wymaga roota albo użytkownika, który może uruchamiać sudo bez hasła, i wtedy pod sudo działa tylko program. Hostowane runnery GitHuba z Windows działają z uprawnieniami administratora, a te z Ubuntu pozwalają na sudo, więc workflow nie potrzebuje dodatkowego kroku.

Test na wolnej sieci

Zapisz to jako tests/slow.spec.js i uruchom npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

Test przechodzi, bo strona naprawdę przychodzi później: każdy pakiet do tego serwera i z niego czeka 500 ms. Po końcu testu sieć wraca do normy. Zmierzone na Windows przy latency: 200: zapytanie do serwera w celu trwało 404 ms zamiast 0,8 ms, bo czeka i zapytanie, i odpowiedź, a strona w Chromium 416 ms zamiast 13 ms. Inny lokalny serwer, poza celem, odpowiadał w tym czasie w 1,6 ms.

Nie masz uprawnień pod ręką? badNetwork({ simulate: true, latency: 500 }) uruchamia program na zmyślonym ruchu i niczego w sieci nie zmienia. Sprawdza, czy pakiet jest dobrze zainstalowany, i niczego nie spowalnia.

Fixture badNetwork

Zaimportuj test i expect z beannetworktester/playwright zamiast z @playwright/test. badNetwork zaczyna sesję, gdy go wywołasz, i kończy czekanie, gdy sieć jest już wolna. Sesja kończy się razem z testem, czy przeszedł, czy nie, czy się wysypał, a podsumowanie programu trafia do raportu testu jako bad-network. Żeby zmienić warunki w połowie testu, zatrzymaj pierwszą sesję, zanim zaczniesz następną:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Poza Playwright Test tę samą sesję zaczyna badNetwork z require('beannetworktester'): const session = await badNetwork({ ... }), a await session.stop() ją kończy i zwraca podsumowanie.

W co celuje sesja

Każda sesja w coś celuje i zmienia się tylko ten ruch. Sesja bez celu spowolniłaby każde połączenie maszyny, także połączenie samego uruchamiacza testów, więc w ogóle nie startuje.

  • server: 'http://localhost:3000' spowalnia każde połączenie z tym adresem i portem: z przeglądarki, z Twojego serwera API albo z dowolnego innego programu. Działa też 'db.local:5432' i lista serwerów. To pierwszy wybór, dokładny na Windows i Linuksie.
  • process: 'self' spowalnia workera testów i każdy program, który uruchomił, na przykład jego przeglądarkę. Proces uruchomiony przez sam test podajesz jako jego ChildProcess.
  • dstPort, dstIp i target to cele samego programu, pisane w jego składni, dla API na znanym porcie albo adresie. Obejmują wszystko, co pasuje: dstPort: 443 to każde połączenie HTTPS maszyny, także Twojego edytora, a target: 'node' to każdy program z „node” w nazwie.

Cele podane razem zawężają się nawzajem: server z process: 'self' spowalnia tylko połączenia tego workera z tym serwerem. Na Linuksie process i target sięgają nowego połączenia do około 0,2 sekundy po jego otwarciu, więc celuj w serwer, gdy liczy się pierwsze zapytanie.

Co potrafi sesja

Każde ustawienie to jedna z opcji linii komend programu. latency: 300 dodaje 300 ms do każdego pakietu, jitter: 100 zmienia to opóźnienie, loss: 5 gubi 5 % pakietów, down i up ograniczają prędkość w KB/s, a loss: 100 odcina serwer. preset: 'presets.3g' to cały profil łącza, a seed: 42 daje te same losowania przy każdym uruchomieniu. Scenariusz zmienia warunki z upływem sekund: scenario: 'scenarios/cafe-wifi.json'. Krok scenariusza może zmienić zachowanie sieci, ale nie to, w co celuje sesja.

Równoległe workery i ograniczenia

  • Jedna naraz. Dwie sesje na tym samym ruchu sumowałyby się, więc równoległe workery czekają na swoją kolej, każdy do wait sekund (600, jeśli nie podasz innej wartości). Druga sesja w tym samym teście jest od razu odrzucana.
  • Kończy się z testem. Jeśli worker testów padnie, program to widzi i od razu się zatrzymuje. duration (300 sekund, jeśli nie podasz innej wartości) to w każdym przypadku najdłuższy czas sesji.
  • Mówi, gdy nic nie zrobiła. Sesja, która niczego nie spowolniła, bo nic nie trafiło w jej cel, kończy się ostrzeżeniem BadNetworkWarning. Zwykle znaczy to, że aplikacja rozmawia z innym adresem niż cel, na przykład z kontenerem.
  • macOS. Program działa na Windows i Linuksie. Na Macu uruchom testy w kontenerze albo maszynie wirtualnej z Linuksem x86_64 albo na runnerze CI.
