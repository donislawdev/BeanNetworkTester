จำลองเครือข่ายช้าและแพ็กเก็ตสูญหายในการทดสอบ Playwright

Playwright ทำให้หน้าเว็บออฟไลน์ได้ และทำให้ Chromium ช้าลงผ่าน DevTools ได้ ส่วนแพ็กเกจ beannetworktester บน npm จะทำให้เครือข่ายจริงช้าลงแทน ใต้เบราว์เซอร์ลงไป: ความหน่วง แพ็กเก็ตสูญหาย การจำกัดความเร็ว หรือการขาดการเชื่อมต่อทั้งหมด สำหรับเซิร์ฟเวอร์ที่การทดสอบของคุณคุยด้วย Chromium, Firefox และ WebKit ช้าลงแบบเดียวกัน รวมถึง WebSocket แพ็กเกจนี้มีโปรแกรมของ Bean Network Tester อยู่ในตัว และรันโปรแกรมนั้นตลอดการทดสอบ บน Windows และ Linux แพ็กเกจนี้เผยแพร่พร้อมทุกรุ่นเสถียรตั้งแต่ 1.1.0 เป็นต้นไป

ติดตั้ง

npm install -D @playwright/test beannetworktester
npx playwright install chromium

ต้องใช้ Windows x64 หรือ Linux x64 (glibc 2.39 ขึ้นไป เช่น Ubuntu 24.04) และ Node 20 ขึ้นไป npm ติดตั้งโปรแกรมสำหรับระบบของคุณเป็น dependency แบบเลือกได้ จึงอย่าตัด dependency แบบเลือกได้ออก

การเปลี่ยนเครือข่ายบน Windows ต้องใช้สิทธิ์ผู้ดูแลระบบ: เปิดเทอร์มินัลด้วย "เรียกใช้ในฐานะผู้ดูแลระบบ" บน Linux ต้องใช้ root หรือผู้ใช้ที่รัน sudo ได้โดยไม่ต้องใส่รหัสผ่าน และเมื่อนั้นจะมีเพียงโปรแกรมที่รันภายใต้ sudo รันเนอร์ Windows ที่ GitHub โฮสต์ทำงานด้วยสิทธิ์ยกระดับ และรันเนอร์ Ubuntu อนุญาตให้ใช้ sudo ดังนั้น workflow จึงไม่ต้องมีขั้นตอนเพิ่ม

การทดสอบบนเครือข่ายช้า

บันทึกโค้ดนี้เป็น tests/slow.spec.js แล้วรัน npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

การทดสอบผ่านเพราะหน้าเว็บมาถึงช้าลงจริง: ทุกแพ็กเก็ตที่ไปและกลับจากเซิร์ฟเวอร์นั้นต้องรอ 500 ms เมื่อการทดสอบจบ เครือข่ายจะกลับเป็นปกติ วัดบน Windows ด้วย latency: 200: คำขอไปยังเซิร์ฟเวอร์ในเป้าหมายเพิ่มจาก 0.8 ms เป็น 404 ms เพราะทั้งคำขอและคำตอบต้องรอ และหน้าเว็บใน Chromium เพิ่มจาก 13 ms เป็น 416 ms ระหว่างนั้นเซิร์ฟเวอร์ภายในเครื่องอีกตัวที่อยู่นอกเป้าหมายตอบใน 1.6 ms

ยังไม่มีสิทธิ์ในมือ? badNetwork({ simulate: true, latency: 500 }) รันโปรแกรมกับทราฟฟิกที่สร้างขึ้นและไม่เปลี่ยนอะไรในเครือข่าย ใช้ตรวจว่าแพ็กเกจติดตั้งถูกต้อง โดยไม่ทำให้อะไรช้าลง

fixture ชื่อ badNetwork

นำเข้า test และ expect จาก beannetworktester/playwright แทน @playwright/test เมื่อเรียก badNetwork จะเริ่มเซสชัน และเสร็จทันทีที่เครือข่ายช้าลงแล้ว เซสชันหยุดเมื่อการทดสอบจบ ไม่ว่าจะผ่าน ล้มเหลว หรือแครช และสรุปของโปรแกรมจะแนบไปกับรายงานการทดสอบในชื่อ bad-network หากต้องการเปลี่ยนสภาพเครือข่ายกลางการทดสอบ ให้หยุดเซสชันแรกก่อนเริ่มเซสชันถัดไป:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

นอก Playwright Test ให้ใช้ badNetwork จาก require('beannetworktester') เพื่อเริ่มเซสชันเดียวกัน: const session = await badNetwork({ ... }) และ await session.stop() จะจบเซสชันพร้อมคืนสรุป

เซสชันเล็งไปที่อะไร

ทุกเซสชันเล็งไปที่บางสิ่ง และมีเพียงทราฟฟิกนั้นที่เปลี่ยน เซสชันที่ไม่มีเป้าหมายจะทำให้ทุกการเชื่อมต่อของเครื่องช้าลง รวมถึงของตัวรันการทดสอบเอง จึงไม่เริ่มทำงานเลย

  • server: 'http://localhost:3000' ทำให้ทุกการเชื่อมต่อไปยังที่อยู่และพอร์ตนั้นช้าลง ไม่ว่าจะมาจากเบราว์เซอร์ จากเซิร์ฟเวอร์ API ของคุณ หรือจากโปรแกรมอื่นใด ใช้ 'db.local:5432' และรายการเซิร์ฟเวอร์ได้เช่นกัน นี่คือตัวเลือกแรก และแม่นยำทั้งบน Windows และ Linux
  • process: 'self' ทำให้ worker ของการทดสอบและทุกโปรแกรมที่มันเริ่ม เช่น เบราว์เซอร์ ช้าลง โปรเซสที่การทดสอบของคุณเริ่มเองให้ส่งเป็น ChildProcess ของมัน
  • dstPort, dstIp และ target คือเป้าหมายของโปรแกรมเอง เขียนด้วยไวยากรณ์ของโปรแกรม สำหรับ API บนพอร์ตหรือที่อยู่ที่รู้จัก มันเข้าถึงทุกอย่างที่ตรงกัน: dstPort: 443 คือทุกการเชื่อมต่อ HTTPS ของเครื่อง รวมถึงของโปรแกรมแก้ไขโค้ดของคุณ และ target: 'node' คือทุกโปรแกรมที่มี "node" อยู่ในชื่อ

เป้าหมายที่ให้มาพร้อมกันจะจำกัดกันและกัน: server คู่กับ process: 'self' จะทำให้ช้าลงเฉพาะการเชื่อมต่อของ worker นี้ไปยังเซิร์ฟเวอร์นั้น บน Linux process และ target จะเริ่มมีผลกับการเชื่อมต่อใหม่ช้าได้ถึงราว 0.2 วินาทีหลังเปิด ดังนั้นเมื่อคำขอแรกสำคัญ ให้เล็งไปที่เซิร์ฟเวอร์

เซสชันทำอะไรได้บ้าง

ทุกการตั้งค่าคือหนึ่งในตัวเลือกบรรทัดคำสั่งของโปรแกรม latency: 300 เพิ่ม 300 ms ให้ทุกแพ็กเก็ต jitter: 100 ทำให้ความหน่วงนั้นแกว่ง loss: 5 ทิ้งแพ็กเก็ต 5 % down และ up จำกัดความเร็วเป็น KB/s และ loss: 100 ตัดเซิร์ฟเวอร์ออก preset: 'presets.3g' คือโปรไฟล์ลิงก์ทั้งชุด และ seed: 42 ทำให้สุ่มเหมือนเดิมทุกครั้งที่รัน สถานการณ์จะเปลี่ยนสภาพเครือข่ายตามวินาทีที่ผ่านไป: scenario: 'scenarios/cafe-wifi.json' ขั้นตอนในสถานการณ์เปลี่ยนพฤติกรรมของเครือข่ายได้ แต่เปลี่ยนสิ่งที่เซสชันเล็งไม่ได้

worker แบบขนานและข้อจำกัด

  • ทีละหนึ่ง สองเซสชันบนทราฟฟิกเดียวกันจะซ้อนกัน worker แบบขนานจึงผลัดกันทำ แต่ละตัวรอได้สูงสุด wait วินาที (600 ถ้าไม่ได้กำหนดค่าอื่น) เซสชันที่สองในการทดสอบเดียวกันจะถูกปฏิเสธทันที
  • จบพร้อมการทดสอบ ถ้า worker ของการทดสอบตาย โปรแกรมจะรู้และหยุดทันที duration (300 วินาที ถ้าไม่ได้กำหนดค่าอื่น) คือเวลานานที่สุดที่เซสชันรันได้ไม่ว่ากรณีใด
  • บอกเมื่อไม่ได้ทำอะไร เซสชันที่ไม่ได้ทำให้อะไรช้าลง เพราะไม่มีอะไรไปถึงเป้าหมาย จะจบด้วย BadNetworkWarning สาเหตุที่พบบ่อยคือแอปคุยกับที่อยู่อื่นที่ไม่ใช่เป้าหมาย เช่น คอนเทนเนอร์
  • macOS โปรแกรมทำงานบน Windows และ Linux บน Mac ให้รันการทดสอบในคอนเทนเนอร์หรือเครื่องเสมือน Linux x86_64 หรือบนรันเนอร์ CI
