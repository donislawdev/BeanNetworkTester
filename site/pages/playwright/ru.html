Медленная сеть и потеря пакетов в тестах Playwright

Playwright умеет отключить страницу от сети и замедлить Chromium через DevTools. Пакет beannetworktester из npm вместо этого замедляет настоящую сеть, под браузером: задержка, потеря пакетов, ограничение скорости или полный обрыв, для сервера, с которым говорит ваш тест. Chromium, Firefox и WebKit замедляются одинаково, вместе с WebSocket. Пакет несёт программу Bean Network Tester и запускает её на время теста, в Windows и Linux. Он выходит с каждым стабильным выпуском начиная с 1.1.0.

Установка

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Нужны Windows x64 или Linux x64 (glibc 2.39 или новее, например Ubuntu 24.04) и Node 20 или новее. npm ставит программу для вашей системы как необязательную зависимость, поэтому не отключайте необязательные зависимости.

Чтобы менять сеть, в Windows нужны права администратора: откройте терминал через «Запуск от имени администратора». В Linux нужен root или пользователь, которому разрешён sudo без пароля, и тогда под sudo работает только программа. Размещённые раннеры GitHub с Windows работают с повышенными правами, а раннеры с Ubuntu разрешают sudo, так что workflow не нужен дополнительный шаг.

Тест на медленной сети

Сохраните это как tests/slow.spec.js и запустите npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

Тест проходит, потому что страница действительно приходит позже: каждый пакет к этому серверу и от него ждёт 500 мс. Когда тест заканчивается, сеть снова работает как обычно. Измерено в Windows с latency: 200: запрос к серверу в цели вырос с 0,8 мс до 404 мс, потому что ждут и запрос, и ответ, а страница в Chromium с 13 мс до 416 мс. Другой локальный сервер, вне цели, отвечал в это время за 1,6 мс.

Прав под рукой нет? badNetwork({ simulate: true, latency: 500 }) запускает программу на выдуманном трафике и ничего не меняет в сети. Это проверяет, что пакет установлен правильно, и ничего не замедляет.

Фикстура badNetwork

Импортируйте test и expect из beannetworktester/playwright вместо @playwright/test. badNetwork начинает сессию, когда вы её вызываете, и завершает ожидание, как только сеть стала медленной. Сессия останавливается вместе с концом теста, прошёл он, упал или аварийно завершился, а сводка программы прикрепляется к отчёту теста как bad-network. Чтобы поменять условия посреди теста, остановите первую сессию, прежде чем начинать следующую:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Вне Playwright Test ту же сессию начинает badNetwork из require('beannetworktester'): const session = await badNetwork({ ... }), а await session.stop() завершает её и возвращает сводку.

На что нацелена сессия

Каждая сессия на что-то нацелена, и меняется только этот трафик. Сессия без цели замедлила бы каждое соединение машины, в том числе соединения самого запускателя тестов, поэтому она не запускается.

  • server: 'http://localhost:3000' замедляет каждое соединение с этим адресом и портом, из браузера, из вашего API-сервера или из любой другой программы. Подходят и 'db.local:5432', и список серверов. Это первый выбор, и он точен в Windows и Linux.
  • process: 'self' замедляет тестовый воркер и каждую программу, которую он запустил, например его браузер. Процесс, который запустил сам тест, передаётся как его ChildProcess.
  • dstPort, dstIp и target это собственные цели программы, записанные в её синтаксисе, для API на известном порту или адресе. Они достают всё, что подходит: dstPort: 443 это каждое HTTPS-соединение машины, в том числе соединения вашего редактора, а target: 'node' каждая программа с «node» в имени.

Цели, заданные вместе, сужают друг друга: server с process: 'self' замедляет только соединения этого воркера с этим сервером. В Linux process и target начинают действовать на новое соединение с опозданием примерно до 0,2 секунды после его открытия, поэтому цельтесь в сервер, когда важен первый запрос.

Что умеет сессия

Каждая настройка это один из параметров командной строки программы. latency: 300 добавляет 300 мс каждому пакету, jitter: 100 делает эту задержку переменной, loss: 5 теряет 5 % пакетов, down и up ограничивают скорость в КБ/с, а loss: 100 отрезает сервер. preset: 'presets.3g' это целый профиль канала, а seed: 42 даёт одни и те же случайные решения при каждом запуске. Сценарий меняет условия по мере того, как идут секунды: scenario: 'scenarios/cafe-wifi.json'. Шаг сценария может изменить поведение сети, но не то, на что нацелена сессия.

Параллельные воркеры и ограничения

  • По одной. Две сессии на одном трафике сложились бы, поэтому параллельные воркеры ждут своей очереди, каждый до wait секунд (600, если не задать другое значение). Вторая сессия в том же тесте сразу отклоняется.
  • Она заканчивается вместе с тестом. Если тестовый воркер умирает, программа это видит и сразу останавливается. duration (300 секунд, если не задать другое значение) в любом случае самое долгое время работы сессии.
  • Она говорит, когда ничего не сделала. Сессия, которая ничего не замедлила, потому что до её цели ничего не дошло, завершается предупреждением BadNetworkWarning. Обычно это значит, что приложение говорит с другим адресом, а не с целью, например с контейнером.
  • macOS. Программа работает в Windows и Linux. На Mac запускайте тесты в контейнере или виртуальной машине с Linux x86_64 либо на раннере CI.
