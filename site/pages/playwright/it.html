Simulare rete lenta e perdita di pacchetti nei test Playwright

Playwright può mettere offline una pagina e rallentare Chromium tramite DevTools. Il pacchetto beannetworktester su npm rallenta invece la rete vera, sotto il browser: latenza, perdita di pacchetti, un limite di velocità o un'interruzione completa, per il server con cui parla il tuo test. Chromium, Firefox e WebKit rallentano allo stesso modo, WebSocket compresi. Il pacchetto contiene il programma di Bean Network Tester e lo esegue per la durata di un test, su Windows e Linux. Esce con ogni versione stabile dalla 1.1.0 in poi.

Installazione

npm install -D @playwright/test beannetworktester
npx playwright install chromium

Richiede Windows x64 o Linux x64 (glibc 2.39 o più recente, come Ubuntu 24.04) e Node 20 o più recente. npm installa il programma per il tuo sistema come dipendenza opzionale, quindi non escludere le dipendenze opzionali.

Cambiare la rete richiede i diritti di amministratore su Windows: apri il terminale con "Esegui come amministratore". Su Linux richiede root, o un utente che possa usare sudo senza password, e allora solo il programma gira con sudo. I runner Windows ospitati da GitHub girano con privilegi elevati e i suoi runner Ubuntu permettono sudo, quindi un workflow non ha bisogno di passaggi in più.

Un test su una rete lenta

Salva questo come tests/slow.spec.js ed esegui npx playwright test:

import http from 'node:http';
import { test, expect } from 'beannetworktester/playwright';

let server;
test.beforeAll(async () => {
  server = http.createServer((request, response) => response.end('<h1>Hello</h1>'));
  await new Promise((done) => server.listen(8000, done));
});
test.afterAll(() => server.close());

test('a page takes longer on a slow network', async ({ page, badNetwork }) => {
  await badNetwork({ server: 'http://localhost:8000', latency: 500 });
  const started = Date.now();
  await page.goto('http://localhost:8000');
  await expect(page.locator('h1')).toHaveText('Hello');
  expect(Date.now() - started).toBeGreaterThanOrEqual(500);
});

Il test passa perché la pagina arriva davvero più tardi: ogni pacchetto verso quel server e da quel server aspetta 500 ms. Alla fine del test la rete torna normale. Misurato su Windows con latency: 200: una richiesta al server nell'obiettivo è passata da 0,8 ms a 404 ms, perché aspettano sia la richiesta sia la risposta, e una pagina in Chromium da 13 ms a 416 ms. Un altro server locale, fuori dall'obiettivo, rispondeva intanto in 1,6 ms.

Niente diritti a portata di mano? badNetwork({ simulate: true, latency: 500 }) esegue il programma su traffico inventato e non cambia nulla nella rete. Verifica che il pacchetto sia installato bene, senza rallentare niente.

La fixture badNetwork

Importa test ed expect da beannetworktester/playwright invece che da @playwright/test. badNetwork avvia una sessione quando la chiami e si risolve appena la rete è lenta. La sessione si ferma alla fine del test, che sia passato, fallito o andato in crash, e il riepilogo del programma viene allegato al report del test come bad-network. Per cambiare le condizioni a metà, ferma la prima sessione prima di avviare la successiva:

test('the app recovers when the API comes back', async ({ page, badNetwork }) => {
  const outage = await badNetwork({ server: 'http://localhost:8000', loss: 100 });
  await page.goto('http://localhost:3000');
  await expect(page.getByText('Offline')).toBeVisible();
  await outage.stop();
  await expect(page.getByText('Offline')).toBeHidden();
});

Fuori da Playwright Test, badNetwork da require('beannetworktester') avvia la stessa sessione: const session = await badNetwork({ ... }), e await session.stop() la termina e restituisce il riepilogo.

A cosa punta una sessione

Ogni sessione punta a qualcosa, e cambia solo quel traffico. Una sessione senza obiettivo rallenterebbe ogni connessione della macchina, comprese quelle dello stesso esecutore dei test, quindi non parte.

  • server: 'http://localhost:3000' rallenta ogni connessione verso quell'indirizzo e quella porta, dal browser, dal tuo server API o da qualsiasi altro programma. Funzionano anche 'db.local:5432' e un elenco di server. È la prima scelta, ed è esatta su Windows e Linux.
  • process: 'self' rallenta il worker dei test e ogni programma che ha avviato, come il suo browser. Un processo avviato dal test stesso si passa come il suo ChildProcess.
  • dstPort, dstIp e target sono gli obiettivi propri del programma, scritti nella sua sintassi, per un'API su una porta o un indirizzo noti. Raggiungono tutto ciò che corrisponde: dstPort: 443 è ogni connessione HTTPS della macchina, comprese quelle del tuo editor, e target: 'node' ogni programma con "node" nel nome.

Obiettivi dati insieme si restringono a vicenda: server con process: 'self' rallenta solo le connessioni di questo worker verso quel server. Su Linux, process e target raggiungono una connessione nuova fino a circa 0,2 secondi dopo la sua apertura, quindi punta al server quando conta la prima richiesta.

Cosa può fare una sessione

Ogni impostazione è una delle opzioni da riga di comando del programma. latency: 300 aggiunge 300 ms a ogni pacchetto, jitter: 100 fa variare quel ritardo, loss: 5 scarta il 5 % dei pacchetti, down e up limitano la velocità in KB/s, e loss: 100 taglia fuori il server. preset: 'presets.3g' è un intero profilo di collegamento, e seed: 42 ripete le stesse scelte casuali a ogni esecuzione. Uno scenario cambia le condizioni col passare dei secondi: scenario: 'scenarios/cafe-wifi.json'. Un passo dello scenario può cambiare come si comporta la rete, ma non a cosa punta la sessione.

Worker in parallelo e limiti

  • Una alla volta. Due sessioni sullo stesso traffico si sommerebbero, quindi i worker in parallelo fanno a turno, ciascuno aspettando fino a wait secondi (600 se non ne indichi un altro). Una seconda sessione nello stesso test viene rifiutata subito.
  • Finisce con il test. Se il worker dei test muore, il programma se ne accorge e si ferma subito. duration (300 secondi se non ne indichi un altro) è in ogni caso la durata massima di una sessione.
  • Dice quando non ha fatto niente. Una sessione che non ha rallentato niente, perché niente ha raggiunto il suo obiettivo, finisce con un BadNetworkWarning. Di solito l'app parla con un indirizzo diverso dall'obiettivo, come un container.
  • macOS. Il programma gira su Windows e Linux. Su un Mac, esegui i test in un container o in una macchina virtuale Linux x86_64, oppure su un runner di CI.
