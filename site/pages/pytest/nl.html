Netwerklatentie en pakketverlies simuleren in pytest

Niets gemockt: het pakket beannetworktester op PyPI geeft pytest een fixture bad_network die het echte netwerk vertraagt zolang een test duurt. Latentie, pakketverlies, een snelheidslimiet of een volledige storing, voor één server of één proces, terwijl je app, je browser en je server echt met elkaar praten. Het pakket bevat het programma van Bean Network Tester en draait het op Windows en Linux. Het verschijnt met elke stabiele versie vanaf 1.1.0.

Installeren

pip install beannetworktester

Het heeft Windows x64 of Linux x64 nodig (glibc 2.39 of nieuwer, zoals Ubuntu 24.04) en Python 3.10 of nieuwer.

Het netwerk veranderen vraagt op Windows beheerdersrechten: open de terminal met "Als administrator uitvoeren". Op Linux vraagt het root, of een gebruiker die sudo zonder wachtwoord mag gebruiken, en dan draait alleen het programma onder sudo. De gehoste Windows-runners van GitHub draaien met verhoogde rechten en de Ubuntu-runners staan sudo toe, dus een workflow heeft geen extra stap nodig.

Een test op een traag netwerk

Sla dit op als test_slow.py en draai pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

De test slaagt omdat het antwoord echt later aankomt: elk pakket naar die server en terug wacht 500 ms. Als de test eindigt, is het netwerk weer normaal. Gemeten op Windows met latency=200: een verzoek aan de server in het doel ging van 4 ms naar 404 ms, omdat verzoek en antwoord allebei wachten, en een pagina in Chromium van 61 ms naar 412 ms. Een andere lokale server, buiten het doel, antwoordde intussen in 11 ms.

Geen rechten bij de hand? bad_network(simulate=True, latency=500) draait het programma op verzonnen verkeer en verandert niets aan het netwerk. Het controleert of het pakket goed is ingesteld en vertraagt niets.

De fixture bad_network

pytest vindt de fixture zelf zodra het pakket is geïnstalleerd. bad_network start een sessie als je het aanroept en keert terug zodra het netwerk traag is. De sessie stopt als de test eindigt, of die nu slaagde, faalde of crashte, en de samenvatting van het programma gaat naar de user_properties van de test en van daar naar een JUnit-XML-rapport. Om halverwege de omstandigheden te veranderen, stop je de eerste sessie voordat je de volgende start:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Buiten pytest start from beannetworktester import bad_network dezelfde sessie, en with bad_network(...) as session: stopt hem aan het eind van het blok.

Playwright voor Python

Playwright voor Python draait op pytest, dus de fixture is dezelfde. Chromium, Firefox en WebKit worden even sterk vertraagd, WebSockets inbegrepen, omdat het netwerk zelf traag is en niet het beeld dat de browser ervan heeft:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Waar een sessie op mikt

Elke sessie mikt ergens op, en alleen dat verkeer verandert. Een sessie zonder doel zou elke verbinding van de machine vertragen, ook die van de testrunner zelf, dus die start niet.

  • server="http://localhost:3000" vertraagt elke verbinding met dat adres en die poort, vanuit je app, je browser of elk ander programma. "db.local:5432", ("10.0.0.5", 443) en een lijst van servers werken ook. Dit is de eerste keuze, en die is exact op Windows en Linux.
  • process="self" vertraagt het testproces en elk programma dat het startte, zoals de browser van Playwright. Een proces dat je test zelf startte, geef je mee als zijn subprocess.Popen.
  • dst_port, dst_ip en target zijn de eigen doelen van het programma, geschreven in zijn syntaxis, voor een API op een bekende poort of een bekend adres. Ze bereiken alles wat overeenkomt: dst_port=443 is elke HTTPS-verbinding van de machine, ook die van je editor, en target="python" elk programma met "python" in de naam.

Doelen die samen zijn opgegeven, beperken elkaar: server= met process="self" vertraagt alleen de verbindingen van deze test met die server. Op Linux bereiken process= en target een nieuwe verbinding tot ongeveer 0,2 seconde na het openen, dus mik op de server als het eerste verzoek telt.

Wat een sessie kan

Elke instelling is een van de opdrachtregelopties van het programma, geschreven met _ in plaats van -. latency=300 voegt 300 ms toe aan elk pakket, jitter=100 laat die vertraging variëren, loss=5 laat 5 % van de pakketten vallen, down en up beperken de snelheid in KB/s, en loss=100 snijdt de server af. preset="presets.3g" is een volledig verbindingsprofiel, en seed=42 maakt bij elke run dezelfde willekeurige keuzes. Een scenario verandert de omstandigheden naarmate de seconden verstrijken: scenario="scenarios/cafe-wifi.json". Een stap in het scenario mag veranderen hoe het netwerk zich gedraagt, maar niet waar de sessie op mikt.

pytest-xdist en grenzen

  • Eén tegelijk. Twee sessies op hetzelfde verkeer zouden optellen, dus de workers van pytest-xdist wachten op hun beurt, elk tot wait seconden (600 als je niets anders opgeeft). Een tweede sessie in dezelfde test wordt meteen geweigerd.
  • Hij eindigt met de test. Als het testproces sterft, ziet het programma dat en stopt het meteen. duration (300 seconden als je niets anders opgeeft) is in elk geval het langste dat een sessie mag duren.
  • Hij zegt het als hij niets deed. Een sessie die niets vertraagde, omdat niets zijn doel bereikte, eindigt met een BadNetworkWarning. Meestal praat de app dan met een ander adres dan het doel, zoals een container.
  • macOS. Het programma draait op Windows en Linux. Draai de tests op een Mac in een Linux-x86_64-container of virtuele machine, of op een CI-runner.
