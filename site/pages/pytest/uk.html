Затримка мережі і втрата пакетів у pytest

Жодних моків: пакет beannetworktester з PyPI дає pytest фікстуру bad_network, яка сповільнює справжню мережу на час тесту. Затримка, втрата пакетів, обмеження швидкості або повний обрив, для одного сервера чи одного процесу, поки ваш застосунок, браузер і сервер справді говорять один з одним. Пакет містить програму Bean Network Tester і запускає її у Windows і Linux. Він виходить з кожним стабільним випуском, починаючи з 1.1.0.

Встановлення

pip install beannetworktester

Потрібні Windows x64 або Linux x64 (glibc 2.39 або новіша, наприклад Ubuntu 24.04) і Python 3.10 або новіший.

Щоб змінювати мережу, у Windows потрібні права адміністратора: відкрийте термінал через «Запуск від імені адміністратора». У Linux потрібен root або користувач, якому дозволено sudo без пароля, і тоді під sudo працює лише програма. Розміщені ранери GitHub з Windows працюють із підвищеними правами, а ранери з Ubuntu дозволяють sudo, тож workflow не потребує додаткового кроку.

Тест на повільній мережі

Збережіть це як test_slow.py і запустіть pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Тест проходить, бо відповідь справді приходить пізніше: кожен пакет до цього сервера й від нього чекає 500 мс. Коли тест закінчується, мережа знову працює як звичайно. Виміряно у Windows з latency=200: запит до сервера в цілі зріс з 4 мс до 404 мс, бо чекають і запит, і відповідь, а сторінка в Chromium з 61 мс до 412 мс. Інший локальний сервер, поза ціллю, відповідав тим часом за 11 мс.

Прав під рукою немає? bad_network(simulate=True, latency=500) запускає програму на вигаданому трафіку й нічого не змінює в мережі. Це перевіряє, що пакет установлено правильно, і нічого не сповільнює.

Фікстура bad_network

pytest сам знаходить фікстуру, щойно пакет установлено. bad_network починає сесію, коли ви її викликаєте, і повертається, щойно мережа стала повільною. Сесія зупиняється разом із кінцем тесту, чи він пройшов, чи впав, чи аварійно завершився, а підсумок програми потрапляє до user_properties тесту, а звідти до звіту JUnit XML. Щоб змінити умови посеред тесту, зупиніть першу сесію, перш ніж починати наступну:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Поза pytest ту саму сесію починає from beannetworktester import bad_network, а with bad_network(...) as session: зупиняє її в кінці блоку.

Playwright для Python

Playwright для Python працює на pytest, тож фікстура та сама. Chromium, Firefox і WebKit сповільнюються однаково, разом із WebSocket, бо повільна сама мережа, а не уявлення браузера про неї:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

На що націлена сесія

Кожна сесія на щось націлена, і змінюється лише цей трафік. Сесія без цілі сповільнила б кожне з'єднання машини, зокрема з'єднання самого запускача тестів, тому вона не запускається.

  • server="http://localhost:3000" сповільнює кожне з'єднання з цією адресою та портом, з вашого застосунку, браузера чи будь-якої іншої програми. Підходять і "db.local:5432", ("10.0.0.5", 443), і список серверів. Це перший вибір, і він точний у Windows і Linux.
  • process="self" сповільнює тестовий процес і кожну програму, яку він запустив, наприклад браузер Playwright. Процес, який запустив сам тест, передається як його subprocess.Popen.
  • dst_port, dst_ip і target це власні цілі програми, записані в її синтаксисі, для API на відомому порту чи адресі. Вони дістають усе, що підходить: dst_port=443 це кожне HTTPS-з'єднання машини, зокрема з'єднання вашого редактора, а target="python" кожна програма з «python» в назві.

Цілі, задані разом, звужують одна одну: server= з process="self" сповільнює лише з'єднання цього тесту з цим сервером. У Linux process= і target починають діяти на нове з'єднання із запізненням приблизно до 0,2 секунди після його відкриття, тож цільтеся в сервер, коли важливий перший запит.

Що вміє сесія

Кожне налаштування це один із параметрів командного рядка програми, записаний через _ замість -. latency=300 додає 300 мс кожному пакету, jitter=100 робить цю затримку змінною, loss=5 губить 5 % пакетів, down і up обмежують швидкість у КБ/с, а loss=100 відрізає сервер. preset="presets.3g" це цілий профіль каналу, а seed=42 дає ті самі випадкові рішення під час кожного запуску. Сценарій змінює умови з плином секунд: scenario="scenarios/cafe-wifi.json". Крок сценарію може змінити поведінку мережі, але не те, на що націлена сесія.

pytest-xdist і обмеження

  • По одній. Дві сесії на одному трафіку додалися б, тому воркери pytest-xdist чекають своєї черги, кожен до wait секунд (600, якщо не задати інше значення). Друга сесія в тому самому тесті одразу відхиляється.
  • Вона закінчується разом із тестом. Якщо тестовий процес помирає, програма це бачить і одразу зупиняється. duration (300 секунд, якщо не задати інше значення) у будь-якому разі найдовший час роботи сесії.
  • Вона каже, коли нічого не зробила. Сесія, яка нічого не сповільнила, бо до її цілі нічого не дійшло, завершується попередженням BadNetworkWarning. Зазвичай це означає, що застосунок говорить з іншою адресою, ніж ціль, наприклад з контейнером.
  • macOS. Програма працює у Windows і Linux. На Mac запускайте тести в контейнері чи віртуальній машині з Linux x86_64 або на ранері CI.
