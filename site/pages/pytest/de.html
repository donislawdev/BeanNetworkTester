Netzwerklatenz und Paketverlust in pytest simulieren

Nichts gemockt: Das Paket beannetworktester auf PyPI gibt pytest eine Fixture bad_network, die das echte Netz für die Dauer eines Tests verlangsamt. Latenz, Paketverlust, ein Tempolimit oder ein ganzer Ausfall, für einen Server oder einen Prozess, während Ihre App, Ihr Browser und Ihr Server wirklich miteinander sprechen. Das Paket enthält das Programm von Bean Network Tester und führt es unter Windows und Linux aus. Es erscheint mit jeder stabilen Version ab 1.1.0.

Installation

pip install beannetworktester

Es braucht Windows x64 oder Linux x64 (glibc 2.39 oder neuer, etwa Ubuntu 24.04) und Python 3.10 oder neuer.

Das Netz zu verändern braucht unter Windows Administratorrechte: Öffnen Sie das Terminal mit „Als Administrator ausführen“. Unter Linux braucht es root oder einen Benutzer, der sudo ohne Passwort ausführen darf, und dann läuft nur das Programm unter sudo. Die gehosteten Windows-Runner von GitHub laufen mit erhöhten Rechten und die Ubuntu-Runner erlauben sudo, ein Workflow braucht also keinen zusätzlichen Schritt.

Ein Test in einem langsamen Netz

Speichern Sie das als test_slow.py und führen Sie pytest aus:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Der Test besteht, weil die Antwort wirklich später ankommt: Jedes Paket zu diesem Server und von ihm wartet 500 ms. Wenn der Test endet, ist das Netz wieder normal. Gemessen unter Windows mit latency=200: Eine Anfrage an den Server im Ziel stieg von 4 ms auf 404 ms, weil Anfrage und Antwort beide warten, und eine Seite in Chromium von 61 ms auf 412 ms. Ein anderer lokaler Server außerhalb des Ziels antwortete währenddessen in 11 ms.

Keine Rechte zur Hand? bad_network(simulate=True, latency=500) führt das Programm mit erfundenem Verkehr aus und ändert nichts am Netz. Es prüft, ob das Paket richtig eingerichtet ist, und verlangsamt nichts.

Die Fixture bad_network

pytest findet die Fixture von selbst, sobald das Paket installiert ist. bad_network startet eine Sitzung, wenn Sie es aufrufen, und kehrt zurück, sobald das Netz langsam ist. Die Sitzung endet mit dem Test, ob er bestanden hat, fehlgeschlagen oder abgestürzt ist, und die Zusammenfassung des Programms landet in den user_properties des Tests und von dort in einem JUnit-XML-Bericht. Um die Bedingungen mittendrin zu ändern, beenden Sie die erste Sitzung, bevor Sie die nächste starten:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Außerhalb von pytest startet from beannetworktester import bad_network dieselbe Sitzung, und with bad_network(...) as session: beendet sie am Ende des Blocks.

Playwright für Python

Playwright für Python läuft auf pytest, die Fixture ist also dieselbe. Chromium, Firefox und WebKit werden gleich verlangsamt, WebSockets eingeschlossen, weil das Netz selbst langsam ist und nicht nur die Vorstellung des Browsers davon:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Worauf eine Sitzung zielt

Jede Sitzung zielt auf etwas, und nur dieser Verkehr ändert sich. Eine Sitzung ohne Ziel würde jede Verbindung des Rechners verlangsamen, auch die des Testrunners selbst, deshalb startet sie gar nicht.

  • server="http://localhost:3000" verlangsamt jede Verbindung zu dieser Adresse und diesem Port, von Ihrer App, Ihrem Browser oder jedem anderen Programm. "db.local:5432", ("10.0.0.5", 443) und eine Liste von Servern gehen auch. Das ist die erste Wahl, und sie ist unter Windows und Linux exakt.
  • process="self" verlangsamt den Testprozess und jedes Programm, das er gestartet hat, etwa den Browser von Playwright. Einen Prozess, den Ihr Test selbst gestartet hat, übergeben Sie als seinen subprocess.Popen.
  • dst_port, dst_ip und target sind die eigenen Ziele des Programms, geschrieben in seiner Syntax, für eine API an einem bekannten Port oder einer bekannten Adresse. Sie erreichen alles, was passt: dst_port=443 ist jede HTTPS-Verbindung des Rechners, auch die Ihres Editors, und target="python" jedes Programm mit „python“ im Namen.

Zusammen angegebene Ziele engen einander ein: server= mit process="self" verlangsamt nur die Verbindungen dieses Tests zu diesem Server. Unter Linux erreichen process= und target eine neue Verbindung bis zu etwa 0,2 Sekunden nach ihrem Öffnen, zielen Sie also auf den Server, wenn die erste Anfrage zählt.

Was eine Sitzung kann

Jede Einstellung ist eine der Befehlszeilenoptionen des Programms, geschrieben mit _ statt -. latency=300 fügt jedem Paket 300 ms hinzu, jitter=100 lässt diese Verzögerung schwanken, loss=5 verwirft 5 % der Pakete, down und up begrenzen das Tempo in KB/s, und loss=100 schneidet den Server ab. preset="presets.3g" ist ein ganzes Verbindungsprofil, und seed=42 trifft bei jedem Lauf dieselben Zufallsentscheidungen. Ein Szenario ändert die Bedingungen im Lauf der Sekunden: scenario="scenarios/cafe-wifi.json". Ein Schritt im Szenario darf ändern, wie sich das Netz verhält, aber nicht, worauf die Sitzung zielt.

pytest-xdist und Grenzen

  • Eine nach der anderen. Zwei Sitzungen auf demselben Verkehr würden sich addieren, deshalb wechseln sich die Worker von pytest-xdist ab und warten jeweils bis zu wait Sekunden (600, wenn Sie nichts anderes angeben). Eine zweite Sitzung im selben Test wird sofort abgelehnt.
  • Sie endet mit dem Test. Stirbt der Testprozess, bemerkt das Programm es und hält sofort an. duration (300 Sekunden, wenn Sie nichts anderes angeben) ist in jedem Fall die längste Laufzeit einer Sitzung.
  • Sie sagt, wenn sie nichts getan hat. Eine Sitzung, die nichts verlangsamt hat, weil nichts ihr Ziel erreichte, endet mit einer BadNetworkWarning. Meist spricht die App dann mit einer anderen Adresse als dem Ziel, etwa mit einem Container.
  • macOS. Das Programm läuft unter Windows und Linux. Auf einem Mac führen Sie die Tests in einem Linux-x86_64-Container, in einer virtuellen Maschine oder auf einem CI-Runner aus.
