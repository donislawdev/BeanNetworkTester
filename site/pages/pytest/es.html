Simula latencia de red y pérdida de paquetes en pytest

Nada simulado en el código: el paquete beannetworktester de PyPI le da a pytest un fixture bad_network que ralentiza la red real mientras dura una prueba. Latencia, pérdida de paquetes, un límite de velocidad o un corte total, para un servidor o un proceso, mientras tu aplicación, tu navegador y tu servidor hablan de verdad entre sí. El paquete lleva el programa de Bean Network Tester y lo ejecuta en Windows y Linux. Se publica con cada versión estable a partir de la 1.1.0.

Instalación

pip install beannetworktester

Necesita Windows x64 o Linux x64 (glibc 2.39 o más reciente, como Ubuntu 24.04) y Python 3.10 o más reciente.

Cambiar la red requiere derechos de administrador en Windows: abre la terminal con «Ejecutar como administrador». En Linux requiere root, o un usuario que pueda usar sudo sin contraseña, y entonces solo el programa corre con sudo. Los runners de Windows alojados por GitHub corren con privilegios elevados y sus runners de Ubuntu permiten sudo, así que un workflow no necesita ningún paso extra.

Una prueba en una red lenta

Guarda esto como test_slow.py y ejecuta pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

La prueba pasa porque la respuesta de verdad llega más tarde: cada paquete hacia ese servidor y desde él espera 500 ms. Cuando la prueba termina, la red vuelve a la normalidad. Medido en Windows con latency=200: una petición al servidor del objetivo pasó de 4 ms a 404 ms, porque esperan tanto la petición como la respuesta, y una página en Chromium de 61 ms a 412 ms. Otro servidor local, fuera del objetivo, respondía mientras tanto en 11 ms.

¿No tienes los derechos a mano? bad_network(simulate=True, latency=500) ejecuta el programa con tráfico inventado y no cambia nada en la red. Comprueba que el paquete está bien instalado y no ralentiza nada.

El fixture bad_network

pytest encuentra el fixture solo en cuanto el paquete está instalado. bad_network inicia una sesión cuando lo llamas y vuelve en cuanto la red está lenta. La sesión se detiene cuando termina la prueba, haya pasado, fallado o se haya caído, y el resumen del programa va a las user_properties de la prueba y de ahí a un informe JUnit XML. Para cambiar las condiciones a mitad de la prueba, detén la primera sesión antes de iniciar la siguiente:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Fuera de pytest, from beannetworktester import bad_network inicia la misma sesión, y with bad_network(...) as session: la detiene al final del bloque.

Playwright para Python

Playwright para Python funciona sobre pytest, así que el fixture es el mismo. Chromium, Firefox y WebKit se ralentizan igual, WebSockets incluidos, porque la que es lenta es la red misma, no la idea que el navegador tiene de ella:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

A qué apunta una sesión

Cada sesión apunta a algo, y solo ese tráfico cambia. Una sesión sin objetivo ralentizaría todas las conexiones de la máquina, incluidas las del propio ejecutor de pruebas, así que no arranca.

  • server="http://localhost:3000" ralentiza cada conexión a esa dirección y ese puerto, desde tu aplicación, tu navegador o cualquier otro programa. También sirven "db.local:5432", ("10.0.0.5", 443) y una lista de servidores. Es la primera opción, y es exacta en Windows y Linux.
  • process="self" ralentiza el proceso de pruebas y cada programa que inició, como el navegador de Playwright. Un proceso que tu prueba inició por su cuenta se pasa como su subprocess.Popen.
  • dst_port, dst_ip y target son los objetivos propios del programa, escritos en su sintaxis, para una API en un puerto o una dirección conocidos. Alcanzan todo lo que coincida: dst_port=443 es cada conexión HTTPS de la máquina, incluidas las de tu editor, y target="python" cada programa con «python» en el nombre.

Los objetivos dados juntos se acotan entre sí: server= con process="self" ralentiza solo las conexiones de esta prueba a ese servidor. En Linux, process= y target alcanzan una conexión nueva hasta unos 0,2 segundos después de abrirse, así que apunta al servidor cuando cuenta la primera petición.

Qué puede hacer una sesión

Cada ajuste es una de las opciones de línea de comandos del programa, escrita con _ en lugar de -. latency=300 añade 300 ms a cada paquete, jitter=100 hace variar ese retardo, loss=5 descarta el 5 % de los paquetes, down y up limitan la velocidad en KB/s, y loss=100 corta el servidor. preset="presets.3g" es un perfil de enlace completo, y seed=42 repite las mismas elecciones al azar en cada ejecución. Un escenario cambia las condiciones a medida que pasan los segundos: scenario="scenarios/cafe-wifi.json". Un paso del escenario puede cambiar cómo se comporta la red, pero no a qué apunta la sesión.

pytest-xdist y límites

  • Una a la vez. Dos sesiones sobre el mismo tráfico se sumarían, así que los workers de pytest-xdist se turnan, cada uno esperando hasta wait segundos (600 si no indicas otro valor). Una segunda sesión en la misma prueba se rechaza al instante.
  • Termina con la prueba. Si el proceso de pruebas muere, el programa lo nota y se detiene al instante. duration (300 segundos si no indicas otro valor) es en todo caso lo máximo que puede durar una sesión.
  • Avisa cuando no hizo nada. Una sesión que no ralentizó nada, porque nada llegó a su objetivo, termina con un BadNetworkWarning. Lo habitual es que la aplicación hable con otra dirección distinta del objetivo, como un contenedor.
  • macOS. El programa funciona en Windows y Linux. En un Mac, ejecuta las pruebas en un contenedor o una máquina virtual Linux x86_64, o en un runner de CI.

El README del paquete en GitHub enumera cada opción y explica cada mensaje.
