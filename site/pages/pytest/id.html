Simulasikan latensi jaringan dan packet loss di pytest

Tanpa mock: paket beannetworktester di PyPI memberi pytest fixture bad_network yang memperlambat jaringan sebenarnya selama tes berlangsung. Latensi, packet loss, batas kecepatan, atau pemutusan total, untuk satu server atau satu proses, sementara aplikasi, browser, dan server Anda benar-benar saling berbicara. Paket ini membawa program Bean Network Tester dan menjalankannya di Windows dan Linux. Paket ini terbit bersama setiap rilis stabil mulai 1.1.0.

Instalasi

pip install beannetworktester

Butuh Windows x64 atau Linux x64 (glibc 2.39 atau lebih baru, seperti Ubuntu 24.04) dan Python 3.10 atau lebih baru.

Mengubah jaringan butuh hak administrator di Windows: buka terminal dengan "Jalankan sebagai administrator". Di Linux butuh root, atau pengguna yang boleh menjalankan sudo tanpa kata sandi, dan saat itu hanya programnya yang berjalan dengan sudo. Runner Windows yang di-host GitHub berjalan dengan hak tinggi dan runner Ubuntu-nya mengizinkan sudo, jadi workflow tidak butuh langkah tambahan.

Tes di jaringan yang lambat

Simpan ini sebagai test_slow.py lalu jalankan pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Tes lulus karena jawaban memang tiba lebih lambat: setiap paket ke server itu dan darinya menunggu 500 ms. Saat tes selesai, jaringan kembali normal. Diukur di Windows dengan latency=200: permintaan ke server dalam tujuan naik dari 4 ms ke 404 ms, karena permintaan dan jawabannya sama-sama menunggu, dan halaman di Chromium dari 61 ms ke 412 ms. Server lokal lain, di luar tujuan, menjawab dalam 11 ms selama itu.

Tidak punya hak akses? bad_network(simulate=True, latency=500) menjalankan program pada lalu lintas buatan dan tidak mengubah apa pun di jaringan. Ini memeriksa bahwa paket terpasang dengan benar, tanpa memperlambat apa pun.

Fixture bad_network

pytest menemukan fixture itu sendiri begitu paket terpasang. bad_network memulai sesi saat Anda memanggilnya dan kembali begitu jaringan sudah lambat. Sesi berhenti saat tes selesai, entah lulus, gagal, atau crash, dan ringkasan program masuk ke user_properties tes, lalu dari sana ke laporan JUnit XML. Untuk mengubah kondisi di tengah tes, hentikan sesi pertama sebelum memulai yang berikutnya:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Di luar pytest, from beannetworktester import bad_network memulai sesi yang sama, dan with bad_network(...) as session: menghentikannya di akhir blok.

Playwright untuk Python

Playwright untuk Python berjalan di atas pytest, jadi fixture-nya sama. Chromium, Firefox, dan WebKit diperlambat dengan cara yang sama, termasuk WebSocket, karena jaringannya sendiri yang lambat, bukan anggapan browser tentangnya:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Apa yang dituju sebuah sesi

Setiap sesi menuju sesuatu, dan hanya lalu lintas itu yang berubah. Sesi tanpa tujuan akan memperlambat setiap koneksi mesin, termasuk milik test runner sendiri, jadi sesi itu tidak dimulai.

  • server="http://localhost:3000" memperlambat setiap koneksi ke alamat dan port itu, dari aplikasi Anda, browser Anda, atau program lain mana pun. "db.local:5432", ("10.0.0.5", 443), dan daftar server juga bisa. Ini pilihan pertama, dan tepat di Windows maupun Linux.
  • process="self" memperlambat proses tes dan setiap program yang dijalankannya, seperti browser Playwright. Proses yang dijalankan sendiri oleh tes Anda diberikan sebagai subprocess.Popen-nya.
  • dst_port, dst_ip, dan target adalah tujuan milik program sendiri, ditulis dalam sintaksnya, untuk API di port atau alamat yang diketahui. Semuanya menjangkau apa pun yang cocok: dst_port=443 adalah setiap koneksi HTTPS mesin, termasuk milik editor Anda, dan target="python" setiap program dengan "python" di namanya.

Tujuan yang diberikan bersama saling mempersempit: server= dengan process="self" hanya memperlambat koneksi tes ini ke server itu. Di Linux, process= dan target menjangkau koneksi baru hingga sekitar 0,2 detik setelah koneksi dibuka, jadi tujukan ke server bila permintaan pertama penting.

Apa yang bisa dilakukan sebuah sesi

Setiap pengaturan adalah salah satu opsi baris perintah program, ditulis dengan _ sebagai ganti -. latency=300 menambah 300 ms ke setiap paket, jitter=100 membuat jeda itu bervariasi, loss=5 membuang 5 % paket, down dan up membatasi kecepatan dalam KB/s, dan loss=100 memutus server. preset="presets.3g" adalah profil koneksi utuh, dan seed=42 membuat pilihan acak yang sama di setiap jalannya tes. Sebuah skenario mengubah kondisi seiring detik berjalan: scenario="scenarios/cafe-wifi.json". Langkah skenario boleh mengubah perilaku jaringan, tetapi tidak mengubah apa yang dituju sesi.

pytest-xdist dan batasan

  • Satu per satu. Dua sesi pada lalu lintas yang sama akan saling menambah, jadi worker pytest-xdist bergantian, masing-masing menunggu hingga wait detik (600 kecuali Anda memberi nilai lain). Sesi kedua dalam tes yang sama langsung ditolak.
  • Ia berakhir bersama tes. Jika proses tes mati, program melihatnya dan langsung berhenti. duration (300 detik kecuali Anda memberi nilai lain) adalah waktu terlama sebuah sesi boleh berjalan dalam keadaan apa pun.
  • Ia memberi tahu saat tidak melakukan apa pun. Sesi yang tidak memperlambat apa pun, karena tidak ada yang sampai ke tujuannya, berakhir dengan BadNetworkWarning. Biasanya aplikasi berbicara dengan alamat lain selain tujuan, misalnya sebuah kontainer.
  • macOS. Programnya berjalan di Windows dan Linux. Di Mac, jalankan tes di kontainer atau mesin virtual Linux x86_64, atau di runner CI.
