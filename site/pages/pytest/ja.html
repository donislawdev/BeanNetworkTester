pytest でネットワーク遅延とパケットロスを再現

モックは使いません。PyPI の beannetworktester パッケージは pytest に bad_network フィクスチャを追加し、テストの間だけ本物のネットワークを遅くします。アプリ、ブラウザー、サーバーが実際に通信している間に、1 つのサーバーや 1 つのプロセスに対して、遅延、パケットロス、速度制限、完全な切断を加えます。パッケージには Bean Network Tester のプログラムが入っており、Windows と Linux で実行します。1.1.0 以降の安定版リリースごとに公開されます。

インストール

pip install beannetworktester

Windows x64 または Linux x64（glibc 2.39 以降、たとえば Ubuntu 24.04）と Python 3.10 以降が必要です。

ネットワークを変えるには、Windows では管理者権限が必要です。ターミナルを「管理者として実行」で開いてください。Linux では root か、パスワードなしで sudo を実行できるユーザーが必要で、その場合 sudo で動くのはプログラムだけです。GitHub がホストする Windows ランナーは昇格した権限で動き、Ubuntu ランナーは sudo を許可しているので、ワークフローに追加の手順は要りません。

遅いネットワークでのテスト

これを test_slow.py として保存し、pytest を実行します。

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

テストが通るのは、応答が本当に遅れて届くからです。そのサーバーとの間のすべてのパケットが 500 ms 待ちます。テストが終わるとネットワークは元に戻ります。Windows で latency=200 にして測定すると、対象のサーバーへのリクエストは 4 ms から 404 ms になり（リクエストと応答の両方が待つため）、Chromium のページは 61 ms から 412 ms になりました。対象外の別のローカルサーバーは、その間 11 ms で応答していました。

権限がすぐに使えない場合は、bad_network(simulate=True, latency=500) を使います。作り物の通信でプログラムを動かし、ネットワークには何も変更を加えません。パッケージが正しく入っているかの確認用で、何も遅くしません。

bad_network フィクスチャ

パッケージをインストールすれば、pytest がフィクスチャを自動で見つけます。bad_network を呼ぶとセッションが始まり、ネットワークが遅くなった時点で戻ります。セッションはテストが成功しても失敗してもクラッシュしても、テストの終わりに止まり、プログラムのサマリーはテストの user_properties に入り、そこから JUnit XML レポートに入ります。途中で条件を変えるには、次のセッションを始める前に最初のセッションを止めます。

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

pytest の外では、from beannetworktester import bad_network で同じセッションを始められ、with bad_network(...) as session: はブロックの終わりで止めます。

Playwright for Python

Playwright for Python は pytest の上で動くので、フィクスチャは同じです。Chromium、Firefox、WebKit は WebSocket も含めて同じように遅くなります。遅いのはブラウザーの想定ではなく、ネットワークそのものだからです。

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

セッションの対象

どのセッションも何かを対象にし、変わるのはその通信だけです。対象のないセッションはマシンのすべての接続を、テストランナー自身の接続まで遅くしてしまうため、開始しません。

  • server="http://localhost:3000" は、そのアドレスとポートへのすべての接続を遅くします。アプリからでも、ブラウザーからでも、ほかのどのプログラムからでもです。"db.local:5432"、("10.0.0.5", 443)、サーバーのリストも使えます。これが第一の選択肢で、Windows でも Linux でも正確です。
  • process="self" は、テストプロセスと、それが起動したすべてのプログラム（Playwright のブラウザーなど）を遅くします。テスト自身が起動したプロセスは、その subprocess.Popen を渡します。
  • dst_port、dst_ip、target はプログラム自身の対象で、その構文で書きます。既知のポートやアドレスにある API 向けです。一致するものすべてに届きます。dst_port=443 はエディターの通信も含むマシンのすべての HTTPS 接続、target="python" は名前に「python」を含むすべてのプログラムです。

一緒に指定した対象は互いを絞り込みます。server= と process="self" を合わせると、このテストからそのサーバーへの接続だけが遅くなります。Linux では、process= と target が新しい接続に効くのは、開いてから最大で約 0.2 秒後です。最初のリクエストが大事なときはサーバーを対象にしてください。

セッションでできること

各設定はプログラムのコマンドラインオプションのひとつで、- の代わりに _ で書きます。latency=300 はすべてのパケットに 300 ms を加え、jitter=100 はその遅延を揺らし、loss=5 はパケットの 5 % を落とし、down と up は速度を KB/s で制限し、loss=100 はサーバーを切り離します。preset="presets.3g" は回線プロファイル一式で、seed=42 は毎回同じランダムな選択をします。シナリオは秒ごとに条件を変えます：scenario="scenarios/cafe-wifi.json"。シナリオのステップはネットワークの振る舞いを変えられますが、セッションの対象は変えられません。

pytest-xdist と上限

  • 一度にひとつ。同じ通信に 2 つのセッションをかけると効果が重なるため、pytest-xdist のワーカーは順番待ちをし、それぞれ最大 wait 秒（指定しなければ 600）待ちます。同じテスト内の 2 つ目のセッションはすぐに拒否されます。
  • テストとともに終わります。テストプロセスが落ちると、プログラムはそれに気づいてすぐ止まります。duration（指定しなければ 300 秒）は、どんな場合でもセッションが動ける最長時間です。
  • 何もしなかったときは知らせます。対象に何も届かず、何も遅くしなかったセッションは BadNetworkWarning で終わります。よくある原因は、アプリが対象とは別のアドレス、たとえばコンテナと通信していることです。
  • macOS。プログラムは Windows と Linux で動きます。Mac では、Linux x86_64 のコンテナや仮想マシン、または CI ランナーでテストを実行してください。

パッケージの README（GitHub）に、すべてのオプションと各メッセージの意味が載っています。
