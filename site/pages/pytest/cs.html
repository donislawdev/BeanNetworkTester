Simulace latence sítě a ztráty paketů v pytest

Nic se nepředstírá: balíček beannetworktester z PyPI dává pytestu fixture bad_network, která zpomalí skutečnou síť po dobu testu. Latence, ztráta paketů, omezení rychlosti nebo úplný výpadek, pro jeden server nebo jeden proces, zatímco vaše aplikace, prohlížeč a server spolu opravdu mluví. Balíček obsahuje program Bean Network Tester a spouští ho ve Windows i v Linuxu. Vychází s každou stabilní verzí od 1.1.0.

Instalace

pip install beannetworktester

Potřebuje Windows x64 nebo Linux x64 (glibc 2.39 nebo novější, například Ubuntu 24.04) a Python 3.10 nebo novější.

Změna sítě potřebuje ve Windows práva správce: otevřete terminál přes „Spustit jako správce“. V Linuxu potřebuje root nebo uživatele, který smí spouštět sudo bez hesla, a pak pod sudo běží jen program. Hostované runnery GitHubu s Windows běží se zvýšenými právy a ty s Ubuntu povolují sudo, takže workflow nepotřebuje žádný krok navíc.

Test na pomalé síti

Uložte to jako test_slow.py a spusťte pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Test projde, protože odpověď opravdu přijde později: každý paket k tomu serveru a od něj čeká 500 ms. Po skončení testu je síť zase normální. Změřeno ve Windows s latency=200: požadavek na server v cíli trval místo 4 ms 404 ms, protože čeká požadavek i odpověď, a stránka v Chromiu místo 61 ms 412 ms. Jiný místní server, mimo cíl, mezitím odpovídal za 11 ms.

Nemáte práva po ruce? bad_network(simulate=True, latency=500) spustí program na vymyšleném provozu a na síti nic nezmění. Ověří, že je balíček správně nainstalovaný, a nic nezpomalí.

Fixture bad_network

pytest fixture najde sám, jakmile je balíček nainstalovaný. bad_network spustí sezení, když ho zavoláte, a vrátí se, jakmile je síť pomalá. Sezení skončí s koncem testu, ať prošel, selhal, nebo spadl, a souhrn programu jde do user_properties testu a odtud do zprávy JUnit XML. Chcete-li uprostřed testu změnit podmínky, zastavte první sezení dřív, než spustíte další:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Mimo pytest spustí stejné sezení from beannetworktester import bad_network a with bad_network(...) as session: ho zastaví na konci bloku.

Playwright pro Python

Playwright pro Python běží na pytestu, takže fixture je stejná. Chromium, Firefox i WebKit se zpomalí stejně, včetně WebSocketů, protože pomalá je sama síť, ne představa prohlížeče o ní:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Na co sezení míří

Každé sezení na něco míří a mění se jen tento provoz. Sezení bez cíle by zpomalilo každé spojení počítače, i spojení samotného spouštěče testů, a proto se vůbec nespustí.

  • server="http://localhost:3000" zpomalí každé spojení s touto adresou a portem, z vaší aplikace, prohlížeče nebo jakéhokoli jiného programu. Funguje i "db.local:5432", ("10.0.0.5", 443) a seznam serverů. To je první volba a ve Windows i v Linuxu je přesná.
  • process="self" zpomalí testovací proces a každý program, který spustil, například prohlížeč Playwrightu. Proces, který spustil sám test, předáte jako jeho subprocess.Popen.
  • dst_port, dst_ip a target jsou vlastní cíle programu, zapsané v jeho syntaxi, pro API na známém portu nebo adrese. Zasáhnou všechno, co odpovídá: dst_port=443 je každé spojení HTTPS počítače, i spojení vašeho editoru, a target="python" každý program s „python“ v názvu.

Cíle zadané spolu se navzájem zužují: server= s process="self" zpomalí jen spojení tohoto testu s tím serverem. V Linuxu process= a target zasáhnou nové spojení až asi 0,2 sekundy po jeho otevření, takže miřte na server, když záleží na prvním požadavku.

Co sezení umí

Každé nastavení je jedna z voleb příkazového řádku programu, zapsaná s _ místo -. latency=300 přidá každému paketu 300 ms, jitter=100 tuto prodlevu mění, loss=5 zahodí 5 % paketů, down a up omezí rychlost v KB/s a loss=100 server odřízne. preset="presets.3g" je celý profil linky a seed=42 udělá při každém běhu stejné náhodné volby. Scénář mění podmínky, jak běží sekundy: scenario="scenarios/cafe-wifi.json". Krok scénáře smí změnit, jak se síť chová, ale ne to, na co sezení míří.

pytest-xdist a meze

  • Jedno po druhém. Dvě sezení na stejném provozu by se sčítala, takže workery pytest-xdist se střídají a každý čeká až wait sekund (600, pokud nezadáte jinak). Druhé sezení ve stejném testu je hned odmítnuto.
  • Končí s testem. Když testovací proces zanikne, program to pozná a hned se zastaví. duration (300 sekund, pokud nezadáte jinak) je v každém případě nejdelší doba sezení.
  • Řekne, když nic neudělalo. Sezení, které nic nezpomalilo, protože do jeho cíle nic nedorazilo, skončí varováním BadNetworkWarning. Obvykle aplikace mluví s jinou adresou, než je cíl, například s kontejnerem.
  • macOS. Program běží ve Windows a v Linuxu. Na Macu spusťte testy v kontejneru nebo virtuálním počítači s Linuxem x86_64, nebo na runneru CI.
