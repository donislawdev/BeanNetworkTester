محاكاة تأخير الشبكة وفقدان الحزم في pytest

لا شيء مزيف: حزمة beannetworktester على PyPI تمنح pytest أداة fixture باسم bad_network تبطئ الشبكة الحقيقية طوال مدة الاختبار. تأخير، أو فقدان حزم، أو حد للسرعة، أو انقطاع كامل، لخادم واحد أو عملية واحدة، بينما يتحدث تطبيقك ومتصفحك وخادمك بعضهم إلى بعض فعلًا. تحمل الحزمة برنامج Bean Network Tester نفسه وتشغّله على Windows وLinux. تُنشر الحزمة مع كل إصدار مستقر بدءًا من 1.1.0.

التثبيت

pip install beannetworktester

تحتاج إلى Windows x64 أو Linux x64 (glibc 2.39 أو أحدث، مثل Ubuntu 24.04) وإلى Python 3.10 أو أحدث.

تغيير الشبكة يحتاج إلى صلاحيات المسؤول على Windows: افتح الطرفية عبر "تشغيل كمسؤول". وعلى Linux يحتاج إلى root، أو إلى مستخدم يستطيع تشغيل sudo دون كلمة مرور، وعندها لا يعمل تحت sudo إلا البرنامج. مشغّلات Windows التي يستضيفها GitHub تعمل بصلاحيات مرتفعة، ومشغّلات Ubuntu لديه تسمح بـ sudo، لذا لا يحتاج سير العمل إلى أي خطوة إضافية.

اختبار على شبكة بطيئة

احفظ هذا باسم test_slow.py وشغّل pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

ينجح الاختبار لأن الرد يصل فعلًا متأخرًا: كل حزمة ذاهبة إلى ذلك الخادم أو آتية منه تنتظر 500 ms. عند انتهاء الاختبار تعود الشبكة إلى طبيعتها. القياس على Windows مع latency=200: ارتفع طلب إلى الخادم المستهدف من 4 ms إلى 404 ms، لأن الطلب والرد ينتظران كلاهما، وارتفعت صفحة في Chromium من 61 ms إلى 412 ms. وفي الأثناء كان خادم محلي آخر خارج الهدف يرد في 11 ms.

لا تملك الصلاحيات الآن؟ bad_network(simulate=True, latency=500) يشغّل البرنامج على حركة مختلقة ولا يغيّر شيئًا في الشبكة. إنه يتحقق من أن الحزمة مثبتة كما يجب، ولا يبطئ شيئًا.

الـ fixture المسمى bad_network

يجد pytest الـ fixture بنفسه بمجرد تثبيت الحزمة. يبدأ bad_network جلسة عند استدعائه، ويعود حالما تصبح الشبكة بطيئة. تتوقف الجلسة عند انتهاء الاختبار، سواء نجح أو فشل أو تعطّل، ويذهب ملخص البرنامج إلى user_properties الخاصة بالاختبار، ومنها إلى تقرير JUnit XML. لتغيير الظروف في منتصف الاختبار، أوقف الجلسة الأولى قبل أن تبدأ التالية:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

خارج pytest، يبدأ from beannetworktester import bad_network الجلسة نفسها، ويوقفها with bad_network(...) as session: عند نهاية الكتلة.

Playwright لـ Python

يعمل Playwright لـ Python فوق pytest، لذا فالـ fixture هو نفسه. يتباطأ Chromium وFirefox وWebKit بالطريقة نفسها، بما في ذلك WebSocket، لأن الشبكة نفسها هي البطيئة، لا تصوّر المتصفح عنها:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

ما الذي تستهدفه الجلسة

كل جلسة تستهدف شيئًا ما، ولا يتغير إلا تلك الحركة. الجلسة التي بلا هدف كانت ستبطئ كل اتصال في الجهاز، بما فيها اتصالات مشغّل الاختبارات نفسه، لذلك لا تبدأ أصلًا.

  • server="http://localhost:3000" يبطئ كل اتصال بهذا العنوان وهذا المنفذ، من تطبيقك أو متصفحك أو أي برنامج آخر. ويصلح أيضًا "db.local:5432" و("10.0.0.5", 443) وقائمة من الخوادم. هذا هو الخيار الأول، وهو دقيق على Windows وLinux.
  • process="self" يبطئ عملية الاختبار وكل برنامج بدأته، مثل متصفح Playwright. أما العملية التي بدأها اختبارك بنفسه فتُمرَّر على هيئة subprocess.Popen الخاص بها.
  • dst_port وdst_ip وtarget هي أهداف البرنامج نفسه، تُكتب بصيغته، وهي لواجهة API على منفذ أو عنوان معروف. تصل إلى كل ما يطابقها: dst_port=443 هو كل اتصال HTTPS في الجهاز، بما فيها اتصالات المحرر لديك، وtarget="python" هو كل برنامج في اسمه "python".

الأهداف المعطاة معًا يضيّق بعضها بعضًا: server= مع process="self" يبطئ فقط اتصالات هذا الاختبار بذلك الخادم. على Linux لا يبدأ process= وtarget بالتأثير في اتصال جديد إلا بعد فتحه بنحو 0.2 ثانية في أقصى حد، لذا استهدف الخادم حين يهم الطلب الأول.

ما الذي تستطيعه الجلسة

كل إعداد هو أحد خيارات سطر الأوامر في البرنامج، ويُكتب بـ _ بدلًا من -. latency=300 يضيف 300 ms إلى كل حزمة، وjitter=100 يجعل هذا التأخير متفاوتًا، وloss=5 يُسقط 5 % من الحزم، وdown وup يحدّان السرعة بالكيلوبايت في الثانية، وloss=100 يقطع الخادم. preset="presets.3g" ملف تعريف كامل للاتصال، وseed=42 يعيد الاختيارات العشوائية نفسها في كل تشغيل. أما السيناريو فيغيّر الظروف مع مرور الثواني: scenario="scenarios/cafe-wifi.json". يمكن لخطوة في السيناريو أن تغيّر سلوك الشبكة، لكن لا يمكنها تغيير ما تستهدفه الجلسة.

pytest-xdist والحدود

  • واحدة في كل مرة. جلستان على الحركة نفسها ستتراكمان، لذلك ينتظر عمّال pytest-xdist دورهم، وينتظر كل منهم حتى wait ثانية (600 ما لم تحدد قيمة أخرى). وتُرفض الجلسة الثانية في الاختبار نفسه فورًا.
  • تنتهي مع الاختبار. إذا ماتت عملية الاختبار، يلاحظ البرنامج ذلك ويتوقف فورًا. وduration (300 ثانية ما لم تحدد قيمة أخرى) هو أطول ما يمكن أن تستمر فيه الجلسة في كل الأحوال.
  • تخبرك حين لا تفعل شيئًا. الجلسة التي لم تبطئ شيئًا، لأن شيئًا لم يصل إلى هدفها، تنتهي بتحذير BadNetworkWarning. السبب المعتاد أن التطبيق يتحدث إلى عنوان غير الهدف، مثل حاوية.
  • macOS. يعمل البرنامج على Windows وLinux. على جهاز Mac، شغّل الاختبارات في حاوية أو آلة افتراضية بنظام Linux x86_64، أو على مشغّل CI.
