Simulează latența rețelei și pierderi de pachete în pytest

Nimic simulat în cod: pachetul beannetworktester de pe PyPI îi dă lui pytest un fixture bad_network care încetinește rețeaua reală cât durează un test. Latență, pierderi de pachete, o limită de viteză sau o întrerupere totală, pentru un server sau un proces, în timp ce aplicația, browserul și serverul tău chiar vorbesc între ele. Pachetul conține programul Bean Network Tester și îl rulează pe Windows și Linux. Apare cu fiecare versiune stabilă începând cu 1.1.0.

Instalare

pip install beannetworktester

Are nevoie de Windows x64 sau Linux x64 (glibc 2.39 sau mai nou, de exemplu Ubuntu 24.04) și Python 3.10 sau mai nou.

Schimbarea rețelei cere drepturi de administrator pe Windows: deschide terminalul cu „Executare ca administrator”. Pe Linux cere root sau un utilizator care poate rula sudo fără parolă, și atunci doar programul rulează cu sudo. Runnerele Windows găzduite de GitHub rulează cu drepturi ridicate, iar runnerele Ubuntu permit sudo, deci un workflow nu are nevoie de niciun pas în plus.

Un test pe o rețea lentă

Salvează asta ca test_slow.py și rulează pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Testul trece pentru că răspunsul chiar ajunge mai târziu: fiecare pachet spre acel server și dinspre el așteaptă 500 ms. Când testul se termină, rețeaua revine la normal. Măsurat pe Windows cu latency=200: o cerere către serverul din țintă a crescut de la 4 ms la 404 ms, pentru că așteaptă și cererea, și răspunsul, iar o pagină în Chromium de la 61 ms la 412 ms. Un alt server local, în afara țintei, răspundea între timp în 11 ms.

Nu ai drepturile la îndemână? bad_network(simulate=True, latency=500) rulează programul pe trafic inventat și nu schimbă nimic în rețea. Verifică faptul că pachetul e instalat corect și nu încetinește nimic.

Fixture-ul bad_network

pytest găsește singur fixture-ul după ce pachetul e instalat. bad_network pornește o sesiune când îl apelezi și revine imediat ce rețeaua e lentă. Sesiunea se oprește când testul se termină, fie că a trecut, a picat sau s-a prăbușit, iar rezumatul programului ajunge în user_properties ale testului și de acolo într-un raport JUnit XML. Ca să schimbi condițiile la jumătatea testului, oprește prima sesiune înainte s-o pornești pe următoarea:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

În afara pytest, from beannetworktester import bad_network pornește aceeași sesiune, iar with bad_network(...) as session: o oprește la finalul blocului.

Playwright pentru Python

Playwright pentru Python rulează pe pytest, deci fixture-ul e același. Chromium, Firefox și WebKit sunt încetinite la fel, inclusiv WebSocket-urile, pentru că rețeaua însăși e lentă, nu ideea pe care și-o face browserul despre ea:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Spre ce țintește o sesiune

Fiecare sesiune țintește ceva și doar acel trafic se schimbă. O sesiune fără țintă ar încetini fiecare conexiune a mașinii, inclusiv pe cele ale rulatorului de teste, așa că nu pornește.

  • server="http://localhost:3000" încetinește fiecare conexiune către acea adresă și acel port, din aplicația ta, din browser sau din orice alt program. Merg și "db.local:5432", ("10.0.0.5", 443) și o listă de servere. Aceasta e prima alegere și e exactă pe Windows și Linux.
  • process="self" încetinește procesul de teste și fiecare program pornit de el, de exemplu browserul Playwright. Un proces pornit chiar de test se dă ca subprocess.Popen-ul lui.
  • dst_port, dst_ip și target sunt țintele proprii ale programului, scrise în sintaxa lui, pentru un API pe un port sau o adresă cunoscute. Ele ajung la tot ce se potrivește: dst_port=443 înseamnă fiecare conexiune HTTPS a mașinii, inclusiv cele ale editorului tău, iar target="python" fiecare program cu „python” în nume.

Țintele date împreună se restrâng una pe alta: server= cu process="self" încetinește doar conexiunile acestui test către acel server. Pe Linux, process= și target ajung la o conexiune nouă până la circa 0,2 secunde după deschiderea ei, așa că țintește serverul când contează prima cerere.

Ce poate face o sesiune

Fiecare setare este una dintre opțiunile din linia de comandă ale programului, scrisă cu _ în loc de -. latency=300 adaugă 300 ms fiecărui pachet, jitter=100 face să varieze acea întârziere, loss=5 aruncă 5 % din pachete, down și up limitează viteza în KB/s, iar loss=100 taie serverul. preset="presets.3g" e un profil de legătură întreg, iar seed=42 face aceleași alegeri aleatorii la fiecare rulare. Un scenariu schimbă condițiile pe măsură ce trec secundele: scenario="scenarios/cafe-wifi.json". Un pas din scenariu poate schimba cum se comportă rețeaua, dar nu și spre ce țintește sesiunea.

pytest-xdist și limite

  • Câte una. Două sesiuni pe același trafic s-ar aduna, așa că workerii pytest-xdist își așteaptă rândul, fiecare până la wait secunde (600 dacă nu dai altă valoare). O a doua sesiune în același test e refuzată imediat.
  • Se termină odată cu testul. Dacă procesul de teste moare, programul observă și se oprește imediat. duration (300 de secunde dacă nu dai altă valoare) e, în orice caz, cel mai mult cât poate rula o sesiune.
  • Spune când n-a făcut nimic. O sesiune care n-a încetinit nimic, pentru că nimic n-a ajuns la ținta ei, se încheie cu un BadNetworkWarning. De obicei aplicația vorbește cu altă adresă decât ținta, de exemplu un container.
  • macOS. Programul rulează pe Windows și Linux. Pe un Mac, rulează testele într-un container sau o mașină virtuală Linux x86_64 ori pe un runner de CI.

README-ul pachetului de pe GitHub enumeră fiecare opțiune și explică fiecare mesaj.
