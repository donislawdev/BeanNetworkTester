Задержка сети и потеря пакетов в pytest

Никаких моков: пакет beannetworktester из PyPI даёт pytest фикстуру bad_network, которая замедляет настоящую сеть на время теста. Задержка, потеря пакетов, ограничение скорости или полный обрыв, для одного сервера или одного процесса, пока ваше приложение, браузер и сервер действительно говорят друг с другом. Пакет несёт программу Bean Network Tester и запускает её в Windows и Linux. Он выходит с каждым стабильным выпуском начиная с 1.1.0.

Установка

pip install beannetworktester

Нужны Windows x64 или Linux x64 (glibc 2.39 или новее, например Ubuntu 24.04) и Python 3.10 или новее.

Чтобы менять сеть, в Windows нужны права администратора: откройте терминал через «Запуск от имени администратора». В Linux нужен root или пользователь, которому разрешён sudo без пароля, и тогда под sudo работает только программа. Размещённые раннеры GitHub с Windows работают с повышенными правами, а раннеры с Ubuntu разрешают sudo, так что workflow не нужен дополнительный шаг.

Тест на медленной сети

Сохраните это как test_slow.py и запустите pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Тест проходит, потому что ответ действительно приходит позже: каждый пакет к этому серверу и от него ждёт 500 мс. Когда тест заканчивается, сеть снова работает как обычно. Измерено в Windows с latency=200: запрос к серверу в цели вырос с 4 мс до 404 мс, потому что ждут и запрос, и ответ, а страница в Chromium с 61 мс до 412 мс. Другой локальный сервер, вне цели, отвечал в это время за 11 мс.

Прав под рукой нет? bad_network(simulate=True, latency=500) запускает программу на выдуманном трафике и ничего не меняет в сети. Это проверяет, что пакет установлен правильно, и ничего не замедляет.

Фикстура bad_network

pytest сам находит фикстуру, как только пакет установлен. bad_network начинает сессию, когда вы её вызываете, и возвращается, как только сеть стала медленной. Сессия останавливается вместе с концом теста, прошёл он, упал или аварийно завершился, а сводка программы попадает в user_properties теста и оттуда в отчёт JUnit XML. Чтобы поменять условия посреди теста, остановите первую сессию, прежде чем начинать следующую:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Вне pytest ту же сессию начинает from beannetworktester import bad_network, а with bad_network(...) as session: останавливает её в конце блока.

Playwright для Python

Playwright для Python работает на pytest, поэтому фикстура та же. Chromium, Firefox и WebKit замедляются одинаково, вместе с WebSocket, потому что медленная сама сеть, а не представление браузера о ней:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

На что нацелена сессия

Каждая сессия на что-то нацелена, и меняется только этот трафик. Сессия без цели замедлила бы каждое соединение машины, в том числе соединения самого запускателя тестов, поэтому она не запускается.

  • server="http://localhost:3000" замедляет каждое соединение с этим адресом и портом, из вашего приложения, браузера или любой другой программы. Подходят и "db.local:5432", ("10.0.0.5", 443), и список серверов. Это первый выбор, и он точен в Windows и Linux.
  • process="self" замедляет тестовый процесс и каждую программу, которую он запустил, например браузер Playwright. Процесс, который запустил сам тест, передаётся как его subprocess.Popen.
  • dst_port, dst_ip и target это собственные цели программы, записанные в её синтаксисе, для API на известном порту или адресе. Они достают всё, что подходит: dst_port=443 это каждое HTTPS-соединение машины, в том числе соединения вашего редактора, а target="python" каждая программа с «python» в имени.

Цели, заданные вместе, сужают друг друга: server= с process="self" замедляет только соединения этого теста с этим сервером. В Linux process= и target начинают действовать на новое соединение с опозданием примерно до 0,2 секунды после его открытия, поэтому цельтесь в сервер, когда важен первый запрос.

Что умеет сессия

Каждая настройка это один из параметров командной строки программы, записанный через _ вместо -. latency=300 добавляет 300 мс каждому пакету, jitter=100 делает эту задержку переменной, loss=5 теряет 5 % пакетов, down и up ограничивают скорость в КБ/с, а loss=100 отрезает сервер. preset="presets.3g" это целый профиль канала, а seed=42 даёт одни и те же случайные решения при каждом запуске. Сценарий меняет условия по мере того, как идут секунды: scenario="scenarios/cafe-wifi.json". Шаг сценария может изменить поведение сети, но не то, на что нацелена сессия.

pytest-xdist и ограничения

  • По одной. Две сессии на одном трафике сложились бы, поэтому воркеры pytest-xdist ждут своей очереди, каждый до wait секунд (600, если не задать другое значение). Вторая сессия в том же тесте сразу отклоняется.
  • Она заканчивается вместе с тестом. Если тестовый процесс умирает, программа это видит и сразу останавливается. duration (300 секунд, если не задать другое значение) в любом случае самое долгое время работы сессии.
  • Она говорит, когда ничего не сделала. Сессия, которая ничего не замедлила, потому что до её цели ничего не дошло, завершается предупреждением BadNetworkWarning. Обычно это значит, что приложение говорит с другим адресом, а не с целью, например с контейнером.
  • macOS. Программа работает в Windows и Linux. На Mac запускайте тесты в контейнере или виртуальной машине с Linux x86_64 либо на раннере CI.
