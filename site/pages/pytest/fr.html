Simuler la latence réseau et les pertes de paquets dans pytest

Rien de simulé dans le code : le paquet beannetworktester sur PyPI donne à pytest une fixture bad_network qui ralentit le vrai réseau le temps d'un test. Latence, perte de paquets, limite de débit ou coupure complète, pour un serveur ou un processus, pendant que votre application, votre navigateur et votre serveur se parlent vraiment. Le paquet contient le programme de Bean Network Tester et le lance sous Windows et Linux. Il sort avec chaque version stable à partir de la 1.1.0.

Installation

pip install beannetworktester

Il faut Windows x64 ou Linux x64 (glibc 2.39 ou plus récente, comme Ubuntu 24.04) et Python 3.10 ou plus récent.

Modifier le réseau demande les droits d'administrateur sous Windows : ouvrez le terminal avec « Exécuter en tant qu'administrateur ». Sous Linux, il faut root, ou un utilisateur qui peut lancer sudo sans mot de passe, et seul le programme tourne alors sous sudo. Les runners Windows hébergés par GitHub tournent avec des droits élevés et ses runners Ubuntu autorisent sudo, donc un workflow n'a besoin d'aucune étape de plus.

Un test sur un réseau lent

Enregistrez ceci sous test_slow.py et lancez pytest :

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Le test passe parce que la réponse arrive vraiment plus tard : chaque paquet vers ce serveur et depuis lui attend 500 ms. À la fin du test, le réseau redevient normal. Mesuré sous Windows avec latency=200 : une requête vers le serveur visé est passée de 4 ms à 404 ms, parce que la requête et la réponse attendent toutes les deux, et une page dans Chromium de 61 ms à 412 ms. Un autre serveur local, hors de la cible, répondait pendant ce temps en 11 ms.

Pas de droits sous la main ? bad_network(simulate=True, latency=500) lance le programme sur un trafic inventé et ne change rien au réseau. Cela vérifie que le paquet est bien installé, sans rien ralentir.

La fixture bad_network

pytest trouve la fixture tout seul une fois le paquet installé. bad_network démarre une session quand vous l'appelez et rend la main une fois le réseau ralenti. La session s'arrête à la fin du test, qu'il ait réussi, échoué ou planté, et le résumé du programme va dans les user_properties du test, puis de là dans un rapport JUnit XML. Pour changer les conditions en cours de test, arrêtez la première session avant de lancer la suivante :

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Hors de pytest, from beannetworktester import bad_network démarre la même session, et with bad_network(...) as session: l'arrête à la fin du bloc.

Playwright pour Python

Playwright pour Python tourne sur pytest, donc la fixture est la même. Chromium, Firefox et WebKit sont ralentis de la même façon, WebSockets compris, parce que c'est le réseau lui-même qui est lent, pas l'idée que s'en fait le navigateur :

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Ce que vise une session

Chaque session vise quelque chose, et seul ce trafic change. Une session sans cible ralentirait toutes les connexions de la machine, y compris celles du lanceur de tests, donc elle ne démarre pas.

  • server="http://localhost:3000" ralentit chaque connexion vers cette adresse et ce port, depuis votre application, votre navigateur ou tout autre programme. "db.local:5432", ("10.0.0.5", 443) et une liste de serveurs marchent aussi. C'est le premier choix, et il est exact sous Windows et Linux.
  • process="self" ralentit le processus de test et chaque programme qu'il a lancé, comme le navigateur de Playwright. Un processus que votre test a lancé lui-même se donne sous la forme de son subprocess.Popen.
  • dst_port, dst_ip et target sont les cibles propres du programme, écrites dans sa syntaxe, pour une API sur un port ou une adresse connus. Elles atteignent tout ce qui correspond : dst_port=443 est chaque connexion HTTPS de la machine, y compris celles de votre éditeur, et target="python" chaque programme dont le nom contient « python ».

Des cibles données ensemble se restreignent l'une l'autre : server= avec process="self" ne ralentit que les connexions de ce test vers ce serveur. Sous Linux, process= et target atteignent une nouvelle connexion jusqu'à environ 0,2 seconde après son ouverture, donc visez le serveur quand la première requête compte.

Ce que peut faire une session

Chaque réglage est une des options en ligne de commande du programme, écrite avec _ au lieu de -. latency=300 ajoute 300 ms à chaque paquet, jitter=100 fait varier ce délai, loss=5 perd 5 % des paquets, down et up limitent le débit en Ko/s, et loss=100 coupe le serveur. preset="presets.3g" est un profil de liaison complet, et seed=42 refait les mêmes tirages à chaque exécution. Un scénario change les conditions au fil des secondes : scenario="scenarios/cafe-wifi.json". Une étape du scénario peut changer le comportement du réseau, mais pas ce que vise la session.

pytest-xdist et limites

  • Une à la fois. Deux sessions sur le même trafic s'additionneraient, donc les workers de pytest-xdist passent chacun leur tour, en attendant jusqu'à wait secondes (600 si vous n'en donnez pas d'autre). Une deuxième session dans le même test est refusée tout de suite.
  • Elle finit avec le test. Si le processus de test meurt, le programme le voit et s'arrête tout de suite. duration (300 secondes si vous n'en donnez pas d'autre) est dans tous les cas la durée maximale d'une session.
  • Elle dit quand elle n'a rien fait. Une session qui n'a rien ralenti, parce que rien n'a atteint sa cible, se termine par un BadNetworkWarning. Le plus souvent, l'application parle à une autre adresse que la cible, comme un conteneur.
  • macOS. Le programme tourne sous Windows et Linux. Sur un Mac, lancez les tests dans un conteneur ou une machine virtuelle Linux x86_64, ou sur un runner de CI.

Le README du paquet sur GitHub liste chaque option et explique chaque message.
