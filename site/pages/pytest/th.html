จำลองความหน่วงเครือข่ายและแพ็กเก็ตสูญหายใน pytest

ไม่มีการจำลองในโค้ด: แพ็กเกจ beannetworktester บน PyPI มอบ fixture ชื่อ bad_network ให้ pytest ซึ่งทำให้เครือข่ายจริงช้าลงตลอดการทดสอบ ความหน่วง แพ็กเก็ตสูญหาย การจำกัดความเร็ว หรือการขาดการเชื่อมต่อทั้งหมด สำหรับเซิร์ฟเวอร์เดียวหรือโปรเซสเดียว ขณะที่แอป เบราว์เซอร์ และเซิร์ฟเวอร์ของคุณคุยกันจริง แพ็กเกจนี้มีโปรแกรมของ Bean Network Tester อยู่ในตัว และรันบน Windows และ Linux แพ็กเกจนี้เผยแพร่พร้อมทุกรุ่นเสถียรตั้งแต่ 1.1.0 เป็นต้นไป

ติดตั้ง

pip install beannetworktester

ต้องใช้ Windows x64 หรือ Linux x64 (glibc 2.39 ขึ้นไป เช่น Ubuntu 24.04) และ Python 3.10 ขึ้นไป

การเปลี่ยนเครือข่ายบน Windows ต้องใช้สิทธิ์ผู้ดูแลระบบ: เปิดเทอร์มินัลด้วย "เรียกใช้ในฐานะผู้ดูแลระบบ" บน Linux ต้องใช้ root หรือผู้ใช้ที่รัน sudo ได้โดยไม่ต้องใส่รหัสผ่าน และเมื่อนั้นจะมีเพียงโปรแกรมที่รันภายใต้ sudo รันเนอร์ Windows ที่ GitHub โฮสต์ทำงานด้วยสิทธิ์ยกระดับ และรันเนอร์ Ubuntu อนุญาตให้ใช้ sudo ดังนั้น workflow จึงไม่ต้องมีขั้นตอนเพิ่ม

การทดสอบบนเครือข่ายช้า

บันทึกโค้ดนี้เป็น test_slow.py แล้วรัน pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

การทดสอบผ่านเพราะคำตอบมาถึงช้าลงจริง: ทุกแพ็กเก็ตที่ไปและกลับจากเซิร์ฟเวอร์นั้นต้องรอ 500 ms เมื่อการทดสอบจบ เครือข่ายจะกลับเป็นปกติ วัดบน Windows ด้วย latency=200: คำขอไปยังเซิร์ฟเวอร์ในเป้าหมายเพิ่มจาก 4 ms เป็น 404 ms เพราะทั้งคำขอและคำตอบต้องรอ และหน้าเว็บใน Chromium เพิ่มจาก 61 ms เป็น 412 ms ระหว่างนั้นเซิร์ฟเวอร์ภายในเครื่องอีกตัวที่อยู่นอกเป้าหมายตอบใน 11 ms

ยังไม่มีสิทธิ์ในมือ? bad_network(simulate=True, latency=500) รันโปรแกรมกับทราฟฟิกที่สร้างขึ้นและไม่เปลี่ยนอะไรในเครือข่าย ใช้ตรวจว่าแพ็กเกจติดตั้งถูกต้อง โดยไม่ทำให้อะไรช้าลง

fixture ชื่อ bad_network

pytest จะหา fixture เจอเองเมื่อติดตั้งแพ็กเกจแล้ว เมื่อเรียก bad_network จะเริ่มเซสชัน และคืนค่าทันทีที่เครือข่ายช้าลงแล้ว เซสชันหยุดเมื่อการทดสอบจบ ไม่ว่าจะผ่าน ล้มเหลว หรือแครช และสรุปของโปรแกรมจะไปอยู่ใน user_properties ของการทดสอบ แล้วจากนั้นเข้าไปในรายงาน JUnit XML หากต้องการเปลี่ยนสภาพเครือข่ายกลางการทดสอบ ให้หยุดเซสชันแรกก่อนเริ่มเซสชันถัดไป:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

นอก pytest ให้ใช้ from beannetworktester import bad_network เพื่อเริ่มเซสชันเดียวกัน และ with bad_network(...) as session: จะหยุดเซสชันเมื่อจบบล็อก

Playwright สำหรับ Python

Playwright สำหรับ Python ทำงานบน pytest ดังนั้น fixture จึงเป็นตัวเดียวกัน Chromium, Firefox และ WebKit ช้าลงแบบเดียวกัน รวมถึง WebSocket เพราะสิ่งที่ช้าคือเครือข่ายเอง ไม่ใช่สิ่งที่เบราว์เซอร์คิดว่าเป็น:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

เซสชันเล็งไปที่อะไร

ทุกเซสชันเล็งไปที่บางสิ่ง และมีเพียงทราฟฟิกนั้นที่เปลี่ยน เซสชันที่ไม่มีเป้าหมายจะทำให้ทุกการเชื่อมต่อของเครื่องช้าลง รวมถึงของตัวรันการทดสอบเอง จึงไม่เริ่มทำงานเลย

  • server="http://localhost:3000" ทำให้ทุกการเชื่อมต่อไปยังที่อยู่และพอร์ตนั้นช้าลง ไม่ว่าจะมาจากแอป เบราว์เซอร์ หรือโปรแกรมอื่นใด ใช้ "db.local:5432", ("10.0.0.5", 443) และรายการเซิร์ฟเวอร์ได้เช่นกัน นี่คือตัวเลือกแรก และแม่นยำทั้งบน Windows และ Linux
  • process="self" ทำให้โปรเซสการทดสอบและทุกโปรแกรมที่มันเริ่ม เช่น เบราว์เซอร์ของ Playwright ช้าลง โปรเซสที่การทดสอบของคุณเริ่มเองให้ส่งเป็น subprocess.Popen ของมัน
  • dst_port, dst_ip และ target คือเป้าหมายของโปรแกรมเอง เขียนด้วยไวยากรณ์ของโปรแกรม สำหรับ API บนพอร์ตหรือที่อยู่ที่รู้จัก มันเข้าถึงทุกอย่างที่ตรงกัน: dst_port=443 คือทุกการเชื่อมต่อ HTTPS ของเครื่อง รวมถึงของโปรแกรมแก้ไขโค้ดของคุณ และ target="python" คือทุกโปรแกรมที่มี "python" อยู่ในชื่อ

เป้าหมายที่ให้มาพร้อมกันจะจำกัดกันและกัน: server= คู่กับ process="self" จะทำให้ช้าลงเฉพาะการเชื่อมต่อของการทดสอบนี้ไปยังเซิร์ฟเวอร์นั้น บน Linux process= และ target จะเริ่มมีผลกับการเชื่อมต่อใหม่ช้าได้ถึงราว 0.2 วินาทีหลังเปิด ดังนั้นเมื่อคำขอแรกสำคัญ ให้เล็งไปที่เซิร์ฟเวอร์

เซสชันทำอะไรได้บ้าง

ทุกการตั้งค่าคือหนึ่งในตัวเลือกบรรทัดคำสั่งของโปรแกรม เขียนด้วย _ แทน - latency=300 เพิ่ม 300 ms ให้ทุกแพ็กเก็ต jitter=100 ทำให้ความหน่วงนั้นแกว่ง loss=5 ทิ้งแพ็กเก็ต 5 % down และ up จำกัดความเร็วเป็น KB/s และ loss=100 ตัดเซิร์ฟเวอร์ออก preset="presets.3g" คือโปรไฟล์ลิงก์ทั้งชุด และ seed=42 ทำให้สุ่มเหมือนเดิมทุกครั้งที่รัน สถานการณ์จะเปลี่ยนสภาพเครือข่ายตามวินาทีที่ผ่านไป: scenario="scenarios/cafe-wifi.json" ขั้นตอนในสถานการณ์เปลี่ยนพฤติกรรมของเครือข่ายได้ แต่เปลี่ยนสิ่งที่เซสชันเล็งไม่ได้

pytest-xdist และข้อจำกัด

  • ทีละหนึ่ง สองเซสชันบนทราฟฟิกเดียวกันจะซ้อนกัน worker ของ pytest-xdist จึงผลัดกันทำ แต่ละตัวรอได้สูงสุด wait วินาที (600 ถ้าไม่ได้กำหนดค่าอื่น) เซสชันที่สองในการทดสอบเดียวกันจะถูกปฏิเสธทันที
  • จบพร้อมการทดสอบ ถ้าโปรเซสการทดสอบตาย โปรแกรมจะรู้และหยุดทันที duration (300 วินาที ถ้าไม่ได้กำหนดค่าอื่น) คือเวลานานที่สุดที่เซสชันรันได้ไม่ว่ากรณีใด
  • บอกเมื่อไม่ได้ทำอะไร เซสชันที่ไม่ได้ทำให้อะไรช้าลง เพราะไม่มีอะไรไปถึงเป้าหมาย จะจบด้วย BadNetworkWarning สาเหตุที่พบบ่อยคือแอปคุยกับที่อยู่อื่นที่ไม่ใช่เป้าหมาย เช่น คอนเทนเนอร์
  • macOS โปรแกรมทำงานบน Windows และ Linux บน Mac ให้รันการทดสอบในคอนเทนเนอร์หรือเครื่องเสมือน Linux x86_64 หรือบนรันเนอร์ CI
