Symulacja opóźnienia sieci i utraty pakietów w pytest

Nic nie jest udawane: pakiet beannetworktester z PyPI daje pytestowi fixture bad_network, który spowalnia prawdziwą sieć na czas testu. Opóźnienie, utrata pakietów, limit prędkości albo całkowita awaria, dla jednego serwera albo jednego procesu, podczas gdy Twoja aplikacja, przeglądarka i serwer naprawdę ze sobą rozmawiają. Pakiet zawiera program Bean Network Tester i uruchamia go na Windows i Linuksie. Wychodzi z każdym stabilnym wydaniem od 1.1.0.

Instalacja

pip install beannetworktester

Wymaga Windows x64 albo Linuksa x64 (glibc 2.39 lub nowsza, na przykład Ubuntu 24.04) i Pythona 3.10 lub nowszego.

Zmiana sieci wymaga uprawnień administratora na Windows: otwórz terminal przez „Uruchom jako administrator”. Na Linuksie wymaga roota albo użytkownika, który może uruchamiać sudo bez hasła, i wtedy pod sudo działa tylko program. Hostowane runnery GitHuba z Windows działają z uprawnieniami administratora, a te z Ubuntu pozwalają na sudo, więc workflow nie potrzebuje dodatkowego kroku.

Test na wolnej sieci

Zapisz to jako test_slow.py i uruchom pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

Test przechodzi, bo odpowiedź naprawdę przychodzi później: każdy pakiet do tego serwera i z niego czeka 500 ms. Po końcu testu sieć wraca do normy. Zmierzone na Windows przy latency=200: zapytanie do serwera w celu trwało 404 ms zamiast 4 ms, bo czeka i zapytanie, i odpowiedź, a strona w Chromium 412 ms zamiast 61 ms. Inny lokalny serwer, poza celem, odpowiadał w tym czasie w 11 ms.

Nie masz uprawnień pod ręką? bad_network(simulate=True, latency=500) uruchamia program na zmyślonym ruchu i niczego w sieci nie zmienia. Sprawdza, czy pakiet jest dobrze zainstalowany, i niczego nie spowalnia.

Fixture bad_network

pytest sam znajduje fixture, gdy pakiet jest zainstalowany. bad_network zaczyna sesję, gdy go wywołasz, i wraca, gdy sieć jest już wolna. Sesja kończy się razem z testem, czy przeszedł, czy nie, czy się wysypał, a podsumowanie programu trafia do user_properties testu, a stamtąd do raportu JUnit XML. Żeby zmienić warunki w połowie testu, zatrzymaj pierwszą sesję, zanim zaczniesz następną:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Poza pytestem tę samą sesję zaczyna from beannetworktester import bad_network, a with bad_network(...) as session: kończy ją na końcu bloku.

Playwright dla Pythona

Playwright dla Pythona działa na pyteście, więc fixture jest ten sam. Chromium, Firefox i WebKit zwalniają tak samo, razem z WebSocketami, bo wolna jest sama sieć, a nie to, co przeglądarka o niej sądzi:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

W co celuje sesja

Każda sesja w coś celuje i zmienia się tylko ten ruch. Sesja bez celu spowolniłaby każde połączenie maszyny, także połączenie samego uruchamiacza testów, więc w ogóle nie startuje.

  • server="http://localhost:3000" spowalnia każde połączenie z tym adresem i portem: z Twojej aplikacji, przeglądarki albo dowolnego innego programu. Działa też "db.local:5432", ("10.0.0.5", 443) i lista serwerów. To pierwszy wybór, dokładny na Windows i Linuksie.
  • process="self" spowalnia proces testów i każdy program, który uruchomił, na przykład przeglądarkę Playwrighta. Proces uruchomiony przez sam test podajesz jako jego subprocess.Popen.
  • dst_port, dst_ip i target to cele samego programu, pisane w jego składni, dla API na znanym porcie albo adresie. Obejmują wszystko, co pasuje: dst_port=443 to każde połączenie HTTPS maszyny, także Twojego edytora, a target="python" to każdy program z „python” w nazwie.

Cele podane razem zawężają się nawzajem: server= z process="self" spowalnia tylko połączenia tego testu z tym serwerem. Na Linuksie process= i target sięgają nowego połączenia do około 0,2 sekundy po jego otwarciu, więc celuj w serwer, gdy liczy się pierwsze zapytanie.

Co potrafi sesja

Każde ustawienie to jedna z opcji linii komend programu, pisana z _ zamiast -. latency=300 dodaje 300 ms do każdego pakietu, jitter=100 zmienia to opóźnienie, loss=5 gubi 5 % pakietów, down i up ograniczają prędkość w KB/s, a loss=100 odcina serwer. preset="presets.3g" to cały profil łącza, a seed=42 daje te same losowania przy każdym uruchomieniu. Scenariusz zmienia warunki z upływem sekund: scenario="scenarios/cafe-wifi.json". Krok scenariusza może zmienić zachowanie sieci, ale nie to, w co celuje sesja.

pytest-xdist i ograniczenia

  • Jedna naraz. Dwie sesje na tym samym ruchu sumowałyby się, więc workery pytest-xdist czekają na swoją kolej, każdy do wait sekund (600, jeśli nie podasz innej wartości). Druga sesja w tym samym teście jest od razu odrzucana.
  • Kończy się z testem. Jeśli proces testów padnie, program to widzi i od razu się zatrzymuje. duration (300 sekund, jeśli nie podasz innej wartości) to w każdym przypadku najdłuższy czas sesji.
  • Mówi, gdy nic nie zrobiła. Sesja, która niczego nie spowolniła, bo nic nie trafiło w jej cel, kończy się ostrzeżeniem BadNetworkWarning. Zwykle znaczy to, że aplikacja rozmawia z innym adresem niż cel, na przykład z kontenerem.
  • macOS. Program działa na Windows i Linuksie. Na Macu uruchom testy w kontenerze albo maszynie wirtualnej z Linuksem x86_64 albo na runnerze CI.
