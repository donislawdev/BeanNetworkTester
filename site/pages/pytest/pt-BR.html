Simule latência de rede e perda de pacotes no pytest

Nada de mock: o pacote beannetworktester no PyPI dá ao pytest uma fixture bad_network que deixa a rede de verdade lenta durante um teste. Latência, perda de pacotes, limite de velocidade ou uma queda total, para um servidor ou um processo, enquanto o seu app, o seu navegador e o seu servidor conversam de verdade. O pacote traz o programa do Bean Network Tester e o executa no Windows e no Linux. Ele sai com cada versão estável a partir da 1.1.0.

Instalação

pip install beannetworktester

Precisa de Windows x64 ou Linux x64 (glibc 2.39 ou mais nova, como Ubuntu 24.04) e Python 3.10 ou mais novo.

Mudar a rede exige direitos de administrador no Windows: abra o terminal com "Executar como administrador". No Linux exige root, ou um usuário que possa usar sudo sem senha, e então só o programa roda com sudo. Os runners Windows hospedados pelo GitHub rodam com privilégios elevados e os runners Ubuntu permitem sudo, então um workflow não precisa de nenhum passo extra.

Um teste numa rede lenta

Salve isto como test_slow.py e rode pytest:

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

O teste passa porque a resposta chega mesmo mais tarde: cada pacote para esse servidor e vindo dele espera 500 ms. Quando o teste termina, a rede volta ao normal. Medido no Windows com latency=200: uma requisição ao servidor no alvo foi de 4 ms para 404 ms, porque a requisição e a resposta esperam, e uma página no Chromium de 61 ms para 412 ms. Outro servidor local, fora do alvo, respondia enquanto isso em 11 ms.

Sem os direitos à mão? bad_network(simulate=True, latency=500) roda o programa com tráfego inventado e não muda nada na rede. Isso verifica que o pacote está instalado direito, sem deixar nada lento.

A fixture bad_network

O pytest encontra a fixture sozinho quando o pacote está instalado. bad_network inicia uma sessão quando você a chama e retorna assim que a rede está lenta. A sessão para quando o teste termina, tenha ele passado, falhado ou travado, e o resumo do programa vai para as user_properties do teste e de lá para um relatório JUnit XML. Para mudar as condições no meio do teste, pare a primeira sessão antes de iniciar a próxima:

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

Fora do pytest, from beannetworktester import bad_network inicia a mesma sessão, e with bad_network(...) as session: a encerra no fim do bloco.

Playwright para Python

O Playwright para Python roda sobre o pytest, então a fixture é a mesma. Chromium, Firefox e WebKit ficam lentos do mesmo jeito, WebSockets incluídos, porque é a própria rede que está lenta, não a ideia que o navegador tem dela:

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

Para onde uma sessão aponta

Toda sessão aponta para algo, e só esse tráfego muda. Uma sessão sem alvo deixaria lenta cada conexão da máquina, inclusive a do próprio executor de testes, por isso ela não inicia.

  • server="http://localhost:3000" deixa lenta cada conexão a esse endereço e porta, vinda do seu app, do seu navegador ou de qualquer outro programa. "db.local:5432", ("10.0.0.5", 443) e uma lista de servidores também funcionam. É a primeira escolha, e é exata no Windows e no Linux.
  • process="self" deixa lento o processo de testes e cada programa que ele iniciou, como o navegador do Playwright. Um processo que o próprio teste iniciou é passado como o seu subprocess.Popen.
  • dst_port, dst_ip e target são os alvos do próprio programa, escritos na sintaxe dele, para uma API numa porta ou num endereço conhecidos. Eles alcançam tudo o que combina: dst_port=443 é cada conexão HTTPS da máquina, inclusive as do seu editor, e target="python" cada programa com "python" no nome.

Alvos dados juntos estreitam um ao outro: server= com process="self" deixa lentas só as conexões deste teste com esse servidor. No Linux, process= e target alcançam uma conexão nova até cerca de 0,2 segundo depois de ela abrir, então aponte para o servidor quando a primeira requisição conta.

O que uma sessão pode fazer

Cada ajuste é uma das opções de linha de comando do programa, escrita com _ em vez de -. latency=300 soma 300 ms a cada pacote, jitter=100 varia esse atraso, loss=5 descarta 5 % dos pacotes, down e up limitam a velocidade em KB/s, e loss=100 corta o servidor. preset="presets.3g" é um perfil de link inteiro, e seed=42 faz as mesmas escolhas aleatórias em cada execução. Um cenário muda as condições conforme os segundos passam: scenario="scenarios/cafe-wifi.json". Um passo do cenário pode mudar como a rede se comporta, mas não para onde a sessão aponta.

pytest-xdist e limites

  • Uma de cada vez. Duas sessões sobre o mesmo tráfego se somariam, então os workers do pytest-xdist se revezam, cada um esperando até wait segundos (600 se você não der outro valor). Uma segunda sessão no mesmo teste é recusada na hora.
  • Ela termina com o teste. Se o processo de testes morrer, o programa percebe e para na hora. duration (300 segundos se você não der outro valor) é, em qualquer caso, o máximo que uma sessão pode durar.
  • Ela avisa quando não fez nada. Uma sessão que não deixou nada lento, porque nada chegou ao seu alvo, termina com um BadNetworkWarning. O comum é o app falar com outro endereço que não o alvo, como um contêiner.
  • macOS. O programa roda no Windows e no Linux. Num Mac, rode os testes num contêiner ou numa máquina virtual Linux x86_64, ou num runner de CI.

O README do pacote no GitHub lista cada opção e explica cada mensagem.
