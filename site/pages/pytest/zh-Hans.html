在 pytest 中模拟网络延迟和丢包

不用任何模拟代码：PyPI 上的 beannetworktester 软件包为 pytest 提供 bad_network fixture，在测试期间拖慢真实的网络。在你的应用、浏览器和服务器真正相互通信时，为一个服务器或一个进程加入延迟、丢包、限速或完全断网。软件包自带 Bean Network Tester 的程序，并在 Windows 和 Linux 上运行它。从 1.1.0 起，每个稳定版本都会发布它。

安装

pip install beannetworktester

需要 Windows x64 或 Linux x64（glibc 2.39 或更新，例如 Ubuntu 24.04），以及 Python 3.10 或更新版本。

在 Windows 上更改网络需要管理员权限：用“以管理员身份运行”打开终端。在 Linux 上需要 root，或可以免密码运行 sudo 的用户，这时只有程序在 sudo 下运行。GitHub 托管的 Windows 运行器以提升的权限运行，Ubuntu 运行器允许 sudo，所以工作流不需要额外步骤。

在慢网络上的测试

把它保存为 test_slow.py，然后运行 pytest：

import subprocess
import sys
import time
import urllib.request

import pytest


@pytest.fixture
def web_server():
    server = subprocess.Popen([sys.executable, "-m", "http.server", "8000"])
    time.sleep(1)
    yield "http://localhost:8000"
    server.terminate()


def test_a_page_takes_longer_on_a_slow_network(bad_network, web_server):
    bad_network(server=web_server, latency=500)
    started = time.monotonic()
    urllib.request.urlopen(web_server).read()
    assert time.monotonic() - started >= 0.5

测试能通过，是因为回复确实来得更晚：进出该服务器的每个数据包都要等 500 ms。测试结束后，网络恢复正常。在 Windows 上用 latency=200 实测：对目标服务器的请求从 4 ms 变为 404 ms，因为请求和回复都要等待；Chromium 中的页面从 61 ms 变为 412 ms。同时，目标之外的另一个本地服务器在 11 ms 内响应。

手头没有权限？bad_network(simulate=True, latency=500) 会用虚构的流量运行程序，不改变网络上的任何东西。它用来检查软件包是否装好，不会拖慢任何东西。

bad_network fixture

安装软件包后，pytest 会自动找到这个 fixture。调用 bad_network 时会启动一个会话，网络变慢后即返回。无论测试通过、失败还是崩溃，会话都会在测试结束时停止，程序的摘要会写入测试的 user_properties，再进入 JUnit XML 报告。要在测试中途改变条件，请先停止第一个会话，再启动下一个：

def test_the_app_recovers_when_the_api_comes_back(bad_network):
    outage = bad_network(server="http://localhost:8000", loss=100)
    assert app_shows_offline_banner()
    outage.stop()
    assert app_hides_offline_banner()

在 pytest 之外，from beannetworktester import bad_network 会启动同样的会话，with bad_network(...) as session: 会在代码块结束时停止它。

Playwright for Python

Playwright for Python 运行在 pytest 之上，所以 fixture 相同。Chromium、Firefox 和 WebKit 以同样的方式变慢，WebSocket 也一样，因为慢的是网络本身，而不是浏览器以为的网络：

from playwright.sync_api import expect


def test_the_spinner_shows_on_a_slow_network(bad_network, page):
    bad_network(server="http://localhost:3000", latency=800)
    page.goto("http://localhost:3000")
    expect(page.get_by_role("progressbar")).to_be_visible()

会话针对什么

每个会话都针对某个目标，只有这部分流量会改变。没有目标的会话会拖慢这台机器的所有连接，连测试运行器自己的连接也不例外，所以它不会启动。

  • server="http://localhost:3000" 会拖慢到该地址和端口的每个连接，无论来自你的应用、浏览器还是其他任何程序。"db.local:5432"、("10.0.0.5", 443) 和服务器列表也可以。这是首选，在 Windows 和 Linux 上都很精确。
  • process="self" 会拖慢测试进程以及它启动的每个程序，例如 Playwright 的浏览器。测试自己启动的进程，以它的 subprocess.Popen 传入。
  • dst_port、dst_ip 和 target 是程序自己的目标，用它的语法书写，适用于已知端口或地址上的 API。它们会作用于所有匹配的东西：dst_port=443 是这台机器的每个 HTTPS 连接，包括你的编辑器的连接；target="python" 是名字里含有“python”的每个程序。

同时给出的目标会相互收窄：server= 加上 process="self"，只会拖慢这个测试到该服务器的连接。在 Linux 上，process= 和 target 最多要在新连接打开约 0.2 秒后才生效，所以当第一个请求很重要时，请针对服务器。

会话能做什么

每个设置都是程序的一个命令行选项，用 _ 代替 - 书写。latency=300 给每个数据包加 300 ms，jitter=100 让这个延迟波动，loss=5 丢弃 5 % 的数据包，down 和 up 以 KB/s 限制速度，loss=100 则切断服务器。preset="presets.3g" 是一整套链路配置，seed=42 让每次运行做出相同的随机选择。场景会随着秒数推移改变条件：scenario="scenarios/cafe-wifi.json"。场景中的步骤可以改变网络的表现，但不能改变会话针对的目标。

pytest-xdist 与限制

  • 一次一个。同一流量上的两个会话会叠加，所以 pytest-xdist 的 worker 会轮流进行，每个最多等待 wait 秒（不另行指定时为 600）。同一测试中的第二个会话会被立即拒绝。
  • 随测试一起结束。如果测试进程崩溃，程序会察觉并立即停止。duration（不另行指定时为 300 秒）在任何情况下都是会话的最长运行时间。
  • 什么都没做时会告诉你。没有任何流量到达目标、因而什么也没拖慢的会话，会以 BadNetworkWarning 结束。常见原因是应用连接的地址不是目标，例如一个容器。
  • macOS。程序在 Windows 和 Linux 上运行。在 Mac 上，请在 Linux x86_64 容器或虚拟机中，或在 CI 运行器上运行测试。

软件包在 GitHub 上的 README 列出了每个选项，并解释了每条消息。
