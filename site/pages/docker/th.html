จำลองความหน่วงเครือข่ายใน Docker และ Docker Compose

เพิ่มความหน่วง แพ็กเก็ตสูญหาย หรือจำกัดความเร็วให้ทราฟฟิกของคอนเทนเนอร์เดียว โดยไม่ต้องแก้อิมเมจของมันและไม่ต้องวางพร็อกซีไว้ข้างหน้า อิมเมจของ Bean Network Tester จะเข้าร่วมเครือข่ายของคอนเทนเนอร์นั้น เปลี่ยนเฉพาะสิ่งที่เข้าและออกจากมัน แล้วหยุดเองเมื่อถึงเวลา นี่คือเวอร์ชัน Linux จึงยังเป็นรุ่นทดลอง

ทำให้คอนเทนเนอร์เดียวช้าลง

เริ่มอิมเมจข้างคอนเทนเนอร์ที่ต้องการทดสอบ ในที่นี้คือคอนเทนเนอร์ชื่อ api อิมเมจต้องการ capability เพิ่มอีกสามตัวนอกเหนือจากค่าเริ่มต้นของ Docker และไม่ต้องใช้ --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api พาโปรแกรมเข้าไปในเครือข่ายของคอนเทนเนอร์นั้น คอนเทนเนอร์อื่นและโฮสต์จึงไม่ถูกแตะต้อง --dst-ip จำกัดผลไว้ที่ที่อยู่เดียว ถ้าไม่ใส่ ทุกการเชื่อมต่อของ api จะช้าลง ผลการวัด: ที่ --latency 100 ping จากคอนเทนเนอร์ไปยังที่อยู่นั้นเพิ่มจาก 0.07 ms เป็น 200.8 ms เพราะทั้งคำขอและคำตอบถูกหน่วง ส่วน ping ไปยังที่อยู่อื่นยังต่ำกว่า 1 ms

ทุกการตั้งค่าของบรรทัดคำสั่งใช้ได้ที่นี่: --loss, --jitter, --down และ --up สำหรับจำกัดความเร็ว รวมถึงพรีเซ็ตหรือทั้งสถานการณ์ เซสชันจบด้วย --duration และด้วย docker stop ก็ได้

Docker Compose: จำลองความหน่วงเครือข่ายให้บริการหนึ่ง

ใน Compose สิ่งเดียวกันคือบริการแยกต่างหากที่ใช้เครือข่ายร่วมกับบริการที่มันทำให้ช้าลง:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

ทุกบริการที่คุยกับ api จะเห็นมันไกลออกไป 400 ms และสูญเสียแพ็กเก็ต 2% ผลการวัดด้วยไฟล์นี้: ping จากบริการอื่นเพิ่มจาก 0.1 ms เป็น 401 ms คำสั่ง docker compose stop slow-network จะจบเซสชัน และทราฟฟิกกลับเป็นปกติทันที

โปรแกรมเดียวภายในคอนเทนเนอร์

--target เลือกโปรแกรมตามชื่อ เหมือนบนเดสก์ท็อป หากต้องการเห็นโปรเซสของคอนเทนเนอร์อื่น อิมเมจต้องมีรายการโปรเซสของมันด้วย: --pid container:api

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

ถ้าไม่มี --pid โปรแกรมจะหาโปรเซสนั้นไม่เจอและบอกไว้ในล็อก: Targeting: NO matching process has a connection open - traffic is NOT being impaired. ในกรณีนั้นจะไม่มีอะไรช้าลง

โปรแกรมบนโฮสต์ Linux

อิมเมจยังเข้าถึงโปรแกรมที่รันบนโฮสต์โดยตรงนอกคอนเทนเนอร์ใดๆ ได้ด้วย ซึ่งต้องใช้เครือข่ายและรายการโปรเซสของโฮสต์ และอีกสองตัวเลือก: หากขาดตัวใดตัวหนึ่ง การอ่านการเชื่อมต่อของโปรแกรมนอกคอนเทนเนอร์จะถูกปฏิเสธ

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

เมื่อใช้ --network host เซสชันจะเปลี่ยนทราฟฟิกของโฮสต์เอง รวมถึงเซสชัน ssh ของคุณ จึงควรจำกัดให้แคบด้วย --target, --dst-ip หรือ --dst-port และให้สั้นด้วย --duration ผลการวัดบน Ubuntu 26.04: คำขอของโปรแกรมเป้าหมายเพิ่มจาก 3 ms เป็นประมาณ 250 ms ส่วนของโปรแกรมอื่นยังอยู่ที่ 11 ms บนเดสก์ท็อป แพ็กเกจสำหรับ Linux ทำแบบเดียวกันได้โดยไม่ต้องใช้ Docker

Docker Desktop บน Windows และ macOS

Docker Desktop รันคอนเทนเนอร์ในเครื่องเสมือน Linux ของตัวเอง และที่นั่น "โฮสต์" หมายถึงเครื่องเสมือนนั้น อิมเมจเปลี่ยนทราฟฟิกของคอนเทนเนอร์ ไม่เคยเปลี่ยนทราฟฟิกของโปรแกรม Windows หรือ macOS หากต้องการทำให้โปรแกรม Windows ช้าลง ให้ใช้ Bean Network Tester เวอร์ชัน Windows

บน Mac ที่ใช้ Apple silicon และเครื่อง arm64 อื่นๆ Docker รันอิมเมจ x86_64 นี้ผ่านการจำลอง และในนั้นไม่มีการเรียก BPF ของเคอร์เนล อิมเมจเริ่มทำงานได้และ --simulate ใช้ได้ แต่การดักจับจะหยุดทันทีพร้อม Function not implemented วัดบน Mac M2 ที่ใช้การจำลอง QEMU ของ Colima ซึ่ง --doctor ยังคงแสดง OK ทุกบรรทัด

ไฟล์ สถานการณ์ และ CI

  • ไฟล์ เมานต์โฟลเดอร์ที่ /work (-v "$PWD:/work") สำหรับ --log-conns, --repro-out, ไฟล์ CSV หรือไฟล์ --scenario โปรแกรมรันเป็น root ภายในอิมเมจ ไฟล์ที่มันเขียนจึงเป็นของ root
  • รหัสออก อิมเมจจบด้วยรหัสออกของตัวโปรแกรมเอง ขั้นตอน CI จึงล้มเหลวตามรหัสเหล่านี้ได้ --fail-on-no-traffic จะทำให้การรันที่ไม่มีอะไรผ่านเลยล้มเหลว ซึ่งมักเป็นสัญญาณว่าเลือกเครือข่ายหรือเป้าหมายผิด docker stop จบด้วย 143 ซึ่งคือการหยุดอย่างเรียบร้อย
  • สิ่งที่ขาด --doctor จะบอก เช่น capability ที่ไม่ได้ให้ตอนเริ่มคอนเทนเนอร์
  • การหยุด หลัง docker stop ทราฟฟิกกลับเป็นปกติทันที หลัง docker kill ทราฟฟิกจะไหลอีกครั้งภายในประมาณ 3 วินาที
