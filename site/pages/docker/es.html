Simular latencia de red en Docker y Docker Compose

Añade retardo, pérdida de paquetes o un límite de velocidad al tráfico de un solo contenedor, sin cambiar su imagen y sin un proxy delante. La imagen de Bean Network Tester se une a la red de ese contenedor, cambia solo lo que entra y sale de él y se detiene sola. Es la versión de Linux, así que es experimental.

Ralentizar un contenedor

Inicia la imagen junto al contenedor que quieres probar, aquí uno llamado api. Necesita tres capacidades además de las predeterminadas de Docker, y no necesita --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api mete el programa en la red de ese contenedor, así que los demás contenedores y el host no se tocan. --dst-ip lo limita a una dirección. Sin esa opción se ralentiza cada conexión de api. Medido: con --latency 100, el ping del contenedor a esa dirección subió de 0,07 ms a 200,8 ms, porque se retrasan tanto la petición como la respuesta, y su ping a otra dirección se quedó por debajo de 1 ms.

Aquí funciona cualquier ajuste de la línea de comandos: --loss, --jitter, --down y --up para un límite de velocidad, un preset o un escenario completo. --duration termina la sesión, y también docker stop.

Docker Compose: simular latencia de red para un servicio

En Compose es un servicio propio que comparte la red del servicio que ralentiza:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Cada servicio que habla con api lo ve ahora 400 ms más lejos, con un 2 % de paquetes perdidos. Medido con este archivo: el ping desde otro servicio subió de 0,1 ms a 401 ms. docker compose stop slow-network lo termina, y el tráfico vuelve a la normalidad al instante.

Un programa dentro de un contenedor

--target elige un programa por su nombre, como en un escritorio. Para ver los procesos de otro contenedor, la imagen necesita también su lista de procesos: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Sin --pid, el programa no encuentra ese proceso y lo dice en su registro: Targeting: NO matching process has a connection open - traffic is NOT being impaired. En ese caso no se ralentiza nada.

Un programa en el host Linux

La imagen también llega a un programa que se ejecuta en el propio host, fuera de cualquier contenedor. Para ello necesita la red y la lista de procesos del host, y dos opciones más: sin ambas, se rechaza la lectura de las conexiones de un programa de fuera del contenedor.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Con --network host, la sesión cambia el tráfico del propio host, incluida tu sesión ssh, así que mantenla acotada con --target, --dst-ip o --dst-port, y corta con --duration. Medido en Ubuntu 26.04: las peticiones del programa elegido pasaron de 3 ms a unos 250 ms, y las de otro programa se quedaron en 11 ms. En un escritorio, el paquete para Linux hace lo mismo sin Docker.

Docker Desktop en Windows y macOS

Docker Desktop ejecuta los contenedores en su propia máquina virtual Linux, y allí «host» significa esa máquina. La imagen cambia el tráfico de los contenedores, nunca el de los programas de Windows o macOS. Para ralentizar un programa de Windows, usa la versión de Windows de Bean Network Tester.

En un Mac con Apple silicon y en otras máquinas arm64, Docker ejecuta esta imagen x86_64 con emulación, y ahí no existen las llamadas BPF del kernel. La imagen arranca y --simulate funciona, pero una captura se detiene al instante con Function not implemented. Medido en un Mac M2 con la emulación QEMU de Colima, donde --doctor aun así mostraba OK en cada fila.

Archivos, escenarios y CI

  • Archivos. Monta una carpeta en /work (-v "$PWD:/work") para --log-conns, --repro-out, archivos CSV o un archivo de --scenario. El programa se ejecuta como root en la imagen, así que los archivos que escribe pertenecen a root.
  • Códigos de salida. La imagen termina con los códigos de salida del propio programa, así que un paso de CI puede fallar con ellos. --fail-on-no-traffic hace fallar una ejecución por la que no pasó nada, la señal habitual de una red o un objetivo equivocados. docker stop termina con 143, una parada limpia.
  • Qué falta. --doctor lo dice, por ejemplo una capacidad con la que no se inició el contenedor.
  • Parada. Tras docker stop, el tráfico vuelve a la normalidad al instante. Tras docker kill, vuelve a fluir en unos 3 segundos.

Qué imágenes hay

Cada versión estable desde la 1.1.0 es una imagen, etiquetada con su versión y latest. Las versiones candidatas no tienen. Cada una es el paquete de Linux publicado, sin cambios, sobre Ubuntu 24.04, para x86_64. Antes de publicarla se comprueban la suma de verificación y la procedencia del paquete, y la imagen se ejecuta en un kernel Linux tal como describe esta página. Para comprobar una imagen descargada:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
