Docker と Docker Compose でネットワーク遅延を再現

1つのコンテナの通信に遅延、パケットロス、速度制限を加えます。イメージを変える必要も、前にプロキシを置く必要もありません。Bean Network Tester のイメージはそのコンテナのネットワークに加わり、出入りする通信だけを変え、時間が来ると自分で止まります。Linux 版なので、実験的な扱いです。

1つのコンテナを遅くする

テストしたいコンテナ（ここでは api）の隣でイメージを起動します。Docker の既定に加えて3つのケーパビリティが必要で、--privileged は不要です。

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api でプログラムがそのコンテナのネットワークに入るので、ほかのコンテナとホストには影響しません。--dst-ip は対象を1つのアドレスに絞ります。指定しなければ api のすべての接続が遅くなります。実測では、--latency 100 でコンテナからそのアドレスへの ping が 0.07 ms から 200.8 ms に増えました。要求と応答の両方が遅れるためです。別のアドレスへの ping は 1 ms 未満のままでした。

コマンドラインの設定はすべて使えます。--loss、--jitter、速度制限の --down と --up、プリセットやシナリオ全体もです。--duration でセッションが終わり、docker stop でも終わります。

Docker Compose：サービスにネットワーク遅延を加える

Compose では、遅くしたいサービスとネットワークを共有する別のサービスとして書きます。

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

api と通信するすべてのサービスから見て、api は 400 ms 遠くなり、パケットの 2% が失われます。このファイルでの実測では、別のサービスからの ping が 0.1 ms から 401 ms になりました。docker compose stop slow-network で終わり、通信はすぐ元に戻ります。

コンテナ内の1つのプログラム

--target はデスクトップと同じく、名前でプログラムを選びます。別のコンテナのプロセスを見るには、そのプロセス一覧も必要です：--pid container:api。

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

--pid がないとプログラムはそのプロセスを見つけられず、ログにこう書きます：Targeting: NO matching process has a connection open - traffic is NOT being impaired. この場合、何も遅くなりません。

Linux ホスト上のプログラム

イメージは、コンテナの外、ホスト上で直接動くプログラムにも届きます。ホストのネットワークとプロセス一覧に加えて、2つのオプションが必要です。どちらか一方でも欠けると、コンテナの外のプログラムの接続を読むことが拒否されます。

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

--network host ではセッションがホスト自身の通信を変え、ssh のセッションも含まれます。--target、--dst-ip、--dst-port で絞り、--duration で短くしてください。Ubuntu 26.04 での実測では、対象のプログラムのリクエストが 3 ms から約 250 ms になり、別のプログラムは 11 ms のままでした。デスクトップでは Linux 版パッケージが Docker なしで同じことをします。

Windows と macOS の Docker Desktop

Docker Desktop はコンテナを独自の Linux 仮想マシンで動かし、そこでは「ホスト」はその仮想マシンを指します。イメージが変えるのはコンテナの通信だけで、Windows や macOS のプログラムの通信は変えません。Windows のプログラムを遅くするには、Bean Network Tester の Windows 版を使ってください。

Apple シリコンの Mac やほかの arm64 マシンでは、Docker はこの x86_64 イメージをエミュレーションで動かし、そこにはカーネルの BPF 呼び出しがありません。イメージは起動し --simulate も動きますが、キャプチャはすぐに Function not implemented で止まります。Colima の QEMU エミュレーションを使った M2 Mac での実測で、そのとき --doctor はすべての行で OK と表示していました。

ファイル、シナリオ、CI

  • ファイル。--log-conns、--repro-out、CSV ファイル、--scenario のファイルには、フォルダーを /work にマウントします（-v "$PWD:/work"）。プログラムはイメージ内で root として動くので、書き出したファイルは root のものになります。
  • 終了コード。イメージはプログラム自身の終了コードで終わるので、CI のステップはそれで失敗にできます。--fail-on-no-traffic は何も通過しなかった実行を失敗にします。たいていネットワークか対象の指定ミスです。docker stop は正常停止を示す 143 で終わります。
  • 足りないもの。--doctor が教えてくれます。たとえばコンテナの起動時に渡さなかったケーパビリティです。
  • 停止。docker stop の後、通信はすぐ元に戻ります。docker kill の後は約 3 秒以内に流れ始めます。

提供されるイメージ

1.1.0 以降の安定版はすべてイメージになり、バージョンと latest のタグが付きます。リリース候補（RC）にはありません。中身は公開された Linux 版パッケージそのままで、Ubuntu 24.04 上、x86_64 向けです。プッシュの前に、パッケージのチェックサムとビルドの来歴を確認し、このページの説明どおりに Linux カーネル上でイメージを動かします。取得したイメージを確認するには：

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
