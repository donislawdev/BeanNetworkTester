Docker와 Docker Compose에서 네트워크 지연 시뮬레이션

컨테이너 하나의 트래픽에 지연, 패킷 손실, 속도 제한을 더합니다. 이미지를 바꿀 필요도, 앞에 프록시를 둘 필요도 없습니다. Bean Network Tester 이미지는 그 컨테이너의 네트워크에 합류해 드나드는 트래픽만 바꾸고, 시간이 되면 스스로 멈춥니다. Linux 패키지이므로 실험 단계입니다.

컨테이너 하나를 느리게 하기

테스트할 컨테이너 옆에서 이미지를 실행합니다. 여기서는 이름이 api인 컨테이너입니다. Docker 기본값 외에 세 가지 capability가 필요하고, --privileged는 필요 없습니다.

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api는 프로그램을 그 컨테이너의 네트워크에 넣습니다. 그 네트워크 안의 모든 프로그램에 닿으며, 같은 방법으로 그 안에서 시작한 다른 컨테이너도 포함되지만, 호스트나 자기 네트워크를 가진 컨테이너에는 닿지 않습니다. --dst-ip는 범위를 주소 하나로 좁힙니다. 이 옵션이 없으면 api의 모든 연결이 느려집니다. 측정 결과: --latency 100에서 컨테이너가 그 주소로 보낸 ping은 0.07 ms에서 200.8 ms로 늘었습니다. 요청과 응답이 모두 지연되기 때문입니다. 다른 주소로 보낸 ping은 1 ms 미만에 머물렀습니다.

명령줄의 모든 설정을 여기서 쓸 수 있습니다. --loss, --jitter, 속도 제한용 --down과 --up, 프리셋이나 시나리오 전체도 됩니다. 세션은 --duration으로 끝나고, docker stop으로도 끝납니다.

Docker Compose: 서비스에 네트워크 지연 시뮬레이션

Compose에서는 느리게 할 서비스와 네트워크를 공유하는 별도의 서비스로 씁니다.

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

이제 api와 통신하는 모든 서비스에는 api가 400 ms 더 멀게 보이고, 패킷의 2%가 손실됩니다. 이 파일로 측정한 결과 다른 서비스에서 보낸 ping이 0.1 ms에서 401 ms로 늘었습니다. docker compose stop slow-network로 끝내면 트래픽은 바로 정상으로 돌아옵니다.

컨테이너 안의 프로그램 하나

--target은 데스크톱에서처럼 이름으로 프로그램을 고릅니다. 다른 컨테이너의 프로세스를 보려면 이미지에 그 프로세스 목록도 필요합니다: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

--pid가 없으면 프로그램은 그런 프로세스를 찾지 못하고 로그에 이렇게 남깁니다: Targeting: NO matching process has a connection open - traffic is NOT being impaired. 이 경우 아무것도 느려지지 않습니다.

Linux 호스트의 프로그램

이미지는 컨테이너 밖, 호스트에서 직접 실행되는 프로그램에도 닿을 수 있습니다. 이때는 호스트의 네트워크와 프로세스 목록, 그리고 옵션 두 개가 더 필요합니다. 둘 중 하나라도 없으면 컨테이너 밖 프로그램의 연결을 읽는 것이 거부됩니다.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

--network host를 쓰면 세션이 호스트 자체의 트래픽을 바꾸고, ssh 세션도 포함됩니다. 그러니 --target, --dst-ip, --dst-port로 좁히고 --duration으로 짧게 유지하세요. Ubuntu 26.04에서 측정한 결과, 대상 프로그램의 요청은 3 ms에서 약 250 ms로 늘었고 다른 프로그램의 요청은 11 ms에 머물렀습니다. 데스크톱에서는 Linux 패키지가 Docker 없이 같은 일을 합니다.

Windows와 macOS의 Docker Desktop

Docker Desktop은 자체 Linux 가상 머신에서 컨테이너를 실행하며, 거기서 "호스트"는 그 가상 머신을 뜻합니다. 이미지는 컨테이너의 트래픽만 바꾸고, Windows나 macOS 프로그램의 트래픽은 결코 바꾸지 않습니다. Windows 프로그램을 느리게 하려면 Bean Network Tester의 Windows 버전을 쓰세요.

Apple silicon Mac과 다른 arm64 머신에서 Docker는 이 x86_64 이미지를 에뮬레이션으로 실행하므로, 캡처가 동작하지 않을 수 있습니다. Colima의 QEMU 에뮬레이션을 쓰는 M2 Mac에서 측정한 결과, 이미지는 시작되고 --simulate도 동작하지만 캡처는 곧바로 Function not implemented로 멈추며, 그래도 --doctor는 모든 줄에 OK를 표시합니다.

파일, 시나리오, CI

  • 파일. --log-conns, --repro-out, CSV 파일, --scenario 파일을 위해 폴더를 /work에 마운트하세요(-v "$PWD:/work"). 프로그램은 이미지 안에서 root로 실행되므로, 프로그램이 쓴 파일은 root 소유가 됩니다.
  • 종료 코드. 이미지는 프로그램 자체의 종료 코드로 끝나므로 CI 단계가 이를 보고 실패할 수 있습니다. --fail-on-no-traffic은 아무것도 통과하지 않은 실행을 실패로 처리합니다. 대개 네트워크나 대상을 잘못 지정했다는 신호입니다. docker stop은 깨끗한 종료를 뜻하는 143으로 끝납니다.
  • 빠진 것. --doctor가 알려 줍니다. 예를 들어 컨테이너를 시작할 때 주지 않은 capability입니다.
  • 중지. docker stop 뒤에는 트래픽이 바로 정상으로 돌아옵니다. docker kill 뒤에는 약 3초 안에 다시 흐릅니다.
