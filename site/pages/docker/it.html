Simulare la latenza di rete in Docker e Docker Compose

Aggiungi ritardo, perdita di pacchetti o un limite di velocità al traffico di un solo container, senza cambiarne l'immagine e senza un proxy davanti. L'immagine di Bean Network Tester entra nella rete di quel container, cambia solo ciò che entra ed esce e si ferma da sola. È la versione per Linux, quindi sperimentale.

Rallentare un container

Avvia l'immagine accanto al container da provare, qui uno chiamato api. Le servono tre capability oltre a quelle predefinite di Docker, e non serve --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api porta il programma nella rete di quel container, così gli altri container e l'host restano intatti. --dst-ip lo limita a un indirizzo. Senza, ogni connessione di api rallenta. Misurato: con --latency 100 il ping del container verso quell'indirizzo è salito da 0,07 ms a 200,8 ms, perché sono ritardate sia la richiesta sia la risposta, e il suo ping verso un altro indirizzo è rimasto sotto 1 ms.

Qui funziona ogni impostazione della riga di comando: --loss, --jitter, --down e --up per un limite di velocità, un preset o un intero scenario. --duration chiude la sessione, e così docker stop.

Docker Compose: simulare la latenza di rete per un servizio

In Compose è un servizio a sé che condivide la rete di quello che rallenta:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Ogni servizio che parla con api ora lo vede 400 ms più lontano, con il 2 % dei pacchetti perso. Misurato con questo file: il ping da un altro servizio è salito da 0,1 ms a 401 ms. docker compose stop slow-network lo ferma, e il traffico torna subito normale.

Un programma dentro un container

--target sceglie un programma per nome, come su un desktop. Per vedere i processi di un altro container, l'immagine ha bisogno anche del suo elenco di processi: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Senza --pid il programma non trova quel processo e lo dice nel suo log: Targeting: NO matching process has a connection open - traffic is NOT being impaired. In quel caso non rallenta nulla.

Un programma sull'host Linux

L'immagine raggiunge anche un programma che gira sull'host stesso, fuori da ogni container. Le servono la rete e l'elenco dei processi dell'host, più due opzioni: senza entrambe, la lettura delle connessioni di un programma fuori dal container viene rifiutata.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Con --network host la sessione cambia il traffico dell'host stesso, compresa la tua sessione ssh, quindi tienila stretta con --target, --dst-ip o --dst-port e breve con --duration. Misurato su Ubuntu 26.04: le richieste del programma scelto sono passate da 3 ms a circa 250 ms, quelle di un altro programma sono rimaste a 11 ms. Su un desktop il pacchetto per Linux fa lo stesso senza Docker.

Docker Desktop su Windows e macOS

Docker Desktop esegue i container in una propria macchina virtuale Linux, e lì "host" indica quella macchina. L'immagine cambia il traffico dei container, mai quello dei programmi Windows o macOS. Per rallentare un programma Windows, usa la versione per Windows di Bean Network Tester.

Su un Mac con Apple silicon e su altre macchine arm64, Docker esegue questa immagine x86_64 in emulazione, e lì le chiamate BPF del kernel non ci sono. L'immagine parte e --simulate funziona, ma una cattura si ferma subito con Function not implemented. Misurato su un Mac M2 con l'emulazione QEMU di Colima, dove --doctor mostrava comunque OK su ogni riga.

File, scenari e CI

  • File. Monta una cartella su /work (-v "$PWD:/work") per --log-conns, --repro-out, file CSV o un file di --scenario. Il programma gira come root nell'immagine, quindi i file che scrive appartengono a root.
  • Codici di uscita. L'immagine termina con i codici di uscita del programma, così un passo di CI può fallire su di essi. --fail-on-no-traffic fa fallire un'esecuzione in cui non è passato nulla, il segno tipico di una rete o di un obiettivo sbagliati. docker stop termina con 143, un arresto pulito.
  • Cosa manca. Lo dice --doctor, per esempio una capability senza la quale il container è stato avviato.
  • Arresto. Dopo docker stop il traffico torna subito normale. Dopo docker kill riprende a scorrere entro circa 3 secondi.

Quali immagini ci sono

Ogni versione stabile dalla 1.1.0 in poi è un'immagine, con il tag della sua versione e latest. Le release candidate non ne hanno. Ognuna è il pacchetto per Linux pubblicato, invariato, su Ubuntu 24.04, per x86_64. Prima dell'invio si controllano il checksum e la provenienza del pacchetto, e l'immagine viene eseguita su un kernel Linux come descrive questa pagina. Per verificare un'immagine scaricata:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
