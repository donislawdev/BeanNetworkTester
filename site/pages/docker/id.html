Simulasi latensi jaringan di Docker dan Docker Compose

Tambahkan jeda, packet loss, atau batas kecepatan pada lalu lintas satu container, tanpa mengubah image-nya dan tanpa proxy di depannya. Image Bean Network Tester bergabung ke jaringan container itu, hanya mengubah yang masuk dan keluar darinya, lalu berhenti sendiri. Ini paket Linux, jadi masih eksperimental.

Memperlambat satu container

Jalankan image di samping container yang ingin diuji, di sini bernama api. Image ini butuh tiga capability di luar bawaan Docker, dan tidak butuh --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api memasukkan program ke jaringan container itu. Program ini menjangkau setiap program di jaringan itu, termasuk container lain yang dijalankan di dalamnya dengan cara yang sama, tetapi tidak pernah host atau container yang punya jaringan sendiri. --dst-ip membatasinya ke satu alamat. Tanpa opsi itu, setiap koneksi api melambat. Hasil ukur: pada --latency 100, ping container ke alamat itu naik dari 0,07 ms ke 200,8 ms, karena permintaan dan balasan sama-sama ditunda, sedangkan ping-nya ke alamat lain tetap di bawah 1 ms.

Semua pengaturan baris perintah berlaku di sini: --loss, --jitter, --down dan --up untuk batas kecepatan, preset atau satu skenario utuh. --duration mengakhiri sesi, begitu juga docker stop.

Docker Compose: simulasi latensi jaringan untuk satu layanan

Di Compose, ini adalah layanan tersendiri yang berbagi jaringan dengan layanan yang diperlambatnya:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Setiap layanan yang berbicara dengan api kini melihatnya 400 ms lebih jauh, dengan 2 % paket hilang. Hasil ukur dengan file ini: ping dari layanan lain naik dari 0,1 ms ke 401 ms. docker compose stop slow-network mengakhirinya, dan lalu lintas langsung normal kembali.

Satu program di dalam container

--target memilih program menurut namanya, seperti di desktop. Untuk melihat proses container lain, image juga butuh daftar prosesnya: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Tanpa --pid, program tidak menemukan proses itu dan menyebutkannya di log: Targeting: NO matching process has a connection open - traffic is NOT being impaired. Dalam hal itu tidak ada yang diperlambat.

Program di host Linux

Image ini juga bisa menjangkau program yang berjalan langsung di host, di luar container mana pun. Untuk itu ia butuh jaringan dan daftar proses host, serta dua opsi lagi: tanpa keduanya, membaca koneksi program di luar container ditolak.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Dengan --network host, sesi mengubah lalu lintas host itu sendiri, termasuk sesi ssh Anda, jadi persempit dengan --target, --dst-ip, atau --dst-port, dan perpendek dengan --duration. Hasil ukur di Ubuntu 26.04: permintaan program sasaran naik dari 3 ms ke sekitar 250 ms, sedangkan program lain tetap 11 ms. Di desktop, paket Linux melakukan hal yang sama tanpa Docker.

Docker Desktop di Windows dan macOS

Docker Desktop menjalankan container di mesin virtual Linux miliknya sendiri, dan di sana "host" berarti mesin itu. Image ini mengubah lalu lintas container, tidak pernah lalu lintas program Windows atau macOS. Untuk memperlambat program Windows, gunakan versi Windows dari Bean Network Tester.

Di Mac dengan Apple silicon dan mesin arm64 lain, Docker menjalankan image x86_64 ini lewat emulasi, dan penangkapan mungkin tidak berjalan di sana. Diukur di Mac M2 dengan emulasi QEMU dari Colima: image tetap berjalan dan --simulate berfungsi, tetapi penangkapan langsung berhenti dengan Function not implemented, sementara --doctor tetap menampilkan OK di setiap baris.

File, skenario, dan CI

  • File. Pasang sebuah folder di /work (-v "$PWD:/work") untuk --log-conns, --repro-out, file CSV, atau file --scenario. Program berjalan sebagai root di dalam image, jadi file yang ditulisnya milik root.
  • Kode keluar. Image berakhir dengan kode keluar milik program, jadi langkah CI bisa gagal karenanya. --fail-on-no-traffic menggagalkan proses yang tidak dilalui apa pun, tanda umum jaringan atau sasaran yang salah. docker stop berakhir dengan 143, berhenti dengan bersih.
  • Apa yang kurang. --doctor menyebutkannya, misalnya capability yang tidak diberikan saat container dijalankan.
  • Berhenti. Setelah docker stop, lalu lintas langsung normal. Setelah docker kill, lalu lintas mengalir lagi dalam sekitar 3 detik.

Image yang tersedia

Setiap rilis stabil mulai 1.1.0 menjadi image, dengan tag versinya dan latest. Kandidat rilis tidak mendapat image. Setiap image adalah paket Linux yang dirilis, tanpa perubahan, di atas Ubuntu 24.04, untuk x86_64. Sebelum diunggah, checksum dan asal build paket diperiksa, dan image dijalankan di kernel Linux seperti yang dijelaskan halaman ini. Untuk memeriksa image yang Anda tarik:
