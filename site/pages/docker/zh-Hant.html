在 Docker 和 Docker Compose 中模擬網路延遲

為單一容器的流量加上延遲、封包遺失或限速，不必修改它的映像檔，也不必在它前面放代理。Bean Network Tester 映像檔會加入那個容器的網路，只改變進出它的流量，時間到了就自行停止。這就是 Linux 版，因此仍屬實驗性質。

讓一個容器變慢

在要測試的容器旁邊啟動映像檔，這裡的容器名為 api。它在 Docker 預設權限之外還需要三項能力，不需要 --privileged：

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api 讓程式進入那個容器的網路，其他容器和主機都不受影響。--dst-ip 把範圍縮小到一個位址，不加它則 api 的每個連線都會變慢。實測：在 --latency 100 下，容器 ping 該位址從 0.07 ms 升到 200.8 ms，因為請求和回覆都會延遲；它 ping 另一個位址仍低於 1 ms。

命令列的每個設定在這裡都能用：--loss、--jitter、用於限速的 --down 和 --up，以及預設組或整個情境。--duration 會結束工作階段，docker stop 也會。

Docker Compose：為一個服務模擬網路延遲

在 Compose 中，它是一個獨立的服務，與它要減速的服務共用網路：

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

現在每個與 api 通訊的服務都會看到它遠了 400 ms，並遺失 2% 的封包。用這個檔案實測：從另一個服務 ping 它，從 0.1 ms 升到 401 ms。docker compose stop slow-network 結束工作階段，流量立即恢復正常。

容器裡的一個程式

--target 依名稱選擇程式，和在桌面上一樣。要看到另一個容器的處理程序，映像檔還需要它的處理程序清單：--pid container:api。

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

沒有 --pid 時，程式找不到這個處理程序，並在記錄中寫明：Targeting: NO matching process has a connection open - traffic is NOT being impaired. 這種情況下什麼都不會變慢。

Linux 主機上的程式

映像檔也能作用於直接在主機上執行、不在任何容器中的程式。這需要主機的網路和處理程序清單，再加兩個選項：缺少其中任何一個，讀取容器外程式的連線都會被拒絕。

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

使用 --network host 時，工作階段會改變主機本身的流量，包括你的 ssh 工作階段，所以要用 --target、--dst-ip 或 --dst-port 縮小範圍，並用 --duration 限制時長。在 Ubuntu 26.04 上實測：目標程式的請求從 3 ms 變成約 250 ms，另一個程式的請求仍為 11 ms。在桌面電腦上，Linux 套件不用 Docker 也能做到同樣的事。

Windows 和 macOS 上的 Docker Desktop

Docker Desktop 在自己的 Linux 虛擬機器中執行容器，在那裡「主機」指的就是這台虛擬機器。映像檔改變的是容器的流量，永遠不會改變 Windows 或 macOS 程式的流量。要讓 Windows 程式變慢，請使用 Bean Network Tester 的 Windows 版。

在 Apple 晶片的 Mac 以及其他 arm64 機器上，Docker 以模擬方式執行這個 x86_64 映像檔，而模擬環境中沒有核心的 BPF 呼叫。映像檔能啟動，--simulate 也能用，但擷取會立即以 Function not implemented 停止。這是在使用 Colima QEMU 模擬的 M2 Mac 上測得的，當時 --doctor 仍然每一行都回報 OK。

檔案、情境和 CI

  • 檔案。把一個資料夾掛載到 /work（-v "$PWD:/work"），用於 --log-conns、--repro-out、CSV 檔或 --scenario 檔案。程式在映像檔中以 root 執行，所以它寫出的檔案屬於 root。
  • 結束代碼。映像檔以程式本身的結束代碼結束，所以 CI 步驟可以據此判定失敗。--fail-on-no-traffic 會讓一次沒有任何流量通過的執行失敗，這通常代表網路或目標選錯了。docker stop 以 143 結束，表示正常停止。
  • 缺少什麼。--doctor 會指出來，例如啟動容器時沒有給的某項能力。
  • 停止。docker stop 之後流量立即恢復正常。docker kill 之後約 3 秒內恢復。

有哪些映像檔

從 1.1.0 起，每個穩定版本都有一個映像檔，標籤為版本號和 latest。候選版本（RC）沒有映像檔。每個映像檔都是已發布的 Linux 套件，原樣放在 Ubuntu 24.04 上，適用於 x86_64。推送之前，會先檢查套件的總和檢查碼與建置來源，並依本頁描述的方式在 Linux 核心上執行映像檔。檢查你拉取的映像檔：

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
