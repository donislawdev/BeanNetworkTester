Netwerklatentie simuleren in Docker en Docker Compose

Voeg vertraging, pakketverlies of een snelheidslimiet toe aan het verkeer van één container, zonder zijn image te veranderen en zonder proxy ervoor. De image van Bean Network Tester voegt zich bij het netwerk van die container, verandert alleen wat erin en eruit gaat en stopt vanzelf. Het is het Linux-pakket, dus experimenteel.

Eén container vertragen

Start de image naast de container die u wilt testen, hier een container met de naam api. Hij heeft drie capabilities nodig bovenop de standaard van Docker, en geen --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api zet het programma in het netwerk van die container. Het bereikt elk programma in dat netwerk, ook een andere container die er op dezelfde manier in is gestart, maar nooit de host of containers met een eigen netwerk. --dst-ip beperkt het tot één adres. Zonder die optie wordt elke verbinding van api trager. Gemeten: bij --latency 100 steeg de ping van de container naar dat adres van 0,07 ms naar 200,8 ms, omdat zowel het verzoek als het antwoord vertraagd wordt, en de ping naar een ander adres bleef onder 1 ms.

Elke instelling van de opdrachtregel werkt hier: --loss, --jitter, --down en --up voor een snelheidslimiet, een preset of een heel scenario. --duration beëindigt de sessie, en docker stop ook.

Docker Compose: netwerklatentie simuleren voor een service

In Compose is hetzelfde een eigen service die het netwerk deelt met de service die hij vertraagt:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Elke service die met api praat, ziet hem nu 400 ms verder weg, met 2 % van de pakketten kwijt. Gemeten met dit bestand: de ping vanuit een andere service steeg van 0,1 ms naar 401 ms. docker compose stop slow-network beëindigt het, en het verkeer is meteen weer normaal.

Eén programma in een container

--target kiest een programma op naam, zoals op een desktop. Om de processen van een andere container te zien, heeft de image ook de proceslijst daarvan nodig: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Zonder --pid vindt het programma zo'n proces niet en zegt het dat in zijn log: Targeting: NO matching process has a connection open - traffic is NOT being impaired. Dan wordt er niets vertraagd.

Een programma op de Linux-host

De image kan ook een programma bereiken dat op de host zelf draait, buiten elke container. Daarvoor zijn het netwerk en de proceslijst van de host nodig, plus nog twee opties: zonder beide wordt het lezen van de verbindingen van een programma buiten de container geweigerd.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Met --network host verandert de sessie het verkeer van de host zelf, uw ssh-sessie inbegrepen, dus houd hem smal met --target, --dst-ip of --dst-port, en kort met --duration. Gemeten op Ubuntu 26.04: de verzoeken van het gekozen programma gingen van 3 ms naar ongeveer 250 ms, die van een ander programma bleven op 11 ms. Op een desktop doet het Linux-pakket hetzelfde zonder Docker.

Docker Desktop op Windows en macOS

Docker Desktop draait containers in een eigen virtuele Linux-machine, en daar betekent "host" die machine. De image verandert het verkeer van containers, nooit dat van Windows- of macOS-programma's. Om een Windows-programma te vertragen, gebruikt u de Windows-versie van Bean Network Tester.

Op een Mac met Apple silicon en op andere arm64-machines draait Docker deze x86_64-image via emulatie, en daar werkt een vastlegging misschien niet. Gemeten op een M2-Mac met de QEMU-emulatie van Colima: de image start en --simulate werkt, maar een vastlegging stopt meteen met Function not implemented, terwijl --doctor toch op elke regel OK meldt.

Bestanden, scenario's en CI

  • Bestanden. Koppel een map aan /work (-v "$PWD:/work") voor --log-conns, --repro-out, CSV-bestanden of een --scenario-bestand. Het programma draait in de image als root, dus de bestanden die het schrijft zijn van root.
  • Afsluitcodes. De image eindigt met de eigen afsluitcodes van het programma, zodat een CI-stap erop kan falen. --fail-on-no-traffic laat een run falen waar niets doorheen ging, meestal het teken van een verkeerd netwerk of doel. docker stop eindigt met 143, een nette stop.
  • Wat ontbreekt. --doctor noemt het, bijvoorbeeld een capability zonder welke de container gestart is.
  • Stoppen. Na docker stop is het verkeer meteen normaal. Na docker kill stroomt het binnen ongeveer 3 seconden weer.

Welke images er zijn

Elke stabiele release vanaf 1.1.0 is een image, getagd met zijn versie en latest. Release candidates krijgen er geen. Elke image is het gepubliceerde Linux-pakket, ongewijzigd, op Ubuntu 24.04, voor x86_64. Voordat hij gepusht wordt, worden de checksum en de build-herkomst van het pakket gecontroleerd, en draait de image op een Linux-kernel zoals deze pagina beschrijft. Zo controleert u een image die u hebt opgehaald:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
