Docker और Docker Compose में नेटवर्क लेटेंसी सिमुलेट करें

किसी एक कंटेनर के ट्रैफ़िक में देरी, पैकेट लॉस या स्पीड लिमिट जोड़ें, उसकी इमेज बदले बिना और उसके आगे कोई प्रॉक्सी लगाए बिना। Bean Network Tester की इमेज उस कंटेनर के नेटवर्क में जुड़ती है, सिर्फ़ वही बदलती है जो उसमें आता-जाता है, और अपने-आप रुक जाती है। यह Linux वर्शन है, इसलिए प्रायोगिक है।

एक कंटेनर को धीमा करें

जिस कंटेनर को टेस्ट करना है, उसके बगल में इमेज चलाएँ, यहाँ उसका नाम api है। इसे Docker की डिफ़ॉल्ट क्षमताओं के अलावा तीन और क्षमताएँ चाहिए, और --privileged नहीं चाहिए:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api प्रोग्राम को उस कंटेनर के नेटवर्क में रखता है, इसलिए दूसरे कंटेनर और होस्ट अछूते रहते हैं। --dst-ip असर को एक पते तक सीमित करता है। इसके बिना api का हर कनेक्शन धीमा होता है। मापा गया: --latency 100 पर उस पते तक कंटेनर का पिंग 0.07 ms से बढ़कर 200.8 ms हो गया, क्योंकि अनुरोध और जवाब दोनों में देरी होती है, और किसी दूसरे पते तक उसका पिंग 1 ms से कम रहा।

कमांड लाइन की हर सेटिंग यहाँ काम करती है: --loss, --jitter, स्पीड लिमिट के लिए --down और --up, एक प्रीसेट या पूरा सिनेरियो। सत्र --duration से खत्म होता है, और docker stop से भी।

Docker Compose: किसी सर्विस के लिए नेटवर्क लेटेंसी सिमुलेट करें

Compose में यही एक अलग सर्विस है, जो उस सर्विस के साथ नेटवर्क साझा करती है जिसे वह धीमा करती है:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

अब api से बात करने वाली हर सर्विस को वह 400 ms दूर दिखती है, और 2% पैकेट खो जाते हैं। इस फ़ाइल से मापा गया: दूसरी सर्विस से पिंग 0.1 ms से बढ़कर 401 ms हो गया। docker compose stop slow-network इसे खत्म करता है, और ट्रैफ़िक तुरंत सामान्य हो जाता है।

कंटेनर के अंदर एक प्रोग्राम

--target प्रोग्राम को नाम से चुनता है, जैसे डेस्कटॉप पर। किसी दूसरे कंटेनर की प्रोसेस देखने के लिए इमेज को उसकी प्रोसेस सूची भी चाहिए: --pid container:api।

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

--pid के बिना प्रोग्राम को ऐसी कोई प्रोसेस नहीं मिलती, और वह अपने लॉग में यही कहता है: Targeting: NO matching process has a connection open - traffic is NOT being impaired. उस स्थिति में कुछ भी धीमा नहीं होता।

Linux होस्ट पर चल रहा प्रोग्राम

इमेज उस प्रोग्राम तक भी पहुँच सकती है जो किसी कंटेनर में नहीं, सीधे होस्ट पर चलता है। इसके लिए होस्ट का नेटवर्क और प्रोसेस सूची चाहिए, और दो और विकल्प: दोनों के बिना कंटेनर के बाहर के प्रोग्राम के कनेक्शन पढ़ने से मना कर दिया जाता है।

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

--network host के साथ सत्र होस्ट का अपना ट्रैफ़िक बदलता है, आपके ssh सत्र समेत, इसलिए इसे --target, --dst-ip या --dst-port से सीमित और --duration से छोटा रखें। Ubuntu 26.04 पर मापा गया: चुने गए प्रोग्राम के अनुरोध 3 ms से लगभग 250 ms हो गए, और दूसरे प्रोग्राम के 11 ms पर रहे। डेस्कटॉप पर यही काम Docker के बिना Linux पैकेज करता है।

Windows और macOS पर Docker Desktop

Docker Desktop कंटेनरों को अपनी Linux वर्चुअल मशीन में चलाता है, और वहाँ "होस्ट" का मतलब वही मशीन है। इमेज कंटेनरों का ट्रैफ़िक बदलती है, Windows या macOS के प्रोग्रामों का कभी नहीं। किसी Windows प्रोग्राम को धीमा करने के लिए Bean Network Tester का Windows वर्शन इस्तेमाल करें।

Apple silicon वाले Mac और दूसरी arm64 मशीनों पर Docker इस x86_64 इमेज को इम्यूलेशन में चलाता है, और वहाँ कर्नेल की BPF कॉल उपलब्ध नहीं होतीं। इमेज शुरू होती है और --simulate काम करता है, लेकिन कैप्चर तुरंत Function not implemented के साथ रुक जाता है। Colima के QEMU इम्यूलेशन वाले M2 Mac पर मापा गया, जहाँ --doctor फिर भी हर पंक्ति में OK दिखा रहा था।

फ़ाइलें, सिनेरियो और CI

  • फ़ाइलें। --log-conns, --repro-out, CSV फ़ाइलों या --scenario फ़ाइल के लिए एक फ़ोल्डर /work पर माउंट करें (-v "$PWD:/work")। प्रोग्राम इमेज में root के रूप में चलता है, इसलिए वह जो फ़ाइलें लिखता है वे root की होती हैं।
  • एग्ज़िट कोड। इमेज प्रोग्राम के अपने एग्ज़िट कोड के साथ खत्म होती है, इसलिए CI का कोई चरण उन पर फ़ेल हो सकता है। --fail-on-no-traffic उस रन को फ़ेल करता है जिससे कुछ भी नहीं गुज़रा, जो आमतौर पर गलत नेटवर्क या गलत लक्ष्य का संकेत है। docker stop 143 के साथ खत्म होता है, यानी साफ़ तरीके से रुकना।
  • क्या कमी है। --doctor बताता है, जैसे कोई क्षमता जिसके बिना कंटेनर शुरू किया गया।
  • रोकना। docker stop के बाद ट्रैफ़िक तुरंत सामान्य हो जाता है। docker kill के बाद यह लगभग 3 सेकंड में फिर से चलने लगता है।
