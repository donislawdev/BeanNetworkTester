محاكاة تأخير الشبكة في Docker وDocker Compose

أضف تأخيرًا أو فقدانًا للحزم أو حدًا للسرعة إلى حركة مرور حاوية واحدة، دون تغيير صورتها ودون وكيل أمامها. تنضم صورة Bean Network Tester إلى شبكة تلك الحاوية، وتغيّر فقط ما يدخل إليها ويخرج منها، ثم تتوقف من تلقاء نفسها. إنها حزمة Linux، لذا فهي تجريبية.

إبطاء حاوية واحدة

شغّل الصورة بجوار الحاوية التي تريد اختبارها، وهي هنا حاوية اسمها api. تحتاج الصورة إلى ثلاث قدرات إضافة إلى قدرات Docker الافتراضية، ولا تحتاج إلى --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

يضع --network container:api البرنامج داخل شبكة تلك الحاوية. وهو يصل إلى كل برنامج في تلك الشبكة، بما في ذلك أي حاوية أخرى شُغّلت فيها بالطريقة نفسها، ولا يصل أبدًا إلى المضيف ولا إلى الحاويات التي لها شبكتها الخاصة. ويحصر --dst-ip التأثير في عنوان واحد. ومن دونه يتباطأ كل اتصال لـ api. القياس: عند --latency 100 ارتفع ping الحاوية إلى ذلك العنوان من 0.07 ms إلى 200.8 ms، لأن الطلب والرد يتأخران كلاهما، بينما بقي ping إلى عنوان آخر أقل من 1 ms.

كل إعداد في سطر الأوامر يعمل هنا: --loss و--jitter و--down و--up لحد السرعة، وإعداد مسبق أو سيناريو كامل. تنتهي الجلسة بـ --duration، وكذلك بـ docker stop.

Docker Compose: محاكاة تأخير الشبكة لخدمة

في Compose يكون الأمر نفسه خدمة مستقلة تتشارك الشبكة مع الخدمة التي تبطئها:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

كل خدمة تتحدث إلى api تراها الآن أبعد بـ 400 ms، مع فقدان 2% من الحزم. القياس بهذا الملف: ارتفع ping من خدمة أخرى من 0.1 ms إلى 401 ms. ينهيها docker compose stop slow-network، وتعود الحركة إلى طبيعتها فورًا.

برنامج واحد داخل حاوية

يختار --target برنامجًا باسمه، كما على سطح المكتب. ولكي ترى الصورة عمليات حاوية أخرى، تحتاج أيضًا إلى قائمة عملياتها: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

من دون --pid لا يجد البرنامج تلك العملية ويقول ذلك في سجله: Targeting: NO matching process has a connection open - traffic is NOT being impaired. وفي هذه الحالة لا يتباطأ شيء.

برنامج على مضيف Linux

يمكن للصورة أيضًا أن تصل إلى برنامج يعمل على المضيف نفسه، خارج أي حاوية. وتحتاج لذلك إلى شبكة المضيف وقائمة عملياته، وإلى خيارين آخرين: من دونهما معًا تُرفض قراءة اتصالات برنامج خارج الحاوية.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

مع --network host تغيّر الجلسة حركة المضيف نفسه، بما فيها جلسة ssh الخاصة بك، لذا أبقها ضيقة بـ --target أو --dst-ip أو --dst-port، وقصيرة بـ --duration. القياس على Ubuntu 26.04: ارتفعت طلبات البرنامج المستهدف من 3 ms إلى نحو 250 ms، وبقيت طلبات برنامج آخر عند 11 ms. وعلى سطح المكتب تفعل حزمة Linux الشيء نفسه دون Docker.

Docker Desktop على Windows وmacOS

يشغّل Docker Desktop الحاويات في آلة Linux افتراضية خاصة به، وهناك يعني "المضيف" تلك الآلة. تغيّر الصورة حركة الحاويات، ولا تغيّر أبدًا حركة برامج Windows أو macOS. لإبطاء برنامج على Windows، استخدم نسخة Windows من Bean Network Tester.

على جهاز Mac بمعالج Apple silicon وعلى أجهزة arm64 الأخرى، يشغّل Docker صورة x86_64 هذه عبر المحاكاة، وقد لا يعمل الالتقاط هناك. القياس على جهاز Mac M2 مع محاكاة QEMU في Colima: تبدأ الصورة ويعمل --simulate، لكن الالتقاط يتوقف فورًا مع Function not implemented، بينما يُظهر --doctor مع ذلك OK في كل سطر.

الملفات والسيناريوهات وCI

  • الملفات. اربط مجلدًا على /work (-v "$PWD:/work") من أجل --log-conns أو --repro-out أو ملفات CSV أو ملف --scenario. يعمل البرنامج داخل الصورة بصلاحيات root، لذا تعود ملكية الملفات التي يكتبها إلى root.
  • رموز الخروج. تنتهي الصورة بـ رموز الخروج الخاصة بالبرنامج، فيمكن لخطوة CI أن تفشل بناءً عليها. يجعل --fail-on-no-traffic التشغيل الذي لم يمر عبره شيء فاشلًا، وهي العلامة المعتادة على شبكة أو هدف خاطئ. وينتهي docker stop بالرمز 143، أي توقف نظيف.
  • ما الذي ينقص. يذكره --doctor، مثل قدرة شُغّلت الحاوية من دونها.
  • الإيقاف. بعد docker stop تعود الحركة إلى طبيعتها فورًا. وبعد docker kill تتدفق مجددًا خلال نحو 3 ثوانٍ.

ما الصور المتوفرة

كل إصدار مستقر بدءًا من 1.1.0 هو صورة، موسومة برقم إصدارها وبـ latest. ولا تحصل الإصدارات المرشحة على صورة. كل صورة هي حزمة Linux المنشورة دون تغيير، على Ubuntu 24.04، لمعمارية x86_64. قبل الرفع يُتحقق من المجموع الاختباري للحزمة ومن مصدر بنائها، وتُشغّل الصورة على نواة Linux كما تصف هذه الصفحة. للتحقق من صورة سحبتها:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
