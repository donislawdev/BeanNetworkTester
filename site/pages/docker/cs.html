Simulace latence sítě v Dockeru a Docker Compose

Přidejte zpoždění, ztrátu paketů nebo limit rychlosti provozu jednoho kontejneru, bez změny jeho obrazu a bez proxy před ním. Obraz Bean Network Tester se připojí do sítě toho kontejneru, mění jen to, co do něj vchází a z něj odchází, a sám skončí. Je to verze pro Linux, takže je experimentální.

Zpomalení jednoho kontejneru

Spusťte obraz vedle kontejneru, který chcete testovat, zde jednoho s názvem api. Potřebuje tři schopnosti navíc k výchozím schopnostem Dockeru a nepotřebuje --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api vloží program do sítě toho kontejneru, takže ostatní kontejnery ani hostitel nejsou dotčeny. --dst-ip ho omezí na jednu adresu. Bez této volby se zpomalí každé spojení api. Změřeno: při --latency 100 vzrostl ping kontejneru na tu adresu z 0,07 ms na 200,8 ms, protože se zpožďuje požadavek i odpověď, a jeho ping na jinou adresu zůstal pod 1 ms.

Funguje tu každé nastavení příkazového řádku: --loss, --jitter, --down a --up pro limit rychlosti, předvolba nebo celý scénář. Relaci ukončí --duration a také docker stop.

Docker Compose: simulace latence sítě pro službu

V Compose je to samostatná služba, která sdílí síť se službou, kterou zpomaluje:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Každá služba, která mluví s api, ji teď vidí o 400 ms dál a ztrácí 2 % paketů. Změřeno s tímto souborem: ping z jiné služby vzrostl z 0,1 ms na 401 ms. docker compose stop slow-network relaci ukončí a provoz je hned normální.

Jeden program v kontejneru

--target vybírá program podle názvu, stejně jako na desktopu. Aby obraz viděl procesy jiného kontejneru, potřebuje i jeho seznam procesů: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Bez --pid program takový proces nenajde a řekne to ve svém logu: Targeting: NO matching process has a connection open - traffic is NOT being impaired. V tom případě se nic nezpomalí.

Program na hostiteli s Linuxem

Obraz dosáhne i na program, který běží přímo na hostiteli, mimo jakýkoli kontejner. Potřebuje k tomu síť a seznam procesů hostitele a ještě dvě volby: bez obou je čtení spojení programu mimo kontejner odmítnuto.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

S --network host relace mění provoz samotného hostitele, včetně vaší relace ssh, takže ji držte úzkou pomocí --target, --dst-ip nebo --dst-port a krátkou pomocí --duration. Změřeno na Ubuntu 26.04: požadavky vybraného programu se prodloužily z 3 ms na asi 250 ms a jiného programu zůstaly na 11 ms. Na desktopu totéž bez Dockeru udělá balíček pro Linux.

Docker Desktop ve Windows a macOS

Docker Desktop spouští kontejnery ve vlastním virtuálním stroji s Linuxem a tam „hostitel“ znamená tento stroj. Obraz mění provoz kontejnerů, nikdy ne provoz programů Windows nebo macOS. Chcete-li zpomalit program ve Windows, použijte verzi Bean Network Tester pro Windows.

Na Macu s Apple silicon a na dalších strojích arm64 spouští Docker tento obraz x86_64 v emulaci, a tam volání BPF jádra nejsou k dispozici. Obraz se spustí a --simulate funguje, ale zachytávání hned skončí chybou Function not implemented. Změřeno na Macu M2 s emulací QEMU v Colima, kde --doctor přesto hlásil OK v každém řádku.

Soubory, scénáře a CI

  • Soubory. Připojte složku do /work (-v "$PWD:/work") pro --log-conns, --repro-out, soubory CSV nebo soubor --scenario. Program v obrazu běží jako root, takže soubory, které zapíše, patří rootovi.
  • Návratové kódy. Obraz končí návratovými kódy samotného programu, takže krok CI na nich může selhat. --fail-on-no-traffic označí za neúspěch běh, kterým nic neprošlo, což obvykle znamená špatnou síť nebo cíl. docker stop končí kódem 143, čistým zastavením.
  • Co chybí. Řekne to --doctor, třeba schopnost, bez které byl kontejner spuštěn.
  • Zastavení. Po docker stop je provoz hned normální. Po docker kill znovu teče přibližně do 3 sekund.
