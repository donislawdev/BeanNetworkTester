Netzwerklatenz in Docker und Docker Compose simulieren

Fügen Sie dem Verkehr eines einzelnen Containers Verzögerung, Paketverlust oder ein Tempolimit hinzu, ohne sein Image zu ändern und ohne einen Proxy davor. Das Image von Bean Network Tester tritt dem Netzwerk dieses Containers bei, ändert nur, was hinein- und herausgeht, und hört von selbst auf. Es ist das Linux-Paket und damit experimentell.

Einen Container ausbremsen

Starten Sie das Image neben dem Container, den Sie testen wollen, hier einer namens api. Es braucht drei Capabilities zusätzlich zu Dockers Standard und kein --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api setzt das Programm in das Netzwerk dieses Containers. Es erreicht jedes Programm in diesem Netzwerk, auch einen anderen Container, der genauso darin gestartet wurde, aber nie den Host oder Container mit eigenem Netzwerk. --dst-ip beschränkt es auf eine Adresse. Ohne die Option wird jede Verbindung von api langsamer. Gemessen: Bei --latency 100 stieg der Ping des Containers zu dieser Adresse von 0,07 ms auf 200,8 ms, weil Anfrage und Antwort beide verzögert werden, und sein Ping zu einer anderen Adresse blieb unter 1 ms.

Jede Einstellung der Befehlszeile funktioniert hier: --loss, --jitter, --down und --up für ein Tempolimit, ein Preset oder ein ganzes Szenario. --duration beendet die Sitzung, docker stop ebenso.

Docker Compose: Netzwerklatenz für einen Dienst simulieren

In Compose ist dasselbe ein eigener Dienst, der sich das Netzwerk mit dem Dienst teilt, den er ausbremst:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Jeder Dienst, der mit api spricht, sieht ihn jetzt 400 ms weiter entfernt und verliert 2 % der Pakete. Mit dieser Datei gemessen: Der Ping von einem anderen Dienst stieg von 0,1 ms auf 401 ms. docker compose stop slow-network beendet es, und der Verkehr ist sofort wieder normal.

Ein Programm in einem Container

--target wählt ein Programm nach seinem Namen, wie auf einem Desktop. Um die Prozesse eines anderen Containers zu sehen, braucht das Image auch dessen Prozessliste: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Ohne --pid findet das Programm keinen solchen Prozess und sagt das in seinem Log: Targeting: NO matching process has a connection open - traffic is NOT being impaired. Dann wird nichts verlangsamt.

Ein Programm auf dem Linux-Host

Das Image erreicht auch ein Programm, das direkt auf dem Host läuft, außerhalb jedes Containers. Dazu braucht es das Netzwerk und die Prozessliste des Hosts und zwei weitere Optionen: Ohne beide wird das Lesen der Verbindungen eines Programms außerhalb des Containers verweigert.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Mit --network host ändert die Sitzung den Verkehr des Hosts selbst, Ihre ssh-Sitzung eingeschlossen. Halten Sie sie also mit --target, --dst-ip oder --dst-port eng und mit --duration kurz. Gemessen unter Ubuntu 26.04: Die Anfragen des Zielprogramms stiegen von 3 ms auf etwa 250 ms, die eines anderen Programms blieben bei 11 ms. Auf einem Desktop macht das Linux-Paket dasselbe ohne Docker.

Docker Desktop unter Windows und macOS

Docker Desktop führt Container in einer eigenen virtuellen Linux-Maschine aus, und dort bedeutet „Host“ diese Maschine. Das Image ändert den Verkehr von Containern, nie den von Windows- oder macOS-Programmen. Um ein Windows-Programm auszubremsen, nutzen Sie die Windows-Version von Bean Network Tester.

Auf einem Mac mit Apple Silicon und auf anderen arm64-Rechnern führt Docker dieses x86_64-Image in einer Emulation aus, und eine Erfassung funktioniert dort womöglich nicht. Gemessen auf einem M2-Mac mit der QEMU-Emulation von Colima: Das Image startet und --simulate funktioniert, aber eine Erfassung bricht sofort mit Function not implemented ab, während --doctor trotzdem in jeder Zeile OK meldet.

Dateien, Szenarien und CI

  • Dateien. Binden Sie einen Ordner unter /work ein (-v "$PWD:/work") für --log-conns, --repro-out, CSV-Dateien oder eine --scenario-Datei. Das Programm läuft im Image als root, daher gehören die Dateien, die es schreibt, root.
  • Exit-Codes. Das Image endet mit den Exit-Codes des Programms, sodass ein CI-Schritt daran scheitern kann. --fail-on-no-traffic lässt einen Lauf scheitern, durch den nichts hindurchging, meist ein Zeichen für ein falsches Netzwerk oder Ziel. docker stop endet mit 143, einem sauberen Stopp.
  • Was fehlt. --doctor nennt es, etwa eine Capability, ohne die der Container gestartet wurde.
  • Beenden. Nach docker stop ist der Verkehr sofort normal. Nach docker kill fließt er innerhalb von etwa 3 Sekunden wieder.

Welche Images es gibt

Jede stabile Version ab 1.1.0 ist ein Image, markiert mit ihrer Version und latest. Release Candidates bekommen keins. Jedes ist das veröffentlichte Linux-Paket, unverändert, auf Ubuntu 24.04, für x86_64. Bevor es hochgeladen wird, werden die Prüfsumme und die Build-Herkunft des Pakets geprüft, und das Image wird auf einem Linux-Kernel so ausgeführt, wie diese Seite es beschreibt. So prüfen Sie ein geladenes Image:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
