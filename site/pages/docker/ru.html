Имитация задержки сети в Docker и Docker Compose

Добавьте задержку, потерю пакетов или ограничение скорости трафику одного контейнера, не меняя его образ и не ставя перед ним прокси. Образ Bean Network Tester подключается к сети этого контейнера, меняет только то, что в него входит и из него выходит, и сам останавливается. Это пакет для Linux, поэтому образ экспериментальный.

Замедлить один контейнер

Запустите образ рядом с контейнером, который хотите проверить, здесь он называется api. Образу нужны три возможности сверх стандартных возможностей Docker, а --privileged не нужен:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api помещает программу в сеть этого контейнера. Она действует на каждую программу в этой сети, в том числе на другой контейнер, запущенный в ней так же, но никогда на хост или контейнеры со своей сетью. --dst-ip сужает действие до одного адреса. Без этого параметра замедляется каждое соединение api. Измерено: при --latency 100 пинг контейнера до этого адреса вырос с 0,07 мс до 200,8 мс, потому что задерживаются и запрос, и ответ, а его пинг до другого адреса остался меньше 1 мс.

Здесь работает любой параметр командной строки: --loss, --jitter, --down и --up для ограничения скорости, пресет или целый сценарий. Сеанс завершает --duration, а также docker stop.

Docker Compose: задержка сети для сервиса

В Compose это отдельный сервис, который делит сеть с тем, который он замедляет:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Каждый сервис, который обращается к api, теперь видит его на 400 мс дальше и теряет 2 % пакетов. Измерено с этим файлом: пинг из другого сервиса вырос с 0,1 мс до 401 мс. docker compose stop slow-network завершает сеанс, и трафик сразу становится обычным.

Одна программа в контейнере

--target выбирает программу по имени, как на рабочем столе. Чтобы видеть процессы другого контейнера, образу нужен и его список процессов: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Без --pid программа не находит такой процесс и пишет об этом в журнале: Targeting: NO matching process has a connection open - traffic is NOT being impaired. В этом случае ничего не замедляется.

Программа на хосте Linux

Образ может достать и программу, которая работает на самом хосте, вне контейнеров. Для этого нужны сеть и список процессов хоста и ещё два параметра: без обоих чтение соединений программы вне контейнера запрещено.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

С --network host сеанс меняет трафик самого хоста, включая ваш сеанс ssh, поэтому сужайте его через --target, --dst-ip или --dst-port и ограничивайте по времени через --duration. Измерено в Ubuntu 26.04: запросы выбранной программы выросли с 3 мс примерно до 250 мс, а у другой программы остались на 11 мс. На настольном компьютере то же самое без Docker делает пакет для Linux.

Docker Desktop в Windows и macOS

Docker Desktop запускает контейнеры в собственной виртуальной машине Linux, и там «хост» означает эту машину. Образ меняет трафик контейнеров и никогда не меняет трафик программ Windows или macOS. Чтобы замедлить программу в Windows, используйте версию Bean Network Tester для Windows.

На Mac с Apple silicon и на других машинах arm64 Docker запускает этот образ x86_64 в эмуляции, и там перехват может не работать. Измерено на Mac M2 с эмуляцией QEMU в Colima: образ стартует, и --simulate работает, но перехват сразу останавливается с ошибкой Function not implemented, а --doctor при этом показывает OK в каждой строке.

Файлы, сценарии и CI

  • Файлы. Подключите папку в /work (-v "$PWD:/work") для --log-conns, --repro-out, файлов CSV или файла --scenario. Программа работает в образе от root, поэтому файлы, которые она пишет, принадлежат root.
  • Коды выхода. Образ завершается кодами выхода самой программы, поэтому шаг CI может по ним завершиться ошибкой. --fail-on-no-traffic считает неудачным прогон, через который ничего не прошло, обычно это признак неверной сети или цели. docker stop завершается кодом 143, то есть чистой остановкой.
  • Чего не хватает. Это называет --doctor, например возможность, без которой запустили контейнер.
  • Остановка. После docker stop трафик сразу становится обычным. После docker kill он снова идёт примерно через 3 секунды.

Какие есть образы

Каждый стабильный выпуск начиная с 1.1.0 становится образом с тегами своей версии и latest. У кандидатов в выпуск образа нет. Каждый образ - это опубликованный пакет для Linux без изменений, на Ubuntu 24.04, для x86_64. Перед отправкой проверяются контрольная сумма и происхождение сборки пакета, а сам образ запускается на ядре Linux так, как описано на этой странице. Чтобы проверить загруженный образ:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
