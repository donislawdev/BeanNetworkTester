Імітація затримки мережі в Docker і Docker Compose

Додайте затримку, втрату пакетів або обмеження швидкості трафіку одного контейнера, не змінюючи його образ і не ставлячи перед ним проксі. Образ Bean Network Tester приєднується до мережі цього контейнера, змінює лише те, що в нього входить і з нього виходить, і сам зупиняється. Це пакет для Linux, тому образ експериментальний.

Сповільнити один контейнер

Запустіть образ поруч із контейнером, який хочете перевірити, тут він називається api. Образу потрібні три можливості понад стандартні можливості Docker, а --privileged не потрібен:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api поміщає програму в мережу цього контейнера. Вона діє на кожну програму в цій мережі, зокрема на інший контейнер, запущений у ній так само, але ніколи на хост чи контейнери з власною мережею. --dst-ip звужує дію до однієї адреси. Без цього параметра сповільнюється кожне з'єднання api. Виміряно: за --latency 100 пінг контейнера до цієї адреси зріс з 0,07 мс до 200,8 мс, бо затримуються і запит, і відповідь, а його пінг до іншої адреси лишився меншим за 1 мс.

Тут працює будь-який параметр командного рядка: --loss, --jitter, --down і --up для обмеження швидкості, пресет або цілий сценарій. Сеанс завершує --duration, а також docker stop.

Docker Compose: затримка мережі для сервісу

У Compose це окремий сервіс, який ділить мережу з тим, який він сповільнює:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Кожен сервіс, який звертається до api, тепер бачить його на 400 мс далі й втрачає 2 % пакетів. Виміряно з цим файлом: пінг з іншого сервісу зріс з 0,1 мс до 401 мс. docker compose stop slow-network завершує сеанс, і трафік одразу стає звичайним.

Одна програма в контейнері

--target вибирає програму за назвою, як на робочому столі. Щоб бачити процеси іншого контейнера, образу потрібен і його список процесів: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Без --pid програма не знаходить такий процес і пише про це в журналі: Targeting: NO matching process has a connection open - traffic is NOT being impaired. У цьому разі нічого не сповільнюється.

Програма на хості з Linux

Образ може дістатися й до програми, яка працює на самому хості, поза контейнерами. Для цього потрібні мережа та список процесів хоста і ще два параметри: без обох читання з'єднань програми поза контейнером заборонене.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

З --network host сеанс змінює трафік самого хоста, разом із вашим сеансом ssh, тож звужуйте його через --target, --dst-ip або --dst-port і обмежуйте в часі через --duration. Виміряно в Ubuntu 26.04: запити вибраної програми зросли з 3 мс приблизно до 250 мс, а в іншої програми лишилися на 11 мс. На настільному комп'ютері те саме без Docker робить пакет для Linux.

Docker Desktop у Windows і macOS

Docker Desktop запускає контейнери у власній віртуальній машині Linux, і там «хост» означає цю машину. Образ змінює трафік контейнерів і ніколи не змінює трафік програм Windows або macOS. Щоб сповільнити програму у Windows, використовуйте версію Bean Network Tester для Windows.

На Mac з Apple silicon та на інших машинах arm64 Docker запускає цей образ x86_64 в емуляції, і там перехоплення може не працювати. Виміряно на Mac M2 з емуляцією QEMU в Colima: образ стартує, і --simulate працює, але перехоплення одразу зупиняється з помилкою Function not implemented, а --doctor при цьому показує OK у кожному рядку.

Файли, сценарії та CI

  • Файли. Підключіть теку в /work (-v "$PWD:/work") для --log-conns, --repro-out, файлів CSV або файлу --scenario. Програма працює в образі від root, тому файли, які вона записує, належать root.
  • Коди виходу. Образ завершується кодами виходу самої програми, тож крок CI може за ними завершитися помилкою. --fail-on-no-traffic вважає невдалим прогін, через який нічого не пройшло, зазвичай це ознака неправильної мережі чи цілі. docker stop завершується кодом 143, тобто чистою зупинкою.
  • Чого бракує. Це називає --doctor, наприклад можливість, без якої запустили контейнер.
  • Зупинка. Після docker stop трафік одразу стає звичайним. Після docker kill він знову йде приблизно за 3 секунди.

Які є образи

Кожен стабільний випуск починаючи з 1.1.0 стає образом із тегами своєї версії та latest. Кандидати у випуск образу не мають. Кожен образ - це опублікований пакет для Linux без змін, на Ubuntu 24.04, для x86_64. Перед надсиланням перевіряються контрольна сума та походження збірки пакета, а сам образ запускається на ядрі Linux так, як описано на цій сторінці. Щоб перевірити завантажений образ:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
