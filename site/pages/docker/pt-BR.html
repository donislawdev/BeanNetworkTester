Simular latência de rede no Docker e no Docker Compose

Adicione atraso, perda de pacotes ou um limite de velocidade ao tráfego de um único contêiner, sem mudar a imagem dele e sem um proxy na frente. A imagem do Bean Network Tester entra na rede desse contêiner, muda só o que entra e sai dele e para sozinha. É o pacote para Linux, portanto experimental.

Deixar um contêiner lento

Inicie a imagem ao lado do contêiner que você quer testar, aqui um chamado api. Ela precisa de três capacidades além das padrão do Docker, e não precisa de --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api coloca o programa na rede desse contêiner. Ele alcança todos os programas dessa rede, inclusive outro contêiner iniciado nela do mesmo jeito, e nunca o host nem os contêineres com rede própria. --dst-ip restringe a um endereço. Sem essa opção, toda conexão do api fica lenta. Medido: com --latency 100, o ping do contêiner para esse endereço subiu de 0,07 ms para 200,8 ms, porque a requisição e a resposta são atrasadas, e o ping dele para outro endereço ficou abaixo de 1 ms.

Qualquer configuração da linha de comando funciona aqui: --loss, --jitter, --down e --up para um limite de velocidade, um preset ou um cenário inteiro. --duration encerra a sessão, e docker stop também.

Docker Compose: simular latência de rede para um serviço

No Compose, é um serviço próprio que compartilha a rede do serviço que ele deixa lento:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Todo serviço que fala com o api agora o vê 400 ms mais longe, com 2 % dos pacotes perdidos. Medido com este arquivo: o ping a partir de outro serviço subiu de 0,1 ms para 401 ms. docker compose stop slow-network encerra, e o tráfego volta ao normal na hora.

Um programa dentro de um contêiner

--target escolhe um programa pelo nome, como num desktop. Para ver os processos de outro contêiner, a imagem também precisa da lista de processos dele: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Sem --pid, o programa não encontra esse processo e diz isso no log: Targeting: NO matching process has a connection open - traffic is NOT being impaired. Nesse caso nada fica lento.

Um programa no host Linux

A imagem também alcança um programa que roda no próprio host, fora de qualquer contêiner. Para isso ela precisa da rede e da lista de processos do host, e de mais duas opções: sem as duas, a leitura das conexões de um programa fora do contêiner é recusada.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Com --network host, a sessão muda o tráfego do próprio host, inclusive sua sessão ssh, então mantenha-a restrita com --target, --dst-ip ou --dst-port, e curta com --duration. Medido no Ubuntu 26.04: as requisições do programa escolhido passaram de 3 ms para cerca de 250 ms, e as de outro programa ficaram em 11 ms. Num desktop, o pacote para Linux faz o mesmo sem Docker.

Docker Desktop no Windows e no macOS

O Docker Desktop roda os contêineres numa máquina virtual Linux própria, e lá "host" significa essa máquina. A imagem muda o tráfego dos contêineres, nunca o dos programas do Windows ou do macOS. Para deixar lento um programa do Windows, use a versão para Windows do Bean Network Tester.

Num Mac com Apple silicon e em outras máquinas arm64, o Docker roda esta imagem x86_64 com emulação, e ali uma captura pode não funcionar. Medido num Mac M2 com a emulação QEMU do Colima: a imagem inicia e --simulate funciona, mas uma captura para na hora com Function not implemented, enquanto --doctor ainda assim mostra OK em todas as linhas.

Arquivos, cenários e CI

  • Arquivos. Monte uma pasta em /work (-v "$PWD:/work") para --log-conns, --repro-out, arquivos CSV ou um arquivo de --scenario. O programa roda como root na imagem, então os arquivos que ele grava pertencem ao root.
  • Códigos de saída. A imagem termina com os códigos de saída do próprio programa, então uma etapa de CI pode falhar com eles. --fail-on-no-traffic faz falhar uma execução pela qual nada passou, o sinal comum de rede ou alvo errados. docker stop termina com 143, uma parada limpa.
  • O que falta. --doctor diz, por exemplo uma capacidade sem a qual o contêiner foi iniciado.
  • Parada. Depois de docker stop, o tráfego volta ao normal na hora. Depois de docker kill, volta a fluir em cerca de 3 segundos.

Quais imagens existem

Toda versão estável a partir da 1.1.0 é uma imagem, marcada com a sua versão e latest. Versões candidatas não têm. Cada uma é o pacote para Linux publicado, sem mudanças, sobre o Ubuntu 24.04, para x86_64. Antes do envio, a soma de verificação e a procedência do pacote são conferidas, e a imagem é executada num kernel Linux do jeito que esta página descreve. Para conferir uma imagem baixada:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
