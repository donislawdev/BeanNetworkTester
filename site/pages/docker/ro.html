Simularea latenței rețelei în Docker și Docker Compose

Adăugați întârziere, pierderi de pachete sau o limită de viteză traficului unui singur container, fără să-i schimbați imaginea și fără un proxy în fața lui. Imaginea Bean Network Tester intră în rețeaua acelui container, schimbă doar ce intră și iese din el și se oprește singură. Este versiunea pentru Linux, deci experimentală.

Încetinirea unui container

Porniți imaginea lângă containerul pe care vreți să-l testați, aici unul numit api. Are nevoie de trei capabilități în plus față de cele implicite ale Docker și nu are nevoie de --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api pune programul în rețeaua acelui container, așa că celelalte containere și gazda rămân neatinse. --dst-ip îl restrânge la o adresă. Fără această opțiune, fiecare conexiune a lui api încetinește. Măsurat: la --latency 100, ping-ul containerului spre acea adresă a crescut de la 0,07 ms la 200,8 ms, pentru că sunt întârziate și cererea, și răspunsul, iar ping-ul lui spre altă adresă a rămas sub 1 ms.

Aici funcționează orice setare a liniei de comandă: --loss, --jitter, --down și --up pentru o limită de viteză, un preset sau un scenariu întreg. Sesiunea se încheie cu --duration, dar și cu docker stop.

Docker Compose: simularea latenței rețelei pentru un serviciu

În Compose, același lucru este un serviciu separat, care împarte rețeaua cu serviciul pe care îl încetinește:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Fiecare serviciu care vorbește cu api îl vede acum cu 400 ms mai departe, cu 2 % din pachete pierdute. Măsurat cu acest fișier: ping-ul dintr-un alt serviciu a crescut de la 0,1 ms la 401 ms. docker compose stop slow-network îl oprește, iar traficul revine imediat la normal.

Un program dintr-un container

--target alege un program după nume, ca pe un desktop. Pentru a vedea procesele altui container, imaginea are nevoie și de lista lui de procese: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Fără --pid, programul nu găsește acel proces și spune asta în jurnal: Targeting: NO matching process has a connection open - traffic is NOT being impaired. În acest caz nu încetinește nimic.

Un program pe gazda Linux

Imaginea poate ajunge și la un program care rulează direct pe gazdă, în afara oricărui container. Are nevoie atunci de rețeaua și lista de procese ale gazdei și de încă două opțiuni: fără amândouă, citirea conexiunilor unui program din afara containerului este refuzată.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Cu --network host, sesiunea schimbă traficul gazdei înseși, inclusiv sesiunea ssh, așa că păstrați-o îngustă cu --target, --dst-ip sau --dst-port și scurtă cu --duration. Măsurat pe Ubuntu 26.04: cererile programului ales au crescut de la 3 ms la aproximativ 250 ms, iar ale altui program au rămas la 11 ms. Pe un desktop, pachetul pentru Linux face același lucru fără Docker.

Docker Desktop pe Windows și macOS

Docker Desktop rulează containerele într-o mașină virtuală Linux proprie, iar acolo „gazda” înseamnă acea mașină. Imaginea schimbă traficul containerelor, niciodată pe cel al programelor Windows sau macOS. Pentru a încetini un program Windows, folosiți versiunea pentru Windows a Bean Network Tester.

Pe un Mac cu Apple silicon și pe alte mașini arm64, Docker rulează această imagine x86_64 prin emulare, iar acolo apelurile BPF ale nucleului nu există. Imaginea pornește și --simulate funcționează, dar o captură se oprește imediat cu Function not implemented. Măsurat pe un Mac M2 cu emularea QEMU din Colima, unde --doctor arăta totuși OK pe fiecare rând.

Fișiere, scenarii și CI

  • Fișiere. Montați un dosar în /work (-v "$PWD:/work") pentru --log-conns, --repro-out, fișiere CSV sau un fișier --scenario. Programul rulează ca root în imagine, așa că fișierele pe care le scrie aparțin lui root.
  • Coduri de ieșire. Imaginea se încheie cu codurile de ieșire ale programului, așa că un pas de CI poate eșua pe baza lor. --fail-on-no-traffic face să eșueze o rulare prin care nu a trecut nimic, semnul obișnuit al unei rețele sau ținte greșite. docker stop se încheie cu 143, o oprire curată.
  • Ce lipsește. --doctor spune, de exemplu o capabilitate fără de care a fost pornit containerul.
  • Oprire. După docker stop, traficul revine imediat la normal. După docker kill, circulă din nou în aproximativ 3 secunde.

Ce imagini există

Fiecare versiune stabilă începând cu 1.1.0 este o imagine, etichetată cu versiunea ei și cu latest. Versiunile candidate nu primesc imagine. Fiecare este pachetul pentru Linux publicat, neschimbat, pe Ubuntu 24.04, pentru x86_64. Înainte de publicare se verifică suma de control și proveniența build-ului pachetului, iar imaginea este rulată pe un nucleu Linux așa cum descrie această pagină. Pentru a verifica o imagine descărcată:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
