Simuler la latence réseau dans Docker et Docker Compose

Ajoutez de la latence, de la perte de paquets ou une limite de débit au trafic d'un seul conteneur, sans modifier son image et sans proxy devant lui. L'image de Bean Network Tester rejoint le réseau de ce conteneur, ne change que ce qui y entre et en sort, puis s'arrête d'elle-même. C'est le paquet Linux, elle est donc expérimentale.

Ralentir un conteneur

Lancez l'image à côté du conteneur à tester, ici nommé api. Elle a besoin de trois capacités en plus de celles de Docker par défaut, et pas de --privileged :

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api place le programme dans le réseau de ce conteneur. Il atteint chaque programme de ce réseau, y compris un autre conteneur démarré dedans de la même façon, et jamais l'hôte ni les conteneurs qui ont leur propre réseau. --dst-ip le limite à une adresse. Sans cette option, chaque connexion de api est ralentie. Mesuré : avec --latency 100, le ping du conteneur vers cette adresse est passé de 0,07 ms à 200,8 ms, car la requête et la réponse sont toutes deux retardées, et son ping vers une autre adresse est resté sous 1 ms.

Chaque réglage de la ligne de commande fonctionne ici : --loss, --jitter, --down et --up pour une limite de débit, un préréglage ou tout un scénario. --duration met fin à la session, tout comme docker stop.

Docker Compose : simuler la latence réseau d'un service

Dans Compose, c'est un service à part qui partage le réseau de celui qu'il ralentit :

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Chaque service qui parle à api le voit désormais 400 ms plus loin, avec 2 % des paquets perdus. Mesuré avec ce fichier : le ping depuis un autre service est passé de 0,1 ms à 401 ms. docker compose stop slow-network y met fin, et le trafic redevient normal aussitôt.

Un programme dans un conteneur

--target choisit un programme par son nom, comme sur un poste de travail. Pour voir les processus d'un autre conteneur, l'image a aussi besoin de sa liste de processus : --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Sans --pid, le programme ne trouve pas ce processus et le dit dans son journal : Targeting: NO matching process has a connection open - traffic is NOT being impaired. Rien n'est ralenti dans ce cas.

Un programme sur l'hôte Linux

L'image peut aussi atteindre un programme qui tourne sur l'hôte lui-même, hors de tout conteneur. Il lui faut alors le réseau et la liste de processus de l'hôte, et deux options de plus : sans les deux, la lecture des connexions d'un programme hors du conteneur est refusée.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Avec --network host, la session change le trafic de l'hôte lui-même, votre session ssh comprise : gardez-la étroite avec --target, --dst-ip ou --dst-port, et courte avec --duration. Mesuré sous Ubuntu 26.04 : les requêtes du programme ciblé sont passées de 3 ms à environ 250 ms, et celles d'un autre programme sont restées à 11 ms. Sur un poste de travail, le paquet Linux fait la même chose sans Docker.

Docker Desktop sous Windows et macOS

Docker Desktop exécute les conteneurs dans sa propre machine virtuelle Linux, et là « l'hôte » désigne cette machine. L'image change le trafic des conteneurs, jamais celui des programmes Windows ou macOS. Pour ralentir un programme Windows, utilisez la version Windows de Bean Network Tester.

Sur un Mac à puce Apple et sur les autres machines arm64, Docker exécute cette image x86_64 en émulation, et une capture peut ne pas y fonctionner. Mesuré sur un Mac M2 avec l'émulation QEMU de Colima : l'image démarre et --simulate fonctionne, mais une capture s'arrête aussitôt avec Function not implemented, alors que --doctor indique pourtant OK à chaque ligne.

Fichiers, scénarios et CI

  • Fichiers. Montez un dossier sur /work (-v "$PWD:/work") pour --log-conns, --repro-out, des fichiers CSV ou un fichier --scenario. Le programme tourne en root dans l'image, donc les fichiers qu'il écrit appartiennent à root.
  • Codes de sortie. L'image se termine avec les codes de sortie du programme, qu'une étape de CI peut donc faire échouer. --fail-on-no-traffic fait échouer une exécution que rien n'a traversée, signe habituel d'un mauvais réseau ou d'une mauvaise cible. docker stop se termine par 143, un arrêt propre.
  • Ce qui manque. --doctor le nomme, par exemple une capacité sans laquelle le conteneur a été démarré.
  • Arrêt. Après docker stop, le trafic redevient normal aussitôt. Après docker kill, il circule de nouveau en 3 secondes environ.

Quelles images existent

Chaque version stable à partir de 1.1.0 est une image, étiquetée avec sa version et latest. Les versions candidates n'en ont pas. Chacune est le paquet Linux publié, inchangé, sur Ubuntu 24.04, pour x86_64. Avant l'envoi, la somme de contrôle et la provenance du paquet sont vérifiées, et l'image est lancée sur un noyau Linux comme le décrit cette page. Pour vérifier une image téléchargée :

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
