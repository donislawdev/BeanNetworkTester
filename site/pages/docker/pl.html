Symulacja opóźnienia sieci w Dockerze i Docker Compose

Dodaj opóźnienie, utratę pakietów albo limit prędkości ruchowi jednego kontenera, bez zmiany jego obrazu i bez proxy przed nim. Obraz Bean Network Tester dołącza do sieci tego kontenera, zmienia tylko to, co do niego wchodzi i z niego wychodzi, i sam się wyłącza. To wersja dla Linuksa, więc jest eksperymentalna.

Spowolnij jeden kontener

Uruchom obraz obok kontenera, który chcesz sprawdzić, tutaj o nazwie api. Potrzebuje trzech uprawnień ponad domyślne Dockera i nie potrzebuje --privileged:

docker run --rm --network container:api --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --dst-ip 203.0.113.10 --latency 100 --duration 60

--network container:api wpuszcza program do sieci tego kontenera, więc inne kontenery i host zostają nietknięte. --dst-ip zawęża działanie do jednego adresu. Bez niego zwalnia każde połączenie api. Zmierzone: przy --latency 100 ping kontenera do tego adresu wzrósł z 0,07 ms do 200,8 ms, bo opóźnione są i zapytanie, i odpowiedź, a jego ping do innego adresu został poniżej 1 ms.

Działa tu każde ustawienie wiersza poleceń: --loss, --jitter, --down i --up dla limitu prędkości, preset albo cały scenariusz. Sesję kończy --duration, a także docker stop.

Docker Compose: opóźnienie sieci dla usługi

W Compose to osobna usługa, która dzieli sieć z tą, którą spowalnia:

services:
  api:
    image: your-api-image
  slow-network:
    image: ghcr.io/donislawdev/beannetworktester:1.1.0
    network_mode: "service:api"
    cap_add: [BPF, PERFMON, NET_ADMIN]
    command: ["--latency", "200", "--loss", "2", "--duration", "300"]

Każda usługa, która rozmawia z api, widzi ją teraz 400 ms dalej i traci 2 % pakietów. Zmierzone z tym plikiem: ping z innej usługi wzrósł z 0,1 ms do 401 ms. docker compose stop slow-network kończy sesję, a ruch od razu wraca do normy.

Jeden program w kontenerze

--target wybiera program po nazwie, jak na komputerze. Żeby widzieć procesy innego kontenera, obraz potrzebuje też jego listy procesów: --pid container:api.

docker run --rm --network container:api --pid container:api \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target nginx --latency 100 --duration 60

Bez --pid program nie znajduje takiego procesu i mówi to w logu: Targeting: NO matching process has a connection open - traffic is NOT being impaired. Wtedy nic nie zwalnia.

Program na hoście z Linuksem

Obraz sięga też do programu, który działa na samym hoście, poza kontenerami. Potrzebuje wtedy sieci i listy procesów hosta oraz dwóch dodatkowych opcji: bez obu odczyt połączeń programu spoza kontenera jest zabroniony.

docker run --rm --network host --pid host \
  --cap-add BPF --cap-add PERFMON --cap-add NET_ADMIN \
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined \
  ghcr.io/donislawdev/beannetworktester:1.1.0 --target firefox --latency 100 --duration 60

Z --network host sesja zmienia ruch samego hosta, razem z Twoją sesją ssh, więc zawęź ją przez --target, --dst-ip albo --dst-port i skróć przez --duration. Zmierzone na Ubuntu 26.04: zapytania wybranego programu wydłużyły się z 3 ms do około 250 ms, a innego programu zostały przy 11 ms. Na komputerze z pulpitem to samo bez Dockera robi pakiet dla Linuksa.

Docker Desktop na Windows i macOS

Docker Desktop uruchamia kontenery we własnej maszynie wirtualnej z Linuksem i tam „host” oznacza tę maszynę. Obraz zmienia ruch kontenerów, nigdy programów Windows ani macOS. Żeby spowolnić program w Windows, użyj wersji Bean Network Tester dla Windows.

Na Macu z Apple silicon i na innych maszynach arm64 Docker uruchamia ten obraz x86_64 w emulacji, a tam wywołań BPF jądra nie ma. Obraz startuje i --simulate działa, ale przechwytywanie od razu kończy się błędem Function not implemented. Zmierzone na Macu M2 z emulacją QEMU w Colima, gdzie --doctor i tak pokazał OK w każdym wierszu.

Pliki, scenariusze i CI

  • Pliki. Podłącz folder pod /work (-v "$PWD:/work") dla --log-conns, --repro-out, plików CSV albo pliku --scenario. Program działa w obrazie jako root, więc pliki, które zapisuje, należą do roota.
  • Kody wyjścia. Obraz kończy się kodami wyjścia samego programu, więc krok CI może na nich polec. --fail-on-no-traffic oznacza porażkę przebiegu, przez który nic nie przeszło, co zwykle znaczy złą sieć albo zły cel. docker stop kończy się kodem 143, czyli czystym zatrzymaniem.
  • Czego brakuje. Mówi to --doctor, na przykład uprawnienie, bez którego uruchomiono kontener.
  • Zatrzymanie. Po docker stop ruch od razu wraca do normy. Po docker kill płynie znowu w ciągu około 3 sekund.

Jakie są obrazy

Każde stabilne wydanie od 1.1.0 jest obrazem, oznaczonym swoją wersją i latest. Wydania RC obrazu nie dostają. Każdy to opublikowany pakiet dla Linuksa bez zmian, na Ubuntu 24.04, dla x86_64. Zanim obraz zostanie wysłany, sprawdzana jest suma kontrolna i pochodzenie pakietu, a sam obraz jest uruchamiany na jądrze Linuksa tak, jak opisuje ta strona. Żeby sprawdzić pobrany obraz:

gh attestation verify oci://ghcr.io/donislawdev/beannetworktester:1.1.0 --owner donislawdev --predicate-type https://slsa.dev/provenance/v1
