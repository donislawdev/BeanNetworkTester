Paketverlust per Befehlszeile simulieren

Dasselbe Programm läuft auch ohne Fenster. Gib ihm irgendeine Option, und es arbeitet stattdessen in der Konsole. So nutzt es ein Skript oder ein CI-Job.

Wie es startet

Unter Windows ist es dieselbe BeanNetworkTester.exe, die das Fenster öffnet: ohne Optionen öffnet sie das Fenster, mit irgendeiner Option läuft sie in der Konsole und zeigt kein Fenster. Aus einer Kopie des Quellcodes schreibst du stattdessen python bean_network_tester.py. Unter Linux ist das Programm ./BeanNetworkTester im entpackten Ordner, und ein echtes Abfangen braucht sudo; Schlechtes Netz unter Linux sagt, was es dort sonst noch braucht.

Die Befehlszeile spricht immer Englisch, egal in welcher Sprache das Fenster ist, damit ihre Meldungen in jedem Protokoll gleich lauten.

Erst ohne Risiko ausprobieren

BeanNetworkTester.exe --simulate --loss 20 --duration 10
BeanNetworkTester.exe --doctor
BeanNetworkTester.exe --config meine-einstellungen.json --dry-run

Der erste läuft mit erfundenem Verkehr, braucht also keinen Treiber und keine Administratorrechte und kann das Netz nicht berühren. Der zweite prüft diesen Computer: die Rechte, die das Abfangen braucht, den Abfangtreiber und Reste eines früheren Laufs. Der dritte liest eine Einstellungsdatei und sagt, ob sie gültig ist, ohne etwas zu starten.

Woher die Einstellungen kommen

Vier Quellen, jede überschreibt die vorige: die Standardwerte, eine Einstellungsdatei (--config), ein fertiges Profil (--preset) und die Optionen in der Befehlszeile. --print-config zeigt das Ergebnis als JSON, und --save-config schreibt es in eine Datei, die du wieder laden kannst, im Fenster oder in der Befehlszeile.

Jede Einstellung im Fenster hat eine eigene Option, etwa --loss oder --target. Sie stehen, mit dem, was sie tun, auf der Seite mit den Referenztabellen. Die Optionen unten sind alles Übrige.

Was es ausgibt

Das Protokoll, gedacht für Menschen, geht auf die Standardfehlerausgabe, jede Zeile beginnt mit [bean]. Daten gehen auf die Standardausgabe: alle paar Sekunden eine Berichtszeile und am Ende eine Zusammenfassung. Mit --format json trägt die Standardausgabe ein JSON-Objekt pro Zeile: ein sample-Objekt für jeden Bericht und am Ende eine summary mit dem Exit-Code, dem Seed und dem Befehl, der den Lauf wiederholt. Vor dem ersten Bericht kommt ein start-Objekt, geschrieben, sobald das Abfangen läuft, damit ein Programm, das dieses startet, weiß, wann es seinen Verkehr senden kann.

BeanNetworkTester.exe --simulate --duration 30 --format json > run.ndjson

Jede Art, wie ein Lauf enden kann, hat ihren eigenen Exit-Code, sodass eine Pipeline eine fehlschlagende Anwendung von einem Werkzeug unterscheiden kann, das nicht starten konnte. Die Codes stehen auf der Seite mit den Referenztabellen.

Beispiele

Ein Programm eine Minute lang stören und sonst nichts auf dem Computer:

BeanNetworkTester.exe --target myapp.exe --latency 200 --loss 2 --duration 60

Einen Server zwei Minuten lang stören, mit einer Ausgabe, die eine Pipeline lesen kann, und mit Fehler enden, wenn gar nichts abgefangen wurde:

BeanNetworkTester.exe --dst-ip 10.0.0.5 --dst-port 443 --loss 5 --duration 120 --format json --fail-on-no-traffic

Ein fertiges Szenario, das sich nicht von selbst wiederholt, zehn Minuten lang in Schleife abspielen und einen Bericht behalten, der den Lauf wiederholt:

BeanNetworkTester.exe --scenario scenarios/upload-drop-midway.json --loop --target myapp.exe --duration 600 --repro-out run.json

Mehr Rezepte für Pipelines stehen unter Netzwerktests in CI.
