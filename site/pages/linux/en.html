Simulate a bad network on Linux, for one app

On Linux the usual answer is tc with netem: it adds delay and loss to a whole network interface, from the command line. Bean Network Tester does the same kinds of damage to one program, from a window or from the command line, and stops on its own. Its Linux version is experimental, and this page says what that means.

tc netem commands and what to use here

A netem command and the nearest command here, side by side. Run it with sudo, and keep --target and --duration: without them it affects the whole computer, as netem does.

sudo tc qdisc add dev eth0 root netem delay 100ms 20ms loss 5%
sudo ./BeanNetworkTester --target firefox --latency 100 --jitter 20 --loss 5 --duration 60

The numbers do not all carry over one to one. netem delays only what leaves the interface, and this tool captures both directions, so --latency 100 adds about 200 ms to a round trip: add --filter out to delay only what leaves. A netem rate is in bits per second, and the speed limit is in KB/s. The netem page explains each difference.

Why not just netem?

  • One program, not the whole interface. netem slows everything that leaves eth0, your ssh session included. Here --target picks a process by name (on Linux without .exe: firefox, chrome), a PID, an address or a port, and the rest of the machine keeps working.
  • Both directions. netem shapes what goes out, and incoming traffic needs an ifb device and a second set of rules. Here download and upload each have their own limit.
  • It cleans up after itself. A netem rule stays until you delete it. A session here ends after --duration, and if the program is killed, the traffic it was holding flows again after about 3 seconds.
  • You see what happened. A chart, a connections table and counters of what was delayed, dropped and let through, instead of tc -s qdisc.
  • Runs repeat. --seed replays the same random loss and jitter, and timed scenarios change the settings at set seconds, the way a script of tc and sleep does.

What it needs

  • The package from the releases page, a .tar.gz with its own Python and Tk. It is built on Ubuntu 24.04 and checked on Ubuntu 24.04 and 26.04, for x86_64, and needs glibc 2.38 or newer.
  • The kernel: Linux 5.10 or newer, built with BTF. The capture runs on eBPF.
  • Root, or the capabilities CAP_BPF, CAP_PERFMON, CAP_NET_ADMIN and CAP_NET_RAW. The window asks for an administrator's password in the desktop's own dialog, the command line needs sudo, and --simulate needs neither.
tar -xzf BeanNetworkTester-*-linux-x64.tar.gz
cd BeanNetworkTester
./BeanNetworkTester --install-desktop
sudo ./BeanNetworkTester --doctor

--install-desktop adds the program to the applications menu, so run it without sudo. --doctor lists what the machine still lacks.

The network tools work on Linux too

The {{app.app.tabs.tools}} tab answers questions before and during a test: {{app.tools.ping.tab}} (a continuous ping with a chart), {{app.tools.nat.tab}}, {{app.tools.portscan.tab}}, {{app.tools.sockets.tab}}, {{app.tools.portcheck.tab}}, {{app.tools.tcphealth.tab}} (what the kernel keeps for each connection, as ss -ti shows it) and {{app.tools.adapters.tab}} (as ip addr and ip route show them). {{app.tools.tcphealth.tab}} and {{app.tools.adapters.tab}} need no sudo, and {{app.tools.ping.tab}} needs it only where the system does not let your group send pings, as on Ubuntu 24.04.

Where Linux differs, today

  • --target reads the system's list of sockets, so the first exchange of a new connection can pass before the target applies.
  • When the tool cannot keep up, the kernel lets packets go around it unimpaired, and the counters say how many.
  • IP fragments always pass through untouched.
  • There is no code signature on Linux. The release's checksums and attestation say which build produced the file, and the download page shows how to check them.

For a permanent setup on a whole interface, netem is already in your kernel and is the right tool. This one is for testing one application for a while.
