**Bean Network Tester** は、テスターと開発者のためのツールです。回線の悪い環境で自分のアプリケーションがどう動くかを確かめられます。
Clumsy や NetLimiter と同じように、ネットワークをわざと劣化させることができます。
ping を増やす、パケットを破棄する、速度に上限をかける、接続を切断する、などです。
仕組みとしては、**[WinDivert](https://www.reqrypt.org/windivert.html)** ドライバー
(**[PyDivert](https://github.com/ffalcinelli/pydivert)** 経由) で通信を傍受します。
ツールチップ付きのわかりやすいウィンドウ画面と、CI 向けのコマンドラインモードの両方を備えています。

⭐ **お役に立てたら、ぜひスターを付けてください。** 同じツールを必要としている次のテスターが、このツールの存在を知るきっかけになります。

**できること**

- **遅延とジッターの追加** - 固定またはランダムの遅延に加えて、ときどき起きるスパイクも再現します。
- **パケットの破棄、破損、重複** - パケットロスはバースト状に発生させることもでき、実際の無線回線が不調になるときの様子を再現できます。
- **ダウンロード/アップロード速度の制限** - 指定した KB/s まで絞ります。パケットを破棄し始める前に、キューイング遅延を生むバッファーも備えています。
- **接続の切断** - TCP リセット、死んだ回線、いつまでも確立しない新規接続を再現します。
- **回線のオン・オフの繰り返し** - 断続的に起きる回線の断を再現します。
- **パケットだけでなく経路も壊す** - MTU ブラックホールと、NAT 方式のアイドルタイムアウトを再現します。
- **ポートや IP のブロック** - 小さな内蔵ファイアウォールに加え、LAN モード (インターネットなし) とインターネットのみ (ローカルネットワークなし) があります。
- **1つのアプリに絞る** - プロセス名、PID、IP、ポート、またはアドレスファミリーで指定できます。
- **プリセットと保存済みプロファイル** - 56k モデム、カフェの Wi-Fi、衛星回線、機内 Wi-Fi などがあります。
- **シナリオの実行** - 時間に沿ってネットワークの状態を自動で切り替えるステップを実行します。
- **速度制限のスケジュール** - シナリオを書かなくても、速度を繰り返し変化させるタイムラインを組めます。
- **シードによる再現** - ランダムなパケットロスやジッターまで、まったく同じ実行を再生できます。
- **バグの引き継ぎ** - すべての設定、カウンター、実行を再現するコマンドラインを含むレポートを作成します。
- **リアルタイム表示** - グラフ、カウンター、検索できる接続テーブル、イベントログを備えています。
- **CSV へのエクスポート** - セッションの統計と、接続テーブルのスナップショットを書き出せます。
- **コマンドラインモード** - 終了コードと JSON 出力に対応し、CI からスクリプトで操作できます。
- **テレメトリなし、完全オフライン** - データをどこにも送信しません。

## クイックスタート (3ステップ)

1. `BeanNetworkTester` をダウンロードします。**zip** はインストール不要でそのまま動作し、**`.msi`** はコンピューターのすべてのユーザー向けに、`PATH` とスタートメニューへ登録してインストールします (管理者権限が必要です)。自分でビルドすることもできます: `pyinstaller --noconfirm BeanNetworkTester.spec`。
2. `BeanNetworkTester.exe` を実行します。プログラムが**自分で管理者権限を要求します** (WinDivert に必要なためです)。リポジトリから実行する場合は `python bean_network_tester.py` です。
3. "Profiles" リストからプリセット (例: "3G network") を選び、**START** をクリックします。

**同じファイル**でテキストモードも動きます: `BeanNetworkTester.exe --simulate --loss 10 --duration 5`。

ウィンドウの上部にある "Active: ..." のバーには、現在行っていることの要約が表示されます
(例: *Active: +150 ms ping, 1% loss, download <= 384 KB/s*)。各フィールドにカーソルを合わせると、その役割を説明するツールチップが表示されます。

> 注: プリセットを選んでもフィールドが埋まるだけです。劣化が始まるのは **START** を押したときだけです。
> 管理者権限がないと、WinDivert ドライバーは読み込まれません。

以下の詳しいマニュアルではなく、特定の作業の進め方を知りたい場合は、
[ウェブサイトのガイド](https://beannetworktester.donislawdev.com/ja/)をご覧ください。パケットロス、遅延、速度制限、1つのアプリに絞る方法、インターネットなしでのテストを取り上げ、それぞれ試す価値のある数値と、それを実行するコマンドを載せています。
ほかに2つ、ポートを使っているプログラムを見つける方法と、`tc netem` や Network Link Conditioner の代わりに使うものを説明したガイドがあります。ガイドは英語とポーランド語からアラビア語とベトナム語まで、22 の言語で書かれています。

## 言語

翻訳は **`lang/<code>.json`** ファイルに置かれています (同梱: `lang/en.json`、`lang/pl.json`、そして簡体字中国語の `lang/zh.json`)。起動時にアプリが **`lang/` ディレクトリを走査**し、利用できる言語を自動で検出します。起動時の言語はシステムのロケールに従い、対応する翻訳があればそれを使い、なければ英語になります。システムが繁体字中国語に設定されている場合も英語になります。同梱されているのは簡体字のファイルで、両者は同じ言語の2通りの表記ではなく、別の文字体系だからです。Settings ウィンドウ (右上の歯車) の **Language** リストで、いつでも言語を切り替えられます。現在の設定を保ったまま、UI が選んだ言語で再構築されます。

インターフェースの**すべて**が翻訳されています: タブ、ラベル、ボタン、ツールチップ、列見出し、統計、セッションパネル、イベントログ、ログメッセージ、ダイアログ、エラーメッセージ (ユーザーに表示される例外) です。コードが使うのは**キー**だけ (例: `app.tabs.statistics`) で、テキストは言語ファイルから取得されます。選択した言語にキーがない場合は英語が使われ、それもなければ最後の手段としてキーそのものが表示されます。(コマンドライン - CLI - は、システムや UI の言語に関係なく、**常に英語**です。)

**新しい言語の追加**にコードの変更は不要です。`lang/en.json` を例えば `lang/de.json` にコピーし、値を翻訳して、ヘッダーの `"_meta": {"code": "de", "name": "Deutsch"}` を記入するだけで、再起動後にその言語が一覧に現れます。壊れた言語ファイルは読み飛ばされます (アプリがクラッシュすることはありません)。

## 動作要件

- Windows 10/11 (64 ビット)、Python 3.10+ (tcl/tk オプション付き)
- 管理者権限
- `pydivert` (通信の取得)、`psutil` (フォールバック、後述)

ソースからのインストールは Python 3.10 以降で動作します。CI のテストとビルドは **3.14 のみ**で行っています。リリース版の `.exe` が固められているのがこのバージョンだからです。それより古いバージョンもサポートしていますが、コミットのたびに動作を確認しているわけではありません。

Windows の Python 3.10 から 3.12 は、15.6 ms 刻みで時間を測ります。すべてのパケットはこの時計で時刻が付けられるため、1刻みより細かい遅延、ジッター、速度制限は刻みの整数倍に丸められ、`--doctor` が警告します。Python 3.13 以降と `.exe` は、マイクロ秒単位で測ります。

`psutil` はツールと一緒にインストールされますが、Windows でプロセスの指定を動かしているのはこれではありません。Windows ではソケットテーブルとプロセス名を OS から直接取得するので、`psutil` を完全に取り除いても、プロセスの指定は動き続けます (実測: 310 個のポートを対応付け、37 件中 37 件の名前を解決しました)。`psutil` はそれ以外の環境向けのフォールバックで、ドライバーなしの Linux でエンジンのテストが動くのもそのためです。

## ウィンドウ

ウィンドウは**画面とシステムのスケーリング (DPI) に合わせて調整されます**。初期サイズは解像度から計算され (1366x768 に収まり、Full HD / 2K / 4K では大きくなります)、すべての寸法 - 列幅、テーブルの行の高さ、グラフの余白、テキストの折り返し - がフォントに合わせて拡大縮小されます。プログラムは自身を **Per-Monitor-V2 DPI 対応**と宣言しているため、スケーリングの異なる2台目のモニターへウィンドウを移動しても、インターフェースがぼやけることはありません。

ウィンドウのサイズと位置、選択中のタブ、言語、折りたたんだセクション、ログとタブの分割位置、テーブルの並べ替え順は、`bean_network_tester_ui.json` (プロファイルの隣) に記憶されます。保存されたジオメトリは使用前に検証されます。2台目のモニターに置いたままだったウィンドウは、そこでもう一度開き、そのモニターがなくなっていれば現在の画面の中央に戻ります。

- **Control** - すべての劣化設定を、**折りたたみ可能なセクション**にまとめています (折りたたんだ状態は記憶されます)。幅の広いウィンドウでは、セクションが (1列だけの細い表示と空の右半分になる代わりに) **2列に並ぶ**ので、スクロールがかなり減ります。タブ全体がスクロールし、**マウスホイール**にも対応しています。
- **Statistics** - 3つのサブタブがあり、小さな画面でも何も切れません。
  - **Live** - カウンター (パケット、パケットロス、破損、切断...) とスループットのグラフです。カウンターのグリッドは、ウィンドウ幅に収まるよう列数を自動で選びます。"Export CSV" ボタンがあります。
  - **Session** - シード、継続時間、使用データ量、ピーク値と、"Mark bug"、"Save repro report"、"Copy CLI command" ボタンがあります。
  - **Events** - イベントログです (START/STOP/CHANGE/SCENARIO/BUG/RESET)。
- **Connections** - テスト対象のシステムがどの IP:ポートと通信しているかを表示します。各列の説明は下の[Connectionsページの列](#connectionsページの列)にあり、各列の見出しにもツールチップがあります。ポートがまったくない通信 - ping (ICMP) - も、アドレスごとに1行で、ポートのセルを空にして一覧に載せます。
  - **"down"/"up"/"total" は、アプリケーションが実際に受け取った量**で、セッションパネルが "Downloaded (MB)" と呼ぶものと同じ量です。**"down seen"/"up seen" は、何かを劣化させる前にツールが取得した量**です。何も設定していなければ両者は等しくなります。パケットロスや速度制限を加えた瞬間に差が生まれ、**その差が、その接続に生じた損害**です。どれも、カーソルを合わせると完全な説明文が表示されます。(この分離の前は、劣化の前に取得したバイト数が、「届いた量」を意味する見出しの下に入った1組しかなく、アプリケーションが 0.4 MB しか受け取っていないのに 5 MB 受信と表示される行がありました。) このほか、検索ボックス (デバウンス付きで、キーを押すたびにテーブルを作り直しません)、
    クリックで並べ替えられる見出し、**"Freeze"** (行がカーソルの下から逃げていかなくなります)、そして**右クリックメニュー**があります。行/IP のコピー、**"Target this process"**、**"Limit to this IP:port"** - フィルターのフィールドをワンクリックで埋めます。**"Reset this connection"** は、セッションが動いているかどうかに関係なく、その1本の接続をただちに切断します。その接続を使っているプログラムはエラーを受け取り、相手側は TCP リセットを受け取ります。セッション中は、そのリセットも他のパケットと同様に劣化処理を通るので、パケットロスが大きいと途中で破棄されることがあります。この機能は IPv4 の TCP でのみ使えます - Windows には IPv6 接続をリセットする手段がありません - ので、ほかの行ではメニュー項目がグレーアウトされ、管理者権限も必要です。
    テーブルは**仮想化**されています。実際に画面に表示されている行だけを描画するため、400 行でも数十万行でも、スクロールは一瞬です。以前の 400 行という固定の上限はなくなりました。表示する行数は **"Row limit"** フィールド (*Tables* セクション、0 = 無制限、既定値 50 000) で設定します。
- **Tools** - テストの前や最中に浮かぶ疑問に答える小さな補助機能で、サブタブが1つずつ割り当てられています。このタブの機能は、ネットワークに何も送信しません。現在あるのは次のものです。
  - **Sockets** - このコンピューター上のすべての TCP と UDP のソケットを、`netstat -ano` のように一覧にします。セッションは不要です。何が待ち受けているか、何が接続されているか、その状態 (LISTEN、ESTABLISHED、TIME_WAIT...)、そして所有しているプログラムがわかります。劣化をかける前に、アプリケーションがどのポートで待ち受けているかを確かめたり、どのプログラムがあるポートを握っているかを調べたりするのに使います。テーブルは、タブを開いたときと **Refresh** を押したときに読み込まれます。接続テーブルと同じ書き方 (`lport:8080`、`state:listen`、`proc:chrome`) で検索でき、行を右クリックすると、そのプログラムを対象にする、対象から外す、リモートアドレスに限定する、またはブロックする、といった操作ができます。プログラム名は管理者権限なしでも表示されます。
  - **Port check** - プログラムがそのポートを使えるかを調べます。ポートを1つ、リスト、または範囲で入力し (Control ページでポートを入力するのと同じ書き方で、`8080`、`80, 443`、`9000-9100`、一度に最大 1000 個)、**Check** を押します (Enter でも構いません)。各ポートは TCP と UDP のそれぞれについて、IPv4 と IPv6 で確認され、**Free**、**In use** (保持しているプログラムとその PID つき)、または **Reserved by Windows** と表示されます。**Reserved by Windows** は Windows が確保した範囲のことで、使われていないように見えるポートでサーバーが起動しない、よくある原因です。範囲はプロトコルごとに決まるため、UDP では空いていても TCP では空いていないポートがあり得ます。各ポートについて、ツールはこのコンピューター自身のループバックアドレスでシステムに問い合わせ、ポートはすぐに解放します。ポートを誰が握っているかは、**Sockets** と同じテーブルから取得します。行を右クリックすると、そのポートを握っているプログラムを対象にする、または対象から外す操作ができます。
  - **Filter tester** - Control ページのフィールド (対象プロセス、宛先 IP またはポート、ブロックする IP またはポート) を選び、式と値を入力すると、一致するかどうかがその場でわかります。式のどの部分がその値を選び、どの `!` の部分が除外したか、そして入力した内容をプログラムがどう解釈しているかも表示します。アドレス、ポート、PID のいずれでもない値は、「一致しない」ではなく、そのように報告されます。**"Use in the Control field"** は、式をそのフィールドに入れ、元の内容を置き換えます。入力した内容は、言語を切り替えても、プログラムを閉じるまで残ります。
  - **Adapters** - このコンピューター上のすべてのネットワークアダプターと、テストに影響する設定を、`ipconfig /all` が出力するような形で表示します (Windows のみ)。インターネット通信が出ていくアダプターが一番上に来て、その次に有効なものが続きます。1つ選ぶと、プレフィックスつきのアドレス、ゲートウェイ、DNS サーバー、DHCP、MAC アドレス、MTU、リンク速度が表示されます。別のデバイスが同じアドレスを使っている場合は、注意書きで知らせます。一覧は、タブを開いたときと **Refresh** を押したときに読み込まれます。ゲートウェイまたは DNS サーバーを右クリックすると、そのアドレスが Control ページの宛先 IP フィールドに入ります (そこのポートはそのまま残ります)。最初の行 **Proxy** には、プログラムがプロキシを経由するかどうかが表示されます。このアカウントの設定 (自動検出、セットアップスクリプト、プロキシサーバー、プロキシを経由しない対象)、Windows のサービスが使うプロキシ (WinHTTP)、そして `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 変数です。プロキシを使うプログラムは、対象ではなくプロキシに接続します。プロキシサーバーを右クリックすると、劣化の対象をそのアドレスに限定できます。名前で指定されたプロキシは名前解決しません。アドレスに含まれるパスワードは隠されます。**"Copy report"** は、すべてのアダプターとプロキシの設定を英語でコピーします。テキストには、このコンピューターのアドレスと MAC アドレスが含まれます。
  - **Diagnostics** - START が動かない理由を、コンソールなしで調べます。`--doctor` と同じチェック (管理者権限、WinDivert ドライバー、temp フォルダーの残骸...) を実行し、それぞれに OK、Warning、Problem のいずれかを付けます。**"Clean up the driver"** は、読み込まれたまま残っている WinDivert ドライバーをアンロードします (管理者のみ、セッション中は不可)。**"Copy environment report"** は、`--version` の行と `--doctor` の出力をコピーします。そのままバグ報告に貼り付けられます。レポートにはフォルダーのパスが含まれ、パスには Windows のユーザー名が含まれることがあります。**"Add network adapters"** または **"Add proxy settings"** にチェックを入れると、アダプターまたはプロキシもレポートに追加されます。どちらもチェックするまでオフです。アドレスから、このコンピューターがどのネットワークにいるかがわかるためです。
- 下部には **START/STOP**、**Apply changes**、**Load/Save file** があり、その下にログがあります。このバーは下端に固定されているので、どのタブもこれを覆い隠せません。

### 変更が反映されるタイミング

**何も自動では適用されません。** プリセット、プロファイル、LAN モード、読み込んだ設定ファイルは、**フォームを埋めるだけ**です。実行中のセッションに反映されるのは **"Apply changes"** を押したときだけで、フォームがエンジンの実際の動作と異なっていると、このボタンが**ハイライト**されます。タイトルの下のバーが、今見ているものが何かを教えてくれます。

| 接頭辞 | 意味 |
|---|---|
| `Preview:` | アプリは停止中です。START の後に何が起きるかを表しています |
| `Active:` | 今まさにトラフィックに適用されている内容です |
| `Unapplied changes:` | フォームが変更されています。"Apply changes" をクリックしてください |

セッションの実行中は**2つの要素がロック**されます (STOP でロックが解除されます)。**トラフィックフィルター** (START 時にのみ適用されます) と**言語セレクター** (言語を変更すると UI 全体が再構築されます) です。STOP ボタンは赤色なので、START と見間違えることはありません。

別の設定に引き継がれたフィールドは、**ラベルごとグレーアウト**され、どの設定が引き継いだかを示す注記が付きます。Schedule が設定されているとき "Download"/"Upload" がこうなります。スループットがスケジュールのステップから決まるためです。実際に何が有効になっているかが一目でわかります。

### フィールドの検証

数値フィールドは、**範囲も含めてリアルタイムに**チェックされます (例: パケットロス 0-100%、遅延 0-600000 ms)。不正なフィールドは赤くなり、理由がセクションの下に表示されます。フィルター式にも同じ仕組みが働きます。CLI にも同じ範囲が適用され、`--loss 250` は、以前のように黙って 100% に丸められるのではなく、エラーになります。

## 全オプションの解説

**Traffic to modify** - そもそもどのトラフィックを取得するかを決めます。選択肢は、両方向 (TCP+UDP+ICMP)、送信のみ、受信のみ、TCP のみ、UDP のみ、ICMP のみ (ping)、ループバックのみ (127.0.0.1/::1 - ローカルプロセス間の通信のテスト用) です。どのフィルターも **IPv4 と IPv6 の両方**を対象にします。(ping が「反応しない」場合は、ほぼ間違いなく、選んだフィルターに ICMP が含まれていないのが原因です。)

**ループバックのトラフィックは、アップロードとして扱われます。** Windows は、このコンピューター上の2つのプログラム間のやり取りを、どのフィルターを選んでいても、両方向とも送信として渡してきます。そのトラフィックでは、**Download**、スケジュールのダウンロード列、**NAT timeout** は効果がなく、アップロードに別の値があるときのメインの値も同様です。**Upload** の制限は両方向を合わせて適用され、対象プロセスが影響を受けるのは、そのプロセスが送信した分だけです。ループバックのフィルターでこうした設定を適用すると、プログラムがそのことを知らせます。

> **注:** ポートのプリセット ("DNS/HTTP/HTTPS only") は存在しません。ポートで絞り込むには、"Target destination" の **Port** フィールドを使ってください。リスト、範囲、除外 (`80,443,8000-8100`、`!53`) を理解します。ポートについて意味の異なる判断の場所が2つあると、混乱を招くだけだからです。

**Traffic filter** は開始時に適用されるため、実行中は**ロック**されます。変更するには、停止 (STOP) して別のものを選び、もう一度開始 (START) します。

**LAN mode** - "LAN mode (local network only, no internet)" チェックボックスです。パブリック (インターネット) アドレスとの通信を拒否し、ローカルネットワークは通します。対象は 10.0.0.0/8、172.16-31.x、192.168.x、ループバック、リンクローカル、CGNAT です。「LAN は使えるが、インターネットは落ちている」状態を再現します。インターネットに接続できないときのアプリの動作 (例: ゲートウェイや WAN がない、キャプティブポータル) のテストになります。

**Internet only** - その逆で、同じセクションにある "Internet only (no local network)" チェックボックスです。同じローカルアドレスとの通信を破棄し、インターネットは動いたままにするので、WAN は正常な状態で、イントラネットのサーバー、NAS、プリンターと通信するアプリをテストできます。できないことが2つあり、どちらも重要です。

- **ループバックは動き続けます。** 127.x と `::1` はどちらの場合も通過するため、ローカルの開発サーバー、自分のマシン上のデータベース、ループバックで自分自身と通信するものは何も影響を受けません。これは意図的です。自分のマシンが自分自身と通信することは、「ローカルネットワーク」ではないからです。
- **ルーターはローカルネットワーク上にあります。** PC がルーターに DNS を問い合わせている場合、名前解決も止まるので、インターネットの通信自体は通していても、インターネットが壊れたように見えます。それが邪魔になるときは、このテストの間はパブリックなリゾルバーを使ってください。

両方のチェックボックスを同時にオンにすることもできます。これは許可されており、ループバック以外のすべてが遮断されます。適用したときにログでその旨が通知され、2つのカウンターはそれぞれ自分の半分を報告します。

**Target process** - 影響を特定のアプリに絞り込みます。プロセス名 (例: `chrome.exe`)、PID、カンマ区切りのリスト、PID の範囲、ワイルドカード、正規表現が使えます。詳しくは[フィルター構文](#フィルター構文-プロセス--ip--ポート)を参照してください。マシンのそれ以外のトラフィックには手を加えません。空のフィールド = すべてのトラフィックです。

**Speed limit** - ダウンロード (受信) とアップロード (送信) それぞれの最大スループットを KB/s で指定します。0 = 制限なしです。ping は小さなパケットなので、速度制限ではほとんど変わりません。制限をテストするには、ファイルのダウンロードを使ってください。正の値は必ず何かを制限します。極端に小さな制限 (1 B/s 未満) は 1 B/s に切り上げられ、黙って「制限なし」になることはありません。

**Speed unit (Settings window)** - Statistics ページ、グラフ、この2つのフィールドの隣にある表示で、スループットを `KB/s`、`Mbit/s`、`MB/s` のどれで表示するかを選びます。変わるのは目で**読む**値だけで、入力する値は変わりません。制限そのものは KB/s のままです。保存される設定ファイル、スループットのスケジュール、同梱のシナリオ、`--down`/`--up`、NDJSON 出力が、すべてこの数値を使っているためです。単位を選ぶと、フィールドの隣に灰色の `(= 8.39 Mbit/s)` が表示されるので、ツールが求める数値を入力しながら、回線が販売されている数値で読むことができます。

> **ここでの `K` は 1024 で、メガビットは10進法の100万です。** この2つの規則は相殺されないので、1024 KB/s は 8 ではなく **8.39 Mbit/s** です。これは丸め誤差ではなく、正直な換算です。1バイトは8ビットで、`1024 x 1024 x 8 = 8 388 608` ビット毎秒であり、回線が販売されるあらゆる場面で、メガビットは 10^6 ビットを意味します。広告されている速度に制限を合わせたいときは、8 ではなく 8.39 で割ってください。

**Buffer** - 速度制限をかけたときのリンクバッファーの容量を、ミリ秒で指定します (0 = バッファー無制限)。速度制限のある回線で、超過分を破棄し始める前に、どれだけのキューイング遅延が溜まってよいかを決めます (バッファーブロート)。このバッファーがないと、トークンバケットは数十秒先まで「暴走」することがありました。パケットは極端な遅延を抱え、セッションの途中で制限を引き上げても (例: 「回線が回復する」スケジュールのステップ)、溜まった待ちパケットがその後のどの高速なステップも飲み込むため、効果がありませんでした。`N` ms のバッファーがあれば、遅延は約 `N` ms に抑えられ、超過分は "Rate-limit drop" (別のカウンターで、"Loss" でも "Buffer overflow" でもありません) として破棄され、制限を引き上げた後のスループットは約 `N` ms 以内に回復します。既定値は 1000 ms です。ダウンロード/アップロードの制限またはスケジュールが設定されているときだけ有効です。バッファー内で待つ時間は、実際の回線と同じく *Latency* に上乗せされます。遅延が 200 ms でバッファーが 150 ms まで満杯なら、パケットは約 350 ms 後に到着します。

**Delay (ping)** - *Latency*: すべてのパケットに何 ms を加えるかです。*Jitter*: 遅延のランダムな変動幅 (+/- ms) で、ping が跳ね、パケットの順序が入れ替わります。知っておく価値のある点が3つあります。

(0) **ping は、設定した遅延の約2倍増えます。** 遅延はすべてのパケットに加わり、既定の双方向のトラフィックフィルターでは、それがリクエストとリプライの両方なので、`--latency 100` はおよそ +200 ms の ping として現れます (実測: `--latency 200` で、ループバックの ping が 1 ms 未満から約 408 ms になりました)。希望する ping の半分の値を選んでください。ジッターは、同じようには2倍に**なりません**。各パケットが自分の値を引くため、ゆらぎは約 1.4 倍になり、2倍に達するのは極端な場合だけです。組み込みのプリセットはこの前提で調整されています。`Satellite (geostationary)` は 340 ms を指定していて、実際の静止衛星回線にある約 680 ms の ping を再現します。

(1) ジッターは各パケットに独立したランダムな遅延を加えるので、パケットがキューの中で互いを追い越すことがあります。ジッターには本質的に**パケットの順序を入れ替える**働きがあります (実際のネットワークでも同じことが起きます)。
(2) 負の揺れはゼロに切り詰められるため、ジッターが**遅延より大きい**と、加わる遅延の平均は遅延そのものより大きくなります (例: 遅延 0、ジッター 50 ms では、約半数のパケットは遅延なしで、平均は 0 ではなく約 12 ms になります)。遅延がジッターより大きいときは、この影響は無視できます。

*Latency spike* は同じセクションにあります。スパイクもまた遅延、つまりときどき起きる大きな遅延だからです。指定した確率で**1つのパケット**に追加の遅延 (ms) を加えます。一瞬の「ラグ」は実際にこのように届きます。この確率はパケットごとで**各方向**に適用されるため、往復では、数値から想像するより約2倍の頻度で当たります。

**順序の入れ替わった配送のテスト** - スパイクの2つの設定は、このためにあります。セクションの名前が "Latency (ping) and packet order" なのもそのためです。スパイクを受けたパケットは、それより後に送られたパケットの後に届くので、*Spike chance* と *Spike size* は、ジッターのように他のすべてのパケットの遅延をばらつかせることなく、トラフィックの順序を入れ替えます。テスト対象が、順序の入れ替わりに自力で耐えなければならない UDP プロトコル (ゲーム、QUIC、テレメトリ、音声) のときに重要です。パケットの間隔より大きなスパイクサイズを設定してください。そうしないと、何も追い越しません。

実際にそれが起きたかどうかは、設定したかどうかとは別の問題なので、ツールはそれを数えます。Statistics ページの **Reordered** (統計 CSV では `packets_reordered`) です。スパイクを設定しているのに 0 だった場合は、トラフィックがまばらで、どのパケットも別のパケットを追い越せなかったという意味で、設定が無視されたわけではありません。カウントは方向ごとなので、2つの忙しい接続が互いを追い越しても、どちらの端でも順序の乱れが見えないことがあります。

**Impairments** - *Loss*: 跡形もなく消えるパケットの割合です (5% でもすでに明らかに不調なネットワークです)。*Corruption*: データのビットが反転するパケットの割合で、**ペイロードを持つパケットだけ**が対象です。データのないパケット (例: 純粋な ACK、SYN) には反転するものがないため、そのまま通過し、**破損とは数えられません**。*Duplication*: 2回送られるパケットの割合です。

**Losses in a row (burst)** - 実際の回線では、パケットが1つずつ失われることはまれです。電子レンジ、エレベーター、送信機間の切り替えは、ほんの一瞬だけ接続を奪い、その瞬間に送られたものはすべて消えます。このフィールドは、パケットが**平均で**何個連続して失われるかを指定し、合計でどれだけ失われるかは *Loss* が引き続き決めます。見た目以上に重要です。5% が散らばっているだけなら、たいていの接続は吸収できますが、同じ 5% が20個ずつの連続で起きると、転送が止まり、確立していた接続が切れ、アプリケーションは再接続の処理に入ります。0 にすると、パケットロスは均等に散らばります。この設定が登場する前のツールの動作がそれです。

知っておく価値のある制限が2つあり、設定を適用したときにログが両方を伝えます。非常に高いパケットロスは、非常に短い連続としては発生しません。それだけ短い連続では、連続の間に残る余地が小さすぎるからで、そのため実際に実現できる連続長がログに示されます。そして連続長が長いと、連続の間隔が大きく開くので、短いセッションでは1つも発生しないことがあります。連続は方向ごとに別々に発生するため、20個の連続とは、その方向で20個連続するという意味で、Asymmetry がオンのときは、ログがアップロード側についても両方の制限を伝えます。パケットロスが 100% なら、すべてのパケットが失われるので、連続長は何も変えません。

**Link flapping** - トラフィックが周期的に完全に失われます。*Period* 秒ごとに、指定した割合の時間だけ回線が死にます。不安定にちらつく接続を再現します。これは、連続したパケットロスとは**別物**です。フラッピングは予測できる固定の周期で、上の連続したパケットロスは、そのほかは普通のトラフィックの中に起きる、ランダムで短いものです。

**Advanced (NAT / connections):**
- *Target destination (IP/port)* - 選んだサーバーとの間のトラフィックだけを劣化させます。どちらのフィールドも、リスト、範囲、CIDR、ワイルドカード、比較、除外、正規表現を受け付けます。詳しくは[フィルター構文](#フィルター構文-プロセス--ip--ポート)を参照してください。例: IP `10.0.0.1-10.0.0.50,!10.0.0.7`、ポート `80,443,8000-8100`。空 = すべてです。
- *TCP SYN drop (%)* - 接続を開くパケットを破棄する割合です。確立しない接続 (再試行のテスト) を再現します。NAT の内側からのテストに役立ちます。
- *Max size (MTU)* - N バイトより大きいパケットを破棄します。トンネル、VPN、NAT の内側で起きる「MTU ブラックホール」を再現します (小さなパケットは通り、大きなパケットは消えます)。0 = 無効です。
- *NAT timeout* - 接続が N 秒より長く無通信だった場合、次に届く受信パケットを破棄します (マッピングが「消える」状態)。キープアライブのテストです。0 = 無効です。
- *TCP tear-down (RST)* - RST パケットで突然切断される接続の割合です。再接続を強制します。**TCP のみ**です (RST は TCP の概念で、UDP は「切断」できません。パケットロスか回線のオン・オフを使ってください)。**Tear down TCP now** ボタンは、アクティブなすべての TCP 接続を約 3 秒間リセットします。
- *Schedule* - 時間とともに変化するスループットです。KB/s 単位の `time:download:upload` を、カンマで区切って指定します。例: `2:100:0, 2:500:0` = 100 KB/s で 2 秒、次に 500 KB/s で 2 秒を、ループします。スケジュールが空でないときは、固定の "Download/Upload" フィールドを**上書き**します。GUI はそれらをグレーアウトして、その旨を明示します。ステップの時間は 0 より大きく 86400 秒以下で、各速度は、固定のフィールドと同じく 0 (制限なし) から 10000000 KB/s までです。範囲外のステップは受け付けられず、名前を挙げて知らされます。

**Session:**
- *Duration (s)* - この秒数が経過すると、プログラムが**自分で停止します** (STOP をクリックしたのとまったく同じです)。劣化が消え、ドライバーが解放されます。`0` = STOP まで実行し続けます (以前からの既定の動作)。CLI での対応するオプションは `--duration` です。トラフィックフィルターと同じく、**START 時にのみ**考慮されます ("Apply changes" では変わりません)。この値は設定ファイルと再現コマンドに保存されます。

**Repeatability and scenario:**
- *Seed* - 任意の数値を設定すると、実行のたびに同じようにランダム化されます (バグが再現可能になります)。空 = 毎回異なります。**START 時にのみ**取り込まれるので、セッションの実行中はロックされます。
- *Scenario* - 設定をリアルタイムに変更する JSON ファイルです (例: 10 秒後に ping を追加し、20 秒後に切断する)。"Loop" は、それを延々と繰り返します。例は `scenarios/` にあります (カフェの Wi-Fi、モバイル LTE->3G、混雑した VPN、失敗する DNS、過負荷のゲームサーバー、途中で落ちるアップロード、ブロックされたバックエンド/API)。"Load scenario..."、"Clear"、"Loop" は START 時に作用するため、セッションの実行中はロックされます。シナリオの実行中の "Apply changes" は機能します。[シナリオファイルの形式](#シナリオファイルの形式)を参照してください。

**Profiles** - 用意済みのプリセットで、**良い順 (上) から悪い順 (下) に**並んでいます。Perfect network、Good Wi-Fi、5G network、Home DSL (VDSL)、LTE/4G、Satellite (low orbit)、Distant server (another continent)、Weak Wi-Fi、Cafe (crowded Wi-Fi)、Congested home link (bufferbloat)、Train/metro (tunnels)、3G network、Foreign roaming、Satellite (geostationary)、In-flight Wi-Fi、56k modem、Terrible network です。これに自分で (名前を付けて) 保存したものが加わります。プログラムは**常に "Perfect network" で起動します** (何かを設定するまでは、何も劣化しません)。組み込みのプリセットは削除できません。それらに対しては "Delete" ボタンが無効になります。

無線系のプリセットは、パケットを1つずつではなく**連続して**失います。無線回線がまさにそうだからです。フェージング、干渉、ハンドオーバーによって、一定の間チャネルが奪われます。有線系 (DSL、56k モデム) はパケットロスを均等に散らしたままです。そこでのパケットロスは、無線が途切れるのではなく、キューが満杯になることだからです。

数値は、測定結果がある限り、公表されている測定値に基づいています (衛星とモバイルは Ookla® Speedtest® の中央値、Starlink の 15 秒ごとの再構成、機内 Wi-Fi、Wi-Fi パケットが連続して何個失われるかについては査読済みの研究です)。すべての数値の出典は、`beantester/presets.py` の冒頭のコメントブロックに、著者、掲載誌、DOI とともに記載されているので、信用するのではなく自分で確認できます。そうした数値が存在しない場合 (「弱い Wi-Fi」は測定できる量ではありません) は、出典をでっち上げる代わりに、値の隣のコメントでその旨を述べています。いくつかは、ひと言触れておく価値があります。

- **Satellite (low orbit)** - Starlink をモデルにしています。定常状態は良好です (ping は約 40 ms、100 Mbit/s)。特徴的なのは 15 秒ごとの再構成で、一瞬だけ送信が止まり、パケットロスとしてではなく、ときどき起きる遅延スパイクとして現れます。
- **Distant server (another continent)** - 何も壊れていない高速な回線で、ただ遠いだけです (ping は約 120 ms)。おしゃべりなプロトコルや、サーバーがすぐ隣にあると仮定したコードを暴き出すのは、このプリセットです。
- **Congested home link (bufferbloat)** - 何もしていなければ問題なく見えます (ping は 20 ms)。劣化の正体はキューです。⚠️ **アプリケーションが実際に回線を飽和させたときにだけ効きます。** バッファーは速度制限の一部なので、テスト用のトラフィックをちょろちょろ流しても、下り 8 Mbit/s、上り 1 Mbit/s の素直な回線にしか見えず、ほかには何も起きません。上り 1 Mbit/s を飽和させると、ping が2秒に向かって上昇していくのが見えます。「誰かがバックアップを始めると、ビデオ通話が死ぬ」というケースです。
- **Train/metro (tunnels)** - 一度に数秒間、回線を完全に落とす唯一のプリセットです (30 秒ごとに 3 秒)。そのためアプリケーションは、単に遅くなるだけでなく**再接続**しなければなりません。
- **In-flight Wi-Fi** - 典型的な衛星方式です。ping は約 750 ms、パケットロスは 7% で、これは最悪値ではなく、測定された中央値です。新しい低軌道の機器を積んだ航空機は、代わりに "Satellite (low orbit)" のように振る舞います。

プロファイルは**回線の性質**を保存します。パケットロス、そのうちどれだけが連続して届くか、破損、重複、遅延、ジッター、遅延スパイク、回線の断 (フラッピング)、速度制限、バッファーです。それ以外 - 対象、宛先、ブロック、RST、MTU、NAT の失効、スケジュール、シード - は含まれません。プロファイルを保存するとき、現在オンになっているそれらの項目について警告が出ます。完全な設定を保存するには **"Save file..."** を使ってください。プロファイルまたはプリセットを選ぶと、そのプリセットが言及していないものも含めて、それらのフィールドの**すべて**が一度に設定されます。言及されていないものは既定値に戻るので、"Perfect network" は本当に完璧になります。以前のバージョンで保存したプロファイルは、そのまま読み込めます。

CLI (`--preset`) では、プリセットを**正規の id**、または**任意の UI 言語での名前**で指定できます (大文字小文字とポーランド語のダイアクリティカルマークは区別されません。`"Perfect network"` でも動きます)。id は次のとおりです。
`presets.perfect`、`presets.good_wifi`、`presets.5g`、`presets.dsl`、`presets.lte`、`presets.leo`、
`presets.distant`、`presets.weak_wifi`、`presets.cafe`、`presets.bufferbloat`、`presets.metro`、
`presets.3g`、`presets.roaming`、`presets.satellite`、`presets.inflight`、`presets.modem56k`、
`presets.terrible`。

## フィルター構文 (プロセス / IP / ポート)

3つのフィールド - **Target process**、**IP**、**port** ("Target destination" 内) - は、同じミニ言語を使います。今後ツールにフィルターのフィールドが増えても、同じ構文が使われます。GUI と CLI (`--target`、`--dst-ip`、`--dst-port`) でまったく同じように動作します。

### 構成要素

| 表記 | 意味 | 例 |
|---|---|---|
| `a,b,c` | **リスト** - いずれかの値に一致すれば一致です | `80,443` |
| `a-b` | **範囲**、両端を**含みます** | `8000-8100`, `10.0.0.1-10.0.0.50` |
| `>` `<` `>=` `<=` | **比較** (数値、IP ではアドレスの値) | `>1024`, `<=80`, `>10.0.0.5` |
| `!` | **除外** - 「~以外」 | `!53` |
| `*` `?` | **ワイルドカード** (`*` = 任意の連続、`?` = 1文字) | `chrome*`, `192.168.1.*` |
| `re:` | **正規表現** (Python の `re`、大文字小文字を区別しません) | `re:^chrome\.exe$` |
| `x.x.x.x/n` | **CIDR** (IP フィールドのみ) | `192.168.1.0/24`, `2001:db8::/32` |

空のフィールド = **すべて**です (フィルタリングなし)。カンマや項の前後の空白は無視されます。

### 項の組み合わせ方

```
matches = (no positive terms OR any positive term matches) AND no "!" term matches
```

言い換えると、**肯定の項は足し合わされ (OR)、除外は差し引かれます (AND NOT)**。項の順序は関係ありません。`80,!53` と `!53,80` はまったく同じ意味です。

| 入力 | 意味 |
|---|---|
| *(空)* | すべて |
| `443` | ポート 443 のみ |
| `80,443` | 80 **または** 443 のみ |
| `!53` | 53 **以外のすべて** (肯定の項がありません) |
| `!53,!443` | 53 と 443 以外のすべて |
| `1000-2000,!1500` | 1000-2000 から 1500 を除いたもの |
| `>1024,!3389` | 1024 より大きいすべてから 3389 を除いたもの |
| `80,443,8000-8100,>9000,!8080` | 80、443、8000-8100、9000 より大きいすべて - ただし 8080 を除く |

### "Target process" フィールド

項は**名前**でも **PID** でもよく、1つのフィールドに混在させられます。

* **名前** (`*` も `re:` もないもの) は、**大文字小文字を区別しない部分文字列**として働きます。`chrome` は `chrome.exe` と `chromedriver.exe` の**両方**に一致します。(以前からずっとこの動作で、古い設定やプロファイルが引き続き動くよう、意図的に残しています。)
* **PID** は、数字だけ (`12345`)、範囲 (`1000-2000`)、または比較 (`>1000`) です。
* **ワイルドカード**と **`re:`** は、プロセスの**名前**に対して一致します。
* 比較 `>` `<` `>=` `<=` は、**PID** (数値) に対してのみ意味があります。`>chrome` は**エラー**です。何にも一致しないまま黙っているのではなく、ツールがそのことを明示します。

```
chrome.exe                     all processes with "chrome.exe" in the name
chrome, !chromedriver          chrome but NOT chromedriver
chrome.exe, firefox.exe        two apps at once
12345                          a specific PID
12345, 6789                    two PIDs
1000-2000                      all processes with a PID in that range
>1000                          all processes with a PID > 1000
firefox*                       a name starting with "firefox"
re:^(chrome|firefox)\.exe$      exactly chrome.exe or firefox.exe
firefox, 12345                 a name and a PID in one field
```

一致したすべてのプロセスがそれぞれのローカルポートを提供し、対象の指定はそれらのポートの**和集合**をカバーします。ポートの集合は、セッション中、システムのソケットイベントから最新の状態に保たれるので、プロセスが新しく開いた接続は、開いた時点で捕捉されます (実際の WinDivert がない場合は、ソケットテーブルを1秒に数回スキャンし直す方式に切り替わります)。

**「そのローカルポート」とは、実際にはどういう意味か。** パケットが運ぶのはアドレスとポートであって、プログラム名ではありません。そのため、ツールは「Chrome」を直接照合できません。ツールは、そのプロセスが所有する**ローカル**ポートを調べ、そのローカルポートを持つすべてのパケットに一致させます。

そのため、ここに `443` が現れることは決してありません。Chrome がページを読み込むとき、`443` は**サーバー側**のポートです。その接続での Chrome 自身の側は `15597` のような一時的なポートで、その番号は同時には1つのプロセスにしか属さないので、トラフィックを正確に捕捉できます。

一部のポートは仕組みが異なります。mDNS (5353)、SSDP (1900)、DHCP (67/68) は、複数のプログラムが同時に保持しています。プログラムがネットワーク上のデバイスを見つける方法がそうだからです。そこではポート番号からそのトラフィックの持ち主がわからなくなるため、すべてか無かの二択になります。そのポートのすべてが劣化されるか、何も劣化されないかのどちらかです。そうなったときは、ログでそのことが伝えられ、どちらが適用されたかも示されます。通常のトラフィックには影響しません。

### "IP" フィールド

**IPv4 と IPv6** に対応しています。ルールが、別のファミリーのアドレスに一致することは決してありません。IPv4 のルールは IPv6 のアドレスを捕捉せず、その逆も同様です (1つのフィールドに安全に混在させられます)。

```
1.2.3.4                        one address
1.2.3.4, 8.8.8.8               two addresses
10.0.0.1-10.0.0.50             a range (both ends inclusive)
10.0.0.1-10.0.0.50, !10.0.0.7  a range with a hole
192.168.1.0/24                 a whole subnet (CIDR)
192.168.1.*                    the same via wildcard
!8.8.8.8                       everything except 8.8.8.8
>10.0.0.5                      addresses "greater" than 10.0.0.5
2001:db8::/32                  an IPv6 subnet
2001:db8::1-2001:db8::ff       an IPv6 range
10.0.0.0/8, 2001:db8::/32      IPv4 and IPv6 in one field
re:^10\.                        anything starting with 10.
```

アドレスの表記は問われません。`2001:0db8:0000:0000:0000:0000:0000:0001` と `2001:db8::1` は、ツールにとって同じアドレスです。

### "port" フィールド

```
443                            one port
80,443                         a list
8000-8100                      a range (both ends inclusive)
>1024                          high ports
<=1024                         privileged ports
!53                            everything except DNS
80,443,8000-8100,!8080         a mix
```

許可される範囲は **0-65535** です。`99999` は、黙って読み飛ばされるのではなく、エラーになります。

### 正規表現 (`re:`)

`re:` プレフィックスは**必須**です。付けない項は、ただの値です。そのため `chrome.exe` は (ドットはドットとして扱われる) ファイル名であり、正規表現のパターンではありません。

| パターン | 捕捉するもの |
|---|---|
| `re:^chrome` | `chrome` で始まる名前 |
| `re:^chrome\.exe$` | **ちょうど** `chrome.exe` (`chromedriver.exe` は含まない) |
| `re:^(chrome\|firefox)\.exe$` | ちょうど `chrome.exe` または `firefox.exe` |
| `re:(node\|python)` | `node` または `python` を含む名前 |
| `re:^\d+$` | (ポート/PID フィールドで) 数字だけのもの |
| `re:^10\.` | (IP フィールドで) `10.` で始まるアドレス |
| `!re:^chrome` | `chrome` で始まる名前**以外のすべて** |

パターンは**大文字小文字を区別せず**、どこでも一致を探します (`re.search`)。先頭から末尾までの一致にしたい場合は、`^` と `$` を使ってください。

**正規表現の中のカンマは、バックスラッシュでエスケープする必要があります** (`\,`)。カンマは項の区切りだからです。

```
re:^ch.{1\,8}e\.exe$          correct - {1,8} with a backslash before the comma
re:^ch.{1,8}e\.exe$           WRONG - it is split into "re:^ch.{1" and "8}e\.exe$"
```

### つまずきやすいケース

* **`chrome` は `chromedriver` にも一致しますが、`chrome.exe` は一致しません。** 名前だけの項は*部分文字列*です。"chrome" というテキストは `chromedriver.exe` に含まれますが、"chrome.exe" というテキストは含まれません (そこでは `chrome` + `driver.exe` になっています)。したがって `chrome.exe` -> `chrome.exe` だけです。`chrome` -> `chrome.exe` **と** `chromedriver.exe` です。
* **`chrome*` は見た目より広く一致します。** 星は「任意の連続」なので、`chrome*` は `chrome` とまったく同じように `chromedriver.exe` を捕捉します。ちょうど1つのアプリにしたい場合は、`re:^chrome\.exe$` を使うか、除外を加えてください: `chrome, !chromedriver`。
* **ポートフィールドの `8*` は、数字のテキストに対するワイルドカード**なので、`8`、`80`、`8080`、`8443` を捕捉しますが、`443` は捕捉**しません**。ほぼ間違いなく、意図したのは範囲の `8000-8999` でしょう。ポートのワイルドカードは、意識して使ってください。
* **`80,443,!8080` は、ただの `80,443` です。** 何も削らない除外はエラーではなく、単に意味がないだけです。
* **`!53` は、ポートのないトラフィック (例: ICMP/ping) も対象にします。** 「53 以外のすべて」は、文字どおり「ポート 53 ではないすべて」を意味し、ICMP パケットはポート 53 ではありません。TCP/UDP だけにしたい場合は、**Traffic filter** で絞り込んでください。
* **空の項は、「すべて」ではなくエラーです。** `80,,443` や `80,!` は拒否されます。**フィールド全体**が空なら「すべて」を意味します。
* **IP とポートは AND で組み合わさります。** `IP=10.0.0.0/8` + `port=443` は、「10.x ネットワークへのトラフィックで、**かつ同時に**ポート 443 のもの」を意味します。「どちらか」にしたい場合は、もう一方のフィールドを空にして、2回実行してください。
* **`>chrome` はエラーです。** 比較は数値 (PID) に対して働き、名前には働きません。
* **`2000-1000` はエラーです** (範囲が逆)。空の集合にはなりません。
* **ワイルドカードは正規表現ではありません。** `chrome*` の星は「任意の連続」を意味します。`re:chrome*` では「文字 `e` の0回以上の繰り返し」を意味します。`re:` と書いたなら、書いているのは正規表現です。
* **繰り返しの中の繰り返しは、遅すぎるとして拒否されます。** 例えば `re:^(\w+)+$` や `re:^([0-9:]+)+$` です。こうしたパターンは、ほぼ一致する名前やアドレスが1つあるだけで数秒かかることがあり、アドレスはパケットごとに照合されます。繰り返しは1回だけ書いてください: `re:^\w+$`。

構文エラーはすべて**即座に**報告されます。GUI ではフィールドが赤くなり、下に理由が (UI の言語で) 表示され、CLI は読みやすい `error: ...` で終了します。黙って「何も動かない」ことは決してありません。

## 統計 (カウンターの意味)

スループットのグラフには、値つきの Y 軸、グリッド、「きれいに」丸められた目盛り、隅に現在の down/up の読み取り値があります。Download/Upload (KB/s のリアルタイム値)、Packets (通過した数)、Queued (待機中 - 遅延/制限で増えます)、Lost、Loss runs (そのパケットロスが何回の連続で届いたか - "Losses in a row" を参照)、Corrupted、Duplicated、Buffer overflow (ツールが過負荷のときに破棄されたもの)、Dropped at stop (STOP が押された時点でまだキューにあったもの)、Send failed (ツールは取得したが、回線に戻せなかったもの - 接続が落ちた、またはドライバーが拒否した)、Rate-limit drop (速度制限バッファーが満杯で破棄されたもの - パケットロスや "Buffer overflow" とは別に数えます)、SYN dropped、MTU dropped、NAT expired、RST torn、LAN: internet cut off、Local network cut、RST sent があります。

**数値のコピー。** "Live" または "Session" の任意の値を右クリックすると、その値、またはタブ全体をコピーできます。各パネルにはボタンもあります。グリッドの下の "Copy counters" と、再現用ボタンの隣の "Copy session details" で、画面に表示されているとおりに、キャプションと単位も含めて、すべての行をコピーします。バグ報告に便利です。セッションパネルには、コンピューター名、そのアドレス、シード、取得の対象範囲が載っています。

それらのうち最後の3つ - "Buffer overflow"、"Dropped at stop"、"Send failed" - は、シミュレートを頼まれた回線ではなく、ツールがパケットを失っているものです。これらは数えられ、seen/delivered/dropped の計算の整合性を保ちますが、意図的に "Effective loss" には**含まれません**。そのいずれかが 0 でないなら、測定しているパケットロスの一部はこちら側の責任です。

### バグの再現 ("Session and reproduction" パネル)

バグが起きた後で、まったく同じ条件を再現できるように設計されています。

- **Seed (effective)** - Seed フィールドを空にしていても、プログラムは具体的なシードを引いて記憶します。後でそれを Seed フィールドに入力して再実行すれば、同じ抽選結果が得られます。
- **Repeatable flapping** - 回線の断のパターンはセッションの開始時点から測られるので、同じ設定なら実行間でまったく同じように繰り返されます (システムクロックに依存しません)。
- **What the seed reproduces** - シードが再現するのは、エンジンの**判断** (どのパケットを破棄、破損、重複させるか、どれだけ遅延させるか) であり、**パケット数**ではありません。回線を通るトラフィックは、その瞬間にアプリケーションとシステムが何をするかに依存するため、同じシードの2回の実行は同じ*割合* (例: どちらもパケットロス 15.8%) になりますが、パケット単位で同一のカウンターにはなりません。CI で比較するときは、生のパケット数ではなく、割合 (%) を使ってください。
- **Start / Duration / Effective loss / Queue peak / Down-up peak** - 実行の概要がすばやくわかります。
- **"Effective loss" が数えるもの** - 狙ったトラフィックのうち、**このツール**が壊した割合で、**すべての**劣化にわたります。設定した Loss に加えて、レート制限による破棄、ブロック、LAN の遮断、ローカルネットワークの遮断、回線の断、接続のリセット、SYN の破棄、MTU の破棄、NAT の失効です。対象を設定している場合は、その対象のトラフィックだけが数えられるので、他のアプリケーションに薄められることはありません。**ツール**が捨てたパケットは、意図的に除外されます。"Buffer overflow"、"Dropped at stop"、"Send failed" は、回線ではなくツール自身の失敗であり、それぞれ専用のカウンターがあります。レポートの `effective_loss_pct` は同じ数値で、`packets_in_scope` の隣にあります。
- **Driver queue wait (peak)** - このツールがパケットを受け取った時点で、そのパケットが WinDivert の内部で**すでに**待っていた最長の時間です。推定ではなく測定値です。ドライバーはすべてのパケットに取得時刻を刻み、ツールはそれを1秒に20回サンプリングします。アイドル状態のマシンではミリ秒の何分の一かです (ここでの実測: 0.05-0.16 ms)。これが増えるなら、ツールは、他のどのカウンターにも現れない遅延を加えています。それがツール自身のキューより前の、ドライバーのキューで起きているからです。50 ms に達すると、ログとイベント一覧でその旨が伝えられます。ドライバーのない `--simulate` では空欄です。
- **It measures this machine, not the internet.** ツールが見るのは、このコンピューターのネットワークスタックを通過するパケットです。そのため、ネットワークの途中で失われたパケット (戻ってこなかった応答) はここには届かず、ここでは何も数えられません。30 パケットの ping が1つの応答を失ってもきれいに終わった場合、接続の行には **59** パケットと、破棄**ゼロ**が表示されますが、どちらの数字も正しいのです。30 個のリクエストが出ていき、29 個の応答が戻り、ツールはそのどれも壊していません。エンドツーエンドのパケットロスは、アプリケーション自身の数値 (または `ping` の "Lost") を見るためのものです。
- **Data used** - Downloaded / Uploaded / Total (MB) を開始からの累計で、加えてセッションの平均スループットを表示します。アプリがどれだけのデータを使ったかが、すぐわかります。(レポートには "attempted MB" もあります。パケットロスや制限を差し引く前に、アプリが送ろうとした量です。)
- **Event log** はタイムスタンプつきで、開始、設定の変更、シナリオのステップ、切断、そして自分で付けたバグのマーカーを記録します。列見出しのクリックで**並べ替え**られます。
- **Mark the moment of a bug** - バグが見えたまさにその瞬間にクリックします。タイムスタンプつきのマーカーがログに挿入されます。
- **Save reproduction report** - すべてを収めた1つの JSON ファイルです。シード、すべての設定、カウンター、メトリクス、イベントログ、接続、そして条件を再現する**そのまま使える CLI コマンド**が入っています。**セッションが動いた WinDivert のキュー** (`session.driver_queue`: 長さ、時間、サイズ) も記録されます。これはドライバー自身のバッファーで、このツールより前段にあり、3つの値は固定の遅延ではなく上限です。ツールが追いついている間、パケットはそこでほとんど待ちません (上の **Driver queue wait (peak)** を参照)。満杯になるのは、ツールが遅れたときだけです。そうなるとパケットはより長く待たされ、満杯になるとドライバーは、このツールが見る前にパケットを破棄します。キューを小さくしても、その待ち時間はなくなりません。どのカウンターにも表れない、失われたパケットに変わるだけなので、ツールはドライバー自身の設定には手を加えません。手元にないマシンからのレポートでも、どのキューがその数値を生んだかがわかります。同じ3つの値は、START 時にログにも書き込まれます。
- **Copy CLI command** - そのままクリップボードへ: `BeanNetworkTester.exe --seed ... --loss ...
  --duration ...` (コマンドはビルドに合わせて変わります。リポジトリからなら `python bean_network_tester.py ...` になります)。
- **レポートとコマンドが表すもの** - フォームではなく、直近のセッションです。START が渡した設定を、"Apply changes" のたびに更新したもので、シードとシナリオ (`--scenario`、ループした場合は `--loop` も) を含みます。入力したが適用していない変更と、STOP の後に読み込んだプロファイルは含まれません。シナリオの実行中は、"Apply changes" がその後のステップの土台になるため、コマンドにもそれらの設定が反映されます。プログラムに同梱されているシナリオは、プログラムのフォルダーからの名前で指定され (ソースからなら `scenarios\...`、`.exe` の隣なら `_internal\scenarios\...`)、コマンドはどのフォルダーで実行してもそれを見つけます。それ以外のファイルは、選んだパスで指定されます。最初のセッションの前は、**Copy CLI command** がフォームの設定をコピーします。

## 設定ファイル

"Save/Load file" ボタンは、すべての設定を JSON に書き出します。同じファイルは、`--config` で CLI でも使えます。優先順位は、既定値 < ファイル < プリセット < フラグです。

ファイルを読み込むときに、すべての値の種類が検証され、シナリオのステップも同じ方法で検証されます。スイッチ (`lan_mode`、`internet_only`、`narrow_filter`...) は `true` か `false`、または `1` か `0` です。テキストの `"false"` は、「オン」として読まれるのではなく、拒否されます。`filter` は `--filter` の選択肢のいずれかで、`seed` は整数です (ランダムにするには `-1`)。種類が正しくない値があると、CLI は終了コード `3` で停止し、その設定の名前を挙げます。ウィンドウでも同じメッセージが表示され、フォームは元のまま変わりません。

## コマンドラインモード (CLI)

CLI は GUI と**同じ `BeanNetworkTester.exe`** から動きます。何か引数を付けて起動するとテキストモードが始まり (ウィンドウも tkinter もなし)、引数なしなら GUI になります。メッセージと `--help` は常に英語です。

```bat
:: GUI
BeanNetworkTester.exe

:: CLI (from the same exe)
BeanNetworkTester.exe --loss 5 --latency 100 --down 1024 --target chrome.exe
BeanNetworkTester.exe --preset "3G network" --duration 60
```

> リポジトリから (ビルドなしで) 作業していますか？ その場合は、すべての `BeanNetworkTester.exe` を
> `python bean_network_tester.py` に置き換えてください。フラグと終了コードはすべて同一です。

### 終了コード (CI/CD との約束)

終了のしかたごとに専用のコードがあるので、パイプラインはテキストを解析する必要がありません。

| コード | 名前 | 発生する場面 |
|---|---|---|
| `0` | ok | セッションが実行され、すべてのチェックに合格した |
| `1` | runtime | 開始できなかった (`pydivert` がない、ドライバー、エンジンの失敗) |
| `2` | usage | コマンドラインが不正 (未知のフラグ、型の誤り) - argparse のコード |
| `3` | config | 設定が不正: 式、スケジュール、範囲、プリセット、設定ファイル |
| `4` | scenario | シナリオファイルがない、または形式が不正 |
| `5` | io | 成果物を書き出せなかった (再現レポート、保存した設定) |
| `6` | assertion | 実行は成功したが、`--min-packets` / `--fail-on-no-traffic` に合格しなかった |
| `7` | permission | 管理者権限が必要だが、ない |
| `130` | interrupted | Ctrl+C (SIGINT) |
| `143` | terminated | SIGTERM (ジョブのキャンセル、`docker stop`)、Ctrl+Break、またはコンソールウィンドウを閉じた |

`BeanNetworkTester.exe --help` でも同じコードが表示されます。

### 出力: ログは stderr、データは stdout

- **stderr** - 人間向けのログで、先頭に `[bean]` が付きます (開始、シード、エラー、停止の理由)。
- **stdout** - データです。レポートの行と、`--format json` のときは **NDJSON** (1行に1つの JSON オブジェクト。連続する `sample` オブジェクトと、終了コード、シード、再現コマンドを含む最後の `summary`) です。

```bat
BeanNetworkTester.exe --simulate --duration 30 --format json > run.ndjson
```

### CLI の全パラメーター

**回線の劣化**

| フラグ | 単位 | 説明 |
|---|---|---|
| `--loss` | % | 破棄されるパケットの割合 |
| `--loss-burst` | パケット | 連続して失われるパケットの平均数 (0 = パケットロスを均等に散らす)。`--loss` の形を決めるもので、上乗せはしない |
| `--corrupt` | % | ビットが反転するパケットの割合 |
| `--dup` | % | 2回送られるパケットの割合 |
| `--latency` | ms | すべてのパケットに加える固定の遅延 |
| `--jitter` | ms | 遅延のランダムな変動 (+/-) |
| `--down` `--up` | KB/s | スループットの制限 (0 = 制限なし) |
| `--buffer` | ms | 速度制限用のリンクバッファー (0 = 制限なし)。キューの遅延を抑え、超過分は "Rate-limit drop" として扱われる |
| `--spike-prob` `--spike-ms` | % / ms | 指定した確率で追加の遅延を加える |
| `--syn-drop` | % | 破棄される TCP SYN パケットの割合 |
| `--max-size` | B | 「MTU ブラックホール」 - N バイトより大きいパケットを破棄する (0 = オフ) |
| `--nat-timeout` | s | N 秒の無通信の後、NAT のマッピングが「消える」 (0 = オフ) |
| `--rst-prob` `--rst-cooldown` | % / s | RST で切断される接続の割合と、切断を維持する時間 |
| `--flap-period` `--flap-down` | s / % | 周期的な回線の断: 頻度と、周期のうちどれだけの割合か |
| `--rate-schedule` | - | 変化するスループット: KB/s 単位の `"time:download:upload,..."` をループ。時間は 0 より大きく 86400 秒以下、速度は 0 (制限なし) から 10000000 |
| `--asym` | - | アップロードに専用の値を与える。付けない場合は、1組の数値が両方向に適用される (既定) |
| `--loss-up` `--corrupt-up` `--dup-up` | % | 同じ3つの劣化を、このマシンが送信するパケットに対して設定する。`--asym` と一緒のときだけ使われる |
| `--latency-up` `--jitter-up` | ms | 遅延とその変動を、このマシンが送信するパケットに対して設定する。`--asym` と一緒のときだけ使われる |
| `--spike-prob-up` `--spike-ms-up` | % / ms | ときどき起きる長い遅延を、このマシンが送信するパケットに対して設定する。`--asym` と一緒のときだけ使われる |
| `--ipv4-only` `--ipv6-only` | - | 片方のアドレスファミリーだけを劣化させる。もう片方は手を加えられずに流れ続ける - これはツールの狙いを定めるもので、プロトコルをブロックするものではない。`--dst-ip` が空 (すべてのアドレスを意味する) でも動作する。両方のフラグを同時に付けると互いに打ち消し合い、何も劣化せず、ログでその旨が伝えられる |
| `--lan-mode` | - | LAN モード: インターネット (パブリックアドレス) を遮断し、ローカルネットワークは残す |
| `--internet-only` | - | その逆: ローカルネットワーク (10.x、172.16-31.x、192.168.x、リンクローカル、CGNAT) を遮断し、インターネットは残す。ループバックは動き続ける。注意: ルーターへの DNS 問い合わせはローカルのトラフィックなので、インターネットも使えなくなることがある |
| `--narrow-filter` | - | `--dst-ip`/`--dst-port` を WinDivert のフィルターに押し込み、劣化できないトラフィックをドライバーが渡してこないようにする (パケットレートが高いときはずっと速い)。START 時のみ。オンの間、統計と接続は絞り込まれたトラフィックだけを対象にする |

**対象の指定** (3つとも完全な[フィルター構文](#フィルター構文-プロセス--ip--ポート)を受け付けます。リスト、
範囲、`!`、`>`、`<`、`>=`、`<=`、ワイルドカード、`re:`、そして `--dst-ip` は加えて CIDR も使えます)

| フラグ | 説明 | 例 |
|---|---|---|
| `--target` | プロセス: 名前、PID、PID の範囲、ワイルドカード、正規表現 | `--target chrome.exe`<br>`--target "chrome,!chromedriver"`<br>`--target ">1000"` |
| `--dst-ip` | リモートの IP アドレス (IPv4 と IPv6) | `--dst-ip 1.2.3.4`<br>`--dst-ip "10.0.0.1-10.0.0.50,!10.0.0.7"`<br>`--dst-ip "192.168.1.0/24"`<br>`--dst-ip "2001:db8::/32"` |
| `--dst-port` | リモートのポート (0-65535) | `--dst-port 443`<br>`--dst-port "80,443,8000-8100"`<br>`--dst-port "!53"`<br>`--dst-port ">1024"` |
| `--filter` | そもそもどのトラフィックを取得するか (IPv4 + IPv6): `both,out,in,tcp,udp,ping,loopback` | `--filter tcp` |

**ブロック (ファイアウォール)** - 選んだ宛先へのトラフィックをすべて破棄します。ブロックは **IP または ポート** のどちらかで作動します (空のフィールドは無視されるので、`--block-port 443` だけなら、どのアドレスへの 443 もブロックします)。[フィルター構文](#フィルター構文-プロセス--ip--ポート)は上と同じです。プロセスの指定に従います (対象のトラフィックだけをブロックします)。

| フラグ | 説明 | 例 |
|---|---|---|
| `--block-ip` | リモートの IP アドレスをブロックする (IPv4 と IPv6) | `--block-ip 1.2.3.4`<br>`--block-ip "10.0.0.0/8,!10.0.0.1"` |
| `--block-port` | リモートのポートをブロックする (0-65535) | `--block-port 443`<br>`--block-port "80,443,8000-8100"` |
| `--block-reject` | ブロックした TCP 接続を、黙って破棄する代わりに拒否する | `--block-port 443 --block-reject` |

**拒否か、無視か** - 既定では、ブロックされた接続には一切応答がなく、テスト対象のプログラムは、自分で諦めるまで待ち続けます。`--block-reject` を付けると代わりに拒否され、プログラムは約2秒で "connection refused" を報告します。実際に閉じているポートに対する場合とまったく同じです。多くのアプリケーションでは、この2つは別々のコードパスで、片方しか見たことのないテストスイートは、片方しかテストしていません。拒否の対象は、**このコンピューターが開始する、TCP の接続**です。UDP のトラフィックと、外部から届く接続は、これまでどおり黙ってブロックされます。

> `cmd.exe`/PowerShell では、式にカンマ、`!`、`>`、`<`、`*`、`^` が含まれる場合は**式を引用符で囲んでください**。そうしないと、シェルが独自に解釈します (`cmd.exe` は単独の `^` を取り除くので、`re:^edge` は `re:edge` として届きます)。セッションを再現するコマンド
> (`Copy CLI command` と `Reproduce:` の行) は、自動で引用符を付けます。

| フラグ | 説明 |
|---|---|
| `-v`, `--verbose` | プログラムの動作をログに出す: 有効な設定、コンパイルされたフィルター、解決されたプロセスのポート、シナリオのステップ、ドライバーの開閉 |
| `-q`, `--quiet` | エラーのみ: ログも定期レポートも出さない |
| `--log-level {error,warn,info,debug}` | ログレベルを明示する (`-v`/`-q` より優先される) |
| `--log-file FILE` | ログ (とレポート) をファイルにも追記する - そのまま CI の成果物になる |
| `--format {text,json}` | stdout の形式: 人間向けのテキスト、またはパイプライン向けの NDJSON |

**CI/CD 向け**

| フラグ | 説明 |
|---|---|
| `--dry-run` | 設定をチェックして終了する (ドライバーには触れず、トラフィックも通さない) - パイプラインで設定ファイルを検証するのに最適。`--scenario` も読み込まれて検証されるので、ドライランと本番の実行が一致する |
| `--print-config` | 有効な設定 (`defaults < file < preset < flags` の適用後) を JSON で出力して終了する |
| `--min-packets N` | N 個より少ないパケットしか捕捉されなかった場合、終了コード `6` で終了する |
| `--fail-on-no-traffic` | `--min-packets 1` の短縮形 - **何も捕捉しなかったフィルターを検出する** |
| `--doctor` | 環境 (管理者権限、`pydivert`、WinDivert ドライバーの状態、`%TEMP%` の残骸、管理者権限なしでプログラムのフォルダーに書き込めるか、時計がどれだけ細かく時間を測るか) をチェックして終了する |
| `--cleanup-driver` | 動かなくなった WinDivert ドライバーをアンロードして (ロックされた `.sys` ファイルを**システムの再起動なしで**解放して) 終了する。各行が、1つのサービスに何が起きたかを伝える。サービスを停止できなかった場合でも、終了コードは `0` |

優先順位は、**既定値 < `--config` < `--preset` < フラグ** です。完全な一覧は
`BeanNetworkTester.exe --help` で確認できます。

### 対象指定の例

```bat
:: only the browser, but not its test driver
BeanNetworkTester.exe --loss 10 --target "chrome,!chromedriver"

:: only HTTPS traffic to a test server and its backup address
BeanNetworkTester.exe --latency 300 --dst-ip "10.0.0.5,10.0.0.9" --dst-port 443

:: the whole test subnet except one host, on application ports
BeanNetworkTester.exe --down 128 --dst-ip "10.0.0.0/24,!10.0.0.1" --dst-port "8000-8100"

:: everything EXCEPT DNS (so name resolution works while the rest breaks)
BeanNetworkTester.exe --loss 20 --dst-port "!53"

:: high-PID processes, traffic to IPv6
BeanNetworkTester.exe --jitter 80 --target ">1000" --dst-ip "2001:db8::/32"
```

### ブロックの例 (ファイアウォール)

```bat
:: cut the app off from an external API (the server is "down")
BeanNetworkTester.exe --block-ip 203.0.113.10

:: block all HTTPS - see how the app copes with no connection
BeanNetworkTester.exe --block-port 443

:: block several ports OR the whole backend subnet (blocking is IP OR port)
BeanNetworkTester.exe --block-port "8080,9090" --block-ip 203.0.113.0/24

:: impair only your app's traffic, and cut its link to the payment server entirely
BeanNetworkTester.exe --latency 200 --target myapp.exe --block-ip 198.51.100.7
```

### `--simulate` モード (Windows も管理者権限もなしでテスト)

合成トラフィックによるプレビューです。WinDivert も特権も必要ありません。

```bat
BeanNetworkTester.exe --simulate --down 500 --loss 10 --duration 4 --interval 1
```

### CLI での再現性とシナリオ

```bat
BeanNetworkTester.exe --simulate --seed 42 --loss 20 --duration 10
BeanNetworkTester.exe --simulate --scenario scenarios/cafe-wifi.json
```

`scenarios/<name>.json` (または `_internal\scenarios\<name>.json`) を指定すると、プログラムに同梱されているシナリオを、どのフォルダーからでも開けます。カレントフォルダーにそのパスのファイルがある場合は、そのファイルが使われます。

シードは、同じパケット列に対して、**パケットごとの判断**が同一になることを保証します。シナリオのステップは累積的で (それぞれが状態にパッチを当てます)、`action: reset_tcp` は、その時点で TCP 接続を切断します。シナリオファイルは**開いたときに検証されます**。適当な JSON は「ステップ数 0 のシナリオ」ではなく、読みやすいエラーで終わり、ステップの設定もフォームと同じルールで検査されるので、プログラムが使えない値は、実行の途中で止まる代わりに、ステップ番号つきで名指しされます。

CLI の実行はどれも、最後に**有効なシード**と、それを再現するそのまま使えるコマンドを出力して終わります。コマンドには、入力したとおりの `--scenario` ファイルと、実行にあった場合は `--loop` と `--simulate` が含まれます。`--repro-out file.json` を付けると、同じコマンドを含む完全な再現レポートが保存されます。

## Connectionsページの列

17 列あり、すべてヘッダーをクリックして並べ替えられ、それぞれのヘッダーのツールチップにも同じ説明があります。

| 列 | 内容 |
|---|---|
| `process` | ローカルポートを所有しているプロセス。`?` は名前を解決できなかったという意味です - 管理者として実行してください。 |
| `PID` | ローカルポートを所有しているプロセスの ID。パケットを取得した時点で解決されます。 |
| `proto` | トランスポートプロトコル: TCP / UDP / ICMP / IP。 |
| `remote IP` | このマシンが通信している相手のアドレス。行を右クリックすると、劣化の対象をそのアドレスに限定できます。 |
| `r.port` | リモート側のポート (443 = HTTPS、53 = DNS、80 = HTTP)。ping のようにポートのないトラフィックでは空です。 |
| `l.port` | このマシン側のポート - 接続をプロセスに結び付けるものです。ping/ICMP では空で、そうした行にプロセス名がたいていない理由でもあります。 |
| `packets` | その接続が現れてから見たパケット数。 |
| `impaired?` | その接続が、このセッションで**劣化の対象範囲に入っていたか**どうか - 見ているだけではなく、劣化されたかどうかです。接続が閉じた後も記録として `yes` のまま残ります。対象を設定していなければ、すべてが範囲内です。 |
| `dropped` | アクティブな劣化 (パケットロス、回線の断、LAN モード、"Internet only"、リセットなど) によって、この接続で破棄されたパケット数。 |
| `down` | アプリケーションに実際に**届いた**データ - ダウンロードした量。セッションパネルが "Downloaded (MB)" と呼ぶものと同じ量です。 |
| `up` | このマシンから実際に**出ていった**データ - アプリケーションがアップロードした量。 |
| `total` | 届いたダウンロードと届いたアップロードの合計。 |
| `down seen` | 劣化の前に、ツールが入ってくる方向で**取得した**データ - その接続が差し出したもの。 |
| `up seen` | ツールが出ていく方向で**取得した**データ - アプリケーションが送ろうとしたもの。 |
| `avg[B]` | その接続の平均パケットサイズ (合計バイト数 / パケット数)。 |
| `time[s]` | このセッションで、その接続の最初のパケットと最後のパケットの間の秒数。 |
| `idle[s]` | 最後のパケットからの秒数。セッションが停止すると、カウントも止まります。 |

**5つのトラフィック列は、それぞれ単位を持ちます。** 各セルは、B、KB、MB、GB のうち収まるものの単位で表示されるため、5 GB のフローは `5242880.0` ではなく `5.00 GB` と表示され、90 バイトの DNS 応答は `0.0` ではなく `90 B` と表示されます。テーブルの下のフッターの合計も同様です。`avg` はパケットサイズなので、バイトのままです。並べ替えと CSV へのエクスポートには影響しません - どちらも、セルのテキストではなく、生のバイト数に対して動作します。

**「届いた量」と「見た量」のペアが、このテーブルの要点です。** 何も劣化させていなければ、両者は等しくなります。パケットロスや速度制限を加えると差が生まれ、**その差が、その接続に与えられた損害**です。(分離される前は1組しかなく、劣化の前に取得したバイト数が、「届いた量」を意味する見出しの下に入っていました。そのため、アプリケーションが 0.4 MB しか受け取っていないのに、5 MB 受信と表示される行がありえました。)

## CSVエクスポート

2つのボタンが2つのファイルを書き出し、その動作は**意図的に異なります**。どちらも自分用のフォルダー `%LOCALAPPDATA%\BeanNetworkTester` に、プロファイルやウィンドウの状態と一緒に保存されます (ソースから実行している場合は、プロジェクトのルートです)。プログラムは、保存するたびに、フルパスをログに書き込みます。これらはプログラムのフォルダーの外に置かれます。手作業やパッケージマネージャーによる更新はそのフォルダーを置き換えるので、更新でファイルが持っていかれないようにするためです。ほかの場所にすべてを置きたい場合は、`BEAN_DATA_DIR` に好きなフォルダーを設定してください。例えば、ポータブル版と同じ USB メモリです。

このフォルダーは、プログラムが実行されている Windows アカウントのものです。管理者権限のないアカウントで、昇格のプロンプトに同意すると、プログラムは、入力したパスワードの管理者アカウントとして実行され、そのアカウントのフォルダーを使います。そのため、昇格なしで保存したプロファイルは、昇格したときに見えるものとは異なります。"About" と `--doctor` はどちらも使用中のフォルダーを表示するので、どちらを見ているのかを常に確認できます。マシン上のすべてのアカウントで1つのフォルダーを共有するには、管理者が `BEAN_DATA_DIR` をシステム全体の環境変数として設定できます。

| | **Statistics** ("Export CSV", Statistics -> Live) | **Connections** ("Export connections CSV") |
|---|---|---|
| ファイル | `bean_network_tester_stats.csv` | `bean_network_tester_connections.csv` |
| モード | クリックのたびに1行を**追記**します - 実行をまたいでグラフを作れるログです | **上書き**します - 現在のテーブルのスナップショットです |
| 書き込み | アトミックに (一時ファイル + リネーム) 行われるので、書き込み中にクラッシュしてもファイルが切り詰められることはありません | 同じ |
| 検索 / 並べ替え | 該当しません | **反映されます** - ファイルは見ていたものと一致します |
| "Show only the targeted traffic" | **意図的に無視されます** - 下記を参照 | **反映されます** |
| "Row limit" フィールド | 該当しません | **無視されます** - 描画された行だけでなく、フィルターに合う行がすべてエクスポートされます |
| バージョン間で列が変わった場合 | 古いファイルはタイムスタンプ付きの名前に変更され、新しいファイルが始まるので、古いヘッダーの下で行がずれることはありません | 該当しません |
| エンコーディング | BOM なしの UTF-8。ダブルクリックで開くと、Excel はこのようなファイルを Windows のコードページで読むため、その範囲外の文字 (ポーランド語や中国語のプロセス名) が文字化けします。**Data > Get Data > From File > From Text/CSV** から開き、**File Origin** を **65001: Unicode (UTF-8)** に設定してください | 同じ |

統計 CSV が "show only the targeted traffic" のスイッチに従わないのは、追記型のログだからです。ある行では列が1つの意味を持ち、残りの行では別の意味を持つファイルは、それが作られた目的であるスプレッドシートにとって、役に立たないどころか有害です。代わりに**両方**の合計を含んでいる (`bytes_in`/`bytes_out` と `delivered_in_scope_bytes_*`) ので、自分で絞り込んでも、どれがどれかがわかります。**"Capture only the targeted traffic" は、そのようには元に戻せません** - そもそも `packets_seen` が数えたものが変わってしまうからです - ので、すべての行がそれを `capture_narrowed` に記録します。

### 統計 CSV の列

`time`、セッションの取得範囲、続いてすべてのカウンターが、この順序で並びます。

| 列 | 意味 |
|---|---|

| `capture_narrowed` | そのセッションで "Capture only the targeted traffic" が有効だった場合は `yes`。その行のすべての数は、宛先のトラフィック**のみ**を対象にしています。`no` は、その行がトラフィックフィルターを通過したすべてを対象にしているという意味です。この列がないと、`packets_seen` が同じ2つの行が、まったく異なるトラフィックを表している可能性があります |
| `packets_seen` | 取得したパケット |

| `loss_runs` | そのパケットロスが何回の連続で届いたか ("Losses in a row" を参照)。連続長を設定しているのに 0 の場合は、セッションが短くて1つも見られなかったか、パケットロスが 100% で個別の連続がないという意味です |
| `dropped_overflow` | ツール自身のキューが満杯だったために破棄されたもの (下の注記を参照) |

| `dropped_lan` | LAN モードによって破棄されたもの (インターネットは遮断、ローカルネットワークは生きている) |

| `dropped_rate_limit` | 満杯の速度制限バッファーによって破棄されたもの |
| `dropped_at_stop` | セッションが停止したときに、キューにあって捨てられたパケット |

## シナリオファイルの形式

シナリオはタイムラインです。ステップのリストで、各ステップに、秒単位の時刻と、その時点で行うことが書かれています。ファイルは JSON で、オブジェクトか、ステップだけのリストのどちらかです。

```json
{
  "loop": true,
  "steps": [
    { "at": 0,  "settings": { "latency": 20, "jitter": 15, "loss": 1, "down": 1024, "up": 256 } },
    { "at": 20, "settings": { "loss": 3, "down": 512 } },
    { "at": 45, "action": "reset_tcp", "duration": 5 },
    { "at": 60, "settings": { "loss": 0, "flap_period": 0 } }
  ]
}
```

**ファイルレベル**

| キー | 意味 |
|---|---|
| `steps` | 必須 - ステップのリスト。トップレベルの `[ ... ]` だけでも動作し、`loop: false` を意味します。 |
| `loop` | 省略可、既定値は `false`。タイムラインを延々と繰り返し、最後のステップの `at` の後に最初から再開します。最後のステップの設定とアクションは、再開の直前に適用されるため、ループ中はほんの一瞬しか持続しません。最終フェーズを維持したいときは、後ろにもう1つステップを追加してください。 |

**シナリオ実行中の "Apply changes"** - ただちに適用され、以降のすべてのステップは、START がセッションに渡した設定ではなく、それを土台にします。どのステップも触れない設定 (対象プロセス、宛先の指定) は、新しい値が最後まで保たれます。ステップが設定する項目は、次のステップまでしか新しい値が保たれず、次のステップがシナリオの値に戻します。

**ステップレベル** - ステップには `settings`、`action`、またはその両方が必要です。どちらもないステップは、一時停止ではなくエラーです。

| キー | 意味 |
|---|---|
| `at` | 必須 - セッション開始からの秒数 (`>= 0`)。ステップはこれで並べ替えられるので、ファイル内の順序は関係ありません。 |
| `settings` | **部分的な**設定オブジェクト。**累積的**: 各ステップは、前のステップが残した状態にパッチを当てるので、後のステップが元に戻すまで、値は保たれます。 |
| `action` | `reset_tcp` - その時点で、範囲内の TCP 接続を切断します。**これが唯一のアクションです。** 1.3 より前の綴り `reset_now` は削除されたので、まだそれを使っているファイルは、ステップを名指しするメッセージとともに読み込みに失敗します。 |
| `duration` | リセットが接続を落としたままにする秒数 (既定値 `3`)。0 より大きく 3600 以下。`action` と一緒の場合のみ有効です。 |

**`settings` に書ける名前** - ツールにあるどの設定でも、**設定ファイルと同じ名前**で書けます (つまり、コマンドラインのフラグのダッシュをアンダースコアに替えたものです): `loss`、`latency`、`jitter`、
`down`、`up`、`buffer`、`spike_prob`、`flap_period`、`dst_ip`、`block_port`、`target`、
`rate_schedule`、`max_size`、`nat_timeout`、`rst_prob`、`lan_mode`、`internet_only`、そして
そのほかすべてです。
`--print-config` を実行すると、名前の完全な一覧が現在の値とともに出力されます。ステップから変更できないのは、
`filter`、`duration`、`narrow_filter`、`row_limit`、`seed` です。セッションは最初の3つと
`seed` を START 時にしか取り込まず、`row_limit` を読むのはウィンドウのテーブルだけで、エンジンは読みません。
これらのどれかを設定するステップは何も変えません。ファイルは読み込まれ、その旨が通知されます。

**ファイルを読み込むときにすべてが検証され、間違いは自分で名乗り出ます。** 未知の設定、未知のアクション、未知のキー、数値でない `duration`、何もしないステップ、空のステップリスト、または **1000** を超えるステップのリストは、いずれもステップ番号を示すメッセージとともに失敗します。これは聞こえる以上に重要です。以前は、綴りを間違えたキーが**黙って見過ごされ**、`"duraton"` は黙ってリセットを既定の 3 秒のままにし、`"lop"` は黙ってループをオフにしました。どちらの場合も、ツールがファイルを無視しているように見えました。

ステップは**0.1 秒ごと**に刻むタイマーによって適用されるので、1秒未満のタイミングも、その程度の精度で守られます。`--dry-run` はドライバーに触れずに `--scenario` を検証するので、パイプラインでの手軽なチェックになります。

### `scenarios/` に同梱されているシナリオ

`upload-drop-midway.json` 以外はすべてループするので、1つ開始して、そのまま動かし続けられます。

| ファイル | 再現する内容 |
|---|---|
| `cafe-wifi.json` | 85 秒かけて混み合っていくカフェ。まずまずの回線が、約 240 ms の ping、6% のパケットロス、2 Mbit/s へと劣化し、最悪の時点では 12 秒ごとに接続が完全に途切れ、その後回復します。 |
| `mobile-lte-to-3g.json` | LTE のエリアを歩いて出ていく携帯電話。下り 33 Mbit/s が 3G の 0.8 まで落ち、60 秒で **TCP リセットを伴う完全な断**が起き、その後一部回復して LTE に戻ります。リクエストの最中にネットワークが死んだときのアプリの挙動をテストするためのものです。 |
| `congested-vpn.json` | ダウンロードは問題ないまま**アップロード**が崩れる VPN (512 から 160 KB/s)。遅延スパイク、MTU 1400、ときどき起きるリセットを伴います。 |
| `failing-dns.json` | **ポート 53 のみ**を狙います (DNS - TCP 上の DNS には手を加えないようにするには、START の前に Filter を "UDP only" にしてください)。名前解決がパケットロス 60%、ping 1.5 秒まで劣化し、**13 秒間 100% 死に**、その後戻ります。マシンのほかのものはすべて動き続けるので、障害のテストではなく DNS のテストになります。 |
| `overloaded-game-server.json` | 負荷でたわむサーバー。ping、ジッター、パケットロス、重複がすべて一緒に上昇し、パケットの 45% で最大 800 ms の遅延スパイクが起きます。 |
| `same-loss-in-runs.json` | 実行全体で同じ 5% のパケットロスが、4通りの形で届きます。均等に散らばった状態、次に 5、15、40 パケットの連続です。ほかは何も変わらないので、壊れるものがあれば、それはパケットロスの量ではなくパケットロスの**形**のせいです。再接続の経路が機能するかを調べるためのものです。 |
| `upload-drop-midway.json` | **ループしません** - 1回限りです。正常に始まったアップロードが劣化し、転送の途中で TCP リセットとともに**ゼロまで落とされ**、その後一部回復します。再開可能なアップロードや、嘘をつく進捗バーのテスト用です。 |
| `blocked-endpoint.json` | 1つのバックエンド (`203.0.113.0/24`) が 20 秒で**ブロック**され、ほかはすべて動き続け、その後ブロックが解除されます。1つの依存先に対するタイムアウト、再試行、フォールバックのテスト用です。 |

## CI/CDのレシピ

### 1. E2E テストの裏で回線を劣化させる (GitHub Actions、Windows)

テストは 300 ms の遅延と 5% のパケットロスの中で実行されます。シェーパーは 120 秒後に自分で止まるので、「止まらなくなった」ステップが、壊れたネットワークをエージェントに残すことはありません。

```yaml
- name: Start the network shaper (background, self-stopping)
  shell: pwsh
  run: |
    $p = Start-Process -FilePath dist\BeanNetworkTester\BeanNetworkTester.exe `
      -ArgumentList '--latency','300','--loss','5','--duration','120',
                    '--dst-port','443','--fail-on-no-traffic',
                    '--format','json','--log-file','shaper.log' `
      -RedirectStandardOutput shaper.ndjson -PassThru
    "SHAPER_PID=$($p.Id)" >> $env:GITHUB_ENV

- name: Run the E2E suite under bad network
  run: npm run test:e2e

- name: Stop the shaper and check it actually impaired something
  if: always()
  shell: pwsh
  run: |
    Stop-Process -Id $env:SHAPER_PID -ErrorAction SilentlyContinue
    Get-Content shaper.ndjson | Select-Object -Last 1
```

> **注:** バックグラウンドのプロセスは `--duration` を付けて実行してください。これが安全網です。"Stop" のステップが実行されなくても (ジョブのキャンセル、タイムアウト)、セッションは自分で閉じ、ドライバーは解放され、エージェントは通常のネットワークを取り戻します。

### 2. pre-commit / PR での設定の検証 (ドライバーも管理者権限も不要)

```bat
BeanNetworkTester.exe --dry-run --config profiles/bad-3g.json
```
コード `0` = ファイルは有効です。`3` = エラーがあります (読みやすいメッセージが stderr に出ます)。綴りを間違えた設定はエラーとして扱われ、どのキーかが示されます。以前は黙って捨てられていたので、チェックは通ったのに、その設定が抜けたまま実行されていました。

`--dry-run` が確認するのは**設定**であって、マシンではありません。管理者権限やドライバーについては一切尋ねないので、実際にはキャプチャを実行できないビルドエージェントでも `0` を返します。これは意図的です。設定をある場所で検証し、別の場所で実行するのは普通のことだからです。両方の側を確かめたいときは、この2つを組み合わせて実行してください。

```bat
BeanNetworkTester.exe --doctor && BeanNetworkTester.exe --dry-run --config profiles/bad-3g.json
```

### 3. 成果物を残す、短く再現可能な実行

```bat
BeanNetworkTester.exe --preset presets.3g --seed 42 --duration 60 ^
  --repro-out repro.json --format json --fail-on-no-traffic > run.ndjson
```
成果物 (`run.ndjson`、`repro.json`) があれば、条件を 1:1 で再現できます。`repro.json` には、そのまま使える `cli_command` が入っています。

### 4. エージェント環境のクリーンアップ

```bat
BeanNetworkTester.exe --doctor
BeanNetworkTester.exe --cleanup-driver
```

## .exeのビルド

Windows 上で:

```bat
pip install pyinstaller pydivert psutil
pyinstaller --noconfirm BeanNetworkTester.spec
```

結果: **`dist\BeanNetworkTester\BeanNetworkTester.exe`** (exe、WinDivert ドライバー、翻訳、アイコンを含むディレクトリ) です。この1つのファイルが、**GUI と CLI の両方**を動かします。

意図的なビルド上の判断が3つあります (必要がない限り変更しないでください。それぞれが実際のバグを直しています)。

- **console サブシステム** (`--noconsole` ではない): そうしないと exe に `stdout`/`stderr` がなくなり、`cmd.exe` と PowerShell は GUI プロセスを**待たない**ので、CI は出力も終了コードも見られません。GUI の起動時には、プログラムが自分でコンソールから切り離されるので、ダブルクリックしても黒いウィンドウは残りません。
- **onedir** (`--onefile` ではない): `pydivert` は `WinDivert64.sys` を持っていて、onefile はそれを `%TEMP%\_MEIxxxx` に展開していました。カーネルは読み込まれた `.sys` へのハンドルを開いたままにするので、再起動するまでそのディレクトリを**削除できませんでした**。ディレクトリ形式のビルドでは、ドライバーは exe の隣の、安定したパスにあります。
- **`asInvoker`** (`--uac-admin` ではない): `requireAdministrator` は、昇格のたびに**新しい**プロセスを作るため、呼び出し元のパイプと終了コードが失われます。現在は GUI が自分で昇格を求め、CLI は権限がないとき、終了コード `7` と明確なメッセージで終了します (`--simulate` には権限は不要です)。

アイコンは Pillow のスクリプト (`pip install pillow`) で再生成できますが、通常の動作には Pillow は不要です。

## 落とし穴 (バグを報告する前にお読みください)

- **`--duration` は、便利さだけでなく、安全網です。** これがないと、セッションは `Ctrl+C` / STOP まで続きます。CI では**必ず** `--duration` を付けてください。唯一の例外は、タイムラインのあるシナリオです。ループせず、ステップが複数あるファイルを `--scenario` に渡した場合は、シナリオが終わるとその実行も終了し、開始時にそのことが通知されます。ループするシナリオや、ステップが1つだけのシナリオには、止まる終わりがないので、警告を出して、止めるまで動き続けます。
- **コンソールウィンドウを閉じると実行はきれいに停止しますが、サインアウトは違います。** コンソールウィンドウを閉じると、Ctrl+Break と同じように実行が終わります。キャプチャが停止し、サマリーが出力され、要求していれば `--repro-out` のレポートと `--log-file` が書き込まれ、WinDivert ドライバーがアンロードされ、ログに `Terminated (console window closed).` と表示され、終了コードは `143` になります。Windows がこの後片付けを待つのは約 5 秒だけです。サインアウトやシャットダウンは、プログラムを即座に終了させます。Windows はそれでもキャプチャを閉じるので、劣化されたままのトラフィックは残りませんが、サインアウト後は、`--cleanup-driver` か再起動まで、ドライバーが読み込まれたまま残ることがあります。
- **トラフィックなし = 成功扱い。** フィルターが1つもパケットを捕捉しなくても、プログラムは正しく動作し、終了コード `0` で終わります。それをエラーにしたい場合 -> `--fail-on-no-traffic`。
- **トラフィックフィルターと実行時間が有効になるのは、START からだけです** (GUI と同様)。"Apply changes" はこれらに触れません。
- **STOP の後、遅延キューで待っていたパケットは破棄されます。** `--latency 5000` では、かなりの数のパケットが一度に破棄されることがありますが、これはリークではなく、セッションの終わりです。
- **速度制限にはバッファーがあります (`--buffer`、既定値 1000 ms)。** 制限を超える負荷がかかると、バッファーが満杯になった時点で超過分は "Rate-limit drop" (別のカウンター) として破棄されます。これは回線が詰まったときの挙動であり、バグではありません。セッション中に制限を引き上げても、バッファーが空になってから (最大で約 `--buffer` ms 後に) 有効になります。以前の、無制限のバッファー (破棄の代わりにパケットが溜まり、遅延が増え続ける) がよい場合は、`--buffer 0` を設定してください。
- **`--dst-port "!53"` は、ポートのないトラフィック (例: ICMP) も捕捉します。** ポートのないパケットは、「ポート 53 ではない」からです。
- **名前だけのプロセス指定は部分文字列です。** `--target chrome` は `chromedriver.exe` も捕捉します。厳密には、`--target "re:^chrome\.exe$"` を使ってください。
- **範囲は両端を含みます** (`80-80` = 1つのポート)。nmap/iptables と同じです。
- **CLI は常に英語です。** GUI やシステムの言語には関係ありません。
- **`-q` は本当に静かです。** 成功したときは何も出力しません。結果は終了コードで読んでください (または `--format json` を追加します)。
- **管理者権限なしでの実行** (かつ `--simulate` なし) は、「無言」ではなく、終了コード `7` で終わります。
- **ドライバーが `%TEMP%` のファイルをロックしましたか？** それは古い onefile ビルドの名残です。
  `BeanNetworkTester.exe --cleanup-driver` で、システムを再起動せずに解放できます。

## テスト

エンジンは WinDivert から分離されているので、テストはどのシステムでも動きます (Windows も、管理者権限も、tkinter も不要です)。スイートは **pytest** をベースにしています。

```bat
pip install --require-hashes -r requirements.txt
pip install -r requirements-dev.txt
python -m pytest tests
```

あらゆる仕組みを網羅しています。パケットロス、遅延、ジッター、方向別のスロットル、破損、重複、フィルター式 (リスト、範囲、`!`、`>`、`<`、ワイルドカード、`re:`、CIDR、IPv6)、プロセス/宛先の指定、SYN の破棄、MTU、フラッピング、NAT の失効、RST の注入、遅延スパイク、スケジュール、接続ログ、再現性 (シード)、シナリオ、設定ファイル、サマリー (PL/EN)、UI の翻訳、再現 (有効なシード、イベントログ、レポート、CLI コマンド) です。別のテストで GUI のスモークテスト (`smoke_gui.py`、偽の tkinter 上) も実行され、リポジトリの規約 (命名、コアパッケージに tkinter を入れない、許可された階層構造) もテストで守られています。

**CI/CD の CLI の約束**は、別に守られています。
- `tests/test_cli_runtime.py` - 終了コード (0/1/3/4/5/6/130/143)、`--duration` の精度 (「次のレポートまで」ではない)、stdout/stderr の分離、NDJSON、`-q`/`-v`、`--dry-run`、`--print-config`、`--min-packets`、設定ファイルより `--duration` が優先されること。レポートのループには時計が注入されるので、実行時間のテストはマイクロ秒で終わります。
- `tests/test_failsafe.py` - セッションが `duration` の後に自分で停止すること、死んだキャプチャスレッドが *フェイルオープン* (ドライバーの解放 = ネットワークが戻る) を引き起こすこと、GUI の `_tick` が例外を乗り越えること、対象指定のスレッドが tkinter に決して触れないこと、ウィンドウを閉じると必ずエンジンが解放されること。

**GitHub Actions** は、プッシュのたびに同じテストを実行します (`.github/workflows/ci.yml`)。Linux + **Windows** のマトリクスで、**カバレッジゲート**を通したスイート、偽の tkinter 上の GUI スモークテスト、終了コードのアサーション、NDJSON のチェック、`--doctor` と `--license` を実行し、その後に **`.exe` のビルドと、ビルドしたファイルのスモークテスト** (`--version`、`--simulate`、不正な設定 -> コード 3)、WinDivert ドライバーが本当に exe の隣に同梱されているかの確認を行い、ダウンロード可能な成果物を作ります。

**テストと並んで3つの静的チェックが実行されます。** ソースを実行せずに読むものなので、Linux のみです。**ruff** は、デッドコードまたはバグの典型パターンの検出 (`F` と `B`) でプルリクエストを失敗させ、セキュリティ系 (`S`、`ASYNC`) は、ブロックしないアノテーションとして報告します。ルールのうち2つは意見ではなく上限です。関数を通る経路の数に対する `C90` と、引数の数に対する `PLR0913` で、どちらも現時点で存在する最大のものに合わせてあるため、何かがそれを超えて大きくなるまでは沈黙しています。**mypy** はパッケージを型チェックします。**semgrep** はデフォルトのレジストリのルールセットでスキャンし、ERROR、HIGH、CRITICAL の検出は実行を失敗させ、それ以下のものはすべて全文が出力されます。3つのツールのバージョンはすべて固定されているため、リンターの新しいリリースによって、何も変えていないプルリクエストが赤くなることはありません。ruff と mypy は `requirements-lint.txt` にあり、CI は正確なファイルハッシュでインストールします。semgrep は `requirements-scan.txt` にあり、バージョンだけを固定しています。semgrep は実行時にルールをダウンロードするので、固定しても安定した答えを約束できない、唯一の場所です。

**依存関係は3つの側面から検査されます。** `audit` ジョブは、インストールされた状態のランタイムとビルドのセットに対して pip-audit を実行します。`review new dependencies` (`.github/workflows/dependency-review.yml`) は、既知のアドバイザリのある依存関係や、プロジェクトが配布できないライセンスの依存関係を追加するプルリクエストを失敗させます。**OSV-Scanner** (`.github/workflows/osv-scanner.yml`) は、固定されたすべての requirements ファイルを OSV データベースと照合します。`master` では毎週 Security タブに報告し、プルリクエストでは、そのプルリクエストが新しいアドバイザリを持ち込んだときにだけ失敗します。

単体テストにはできない仕事をするため、知っておく価値のあるステップが1つあります。仮想スクリーン上の**実際の Tk での GUI 描画チェック**で、サポートする最小の 1366x768 で、**すべての言語**について行います。実際のウィンドウを構築し、すべてのページを巡り、About ウィンドウを開き、いずれかのボタンが要求より狭いとき、つまり文字が切れているときにビルドを失敗させます。ポーランド語のラベルは英語より長いため、レイアウトが崩れるのはそこで、英語では見えなかった崩れを検出したことがあります。

リリースは `v*` タグが付くと、2つ目のワークフロー (`.github/workflows/release.yml`) で公開されます。タグを `VERSION.txt` と照合し、変更履歴がまだ開いたままなら公開を拒否し、exe をビルドしてスモークテストし、SPDX SBOM を添えた**ドラフト**を作成します。アーカイブは意図的に公開しません。署名鍵は、どのランナーからも届かないハードウェアカードにあるため、アーカイブはメンテナーのマシンで署名され (`tools/sign_release.py`)、そこからアップロードされ、その後3つ目のワークフローが、実際に配布されるバイト列を証明します。

そのため、公開されたリリースには、zip、この README が検証するよう案内している `SHA256SUMS.txt`、SBOM、証明書バンドルが含まれます。正式なリリースには5つ目のファイルとして `.msi` インストーラーが付きます。リリース候補には付きません。Windows Installer は `-rc.1` を無視するため、候補とそのリリースを同じバージョンとして扱ってしまうからです。

コードは `beantester/` パッケージに分割されています。薄いランチャー `bean_network_tester.py` はルートに残してあるので、既存のコマンドすべて (README、再現レポート、PyInstaller) は変更なしで動きます。

## 仕組み (概要)

コアの `BeanCore.decide()` は純粋関数で、パケットの運命を次の順に決めます。
対象指定 -> LAN モード -> ブロック (ファイアウォール) -> NAT -> RST -> フラッピング -> MTU -> SYN -> パケットロス -> 破損 ->
遅延/ジッター/スパイク -> スループット制限 (上限つきバッファーを持つトークンバケットで、必要に応じて
スケジュールから決まります) -> 重複。キャプチャスレッドがパケットを読み取って判断を実行します。再注入
スレッドが、決められた時刻にそれらを送り出します。すべての乱数は1つのジェネレーターを通ります (任意でシードを指定できます)。

## 注意事項と制限

- フィルターに一致するトラフィックを変更します。より狭いテストには、"Target process" または "Target
  destination" を使ってください。
- ping = ICMP です。劣化させるには、ICMP を含むフィルターを選んでください。
- 速度制限は ping (小さなパケット) では見えにくいので、ファイルのダウンロードでテストしてください。
- 本物の RST のキャプチャと注入は、WinDivert のある Windows でのみ動作します。ロジックは、どこでも
  動くテストで確認されています。
- 自分のアプリケーションとネットワークをテストするためのツールです。

### 知っておく価値のある挙動

- **スケジュールはループします** - 最後のステップの後は最初に戻ります (`2:100:0, 2:500:0` は、
  100 KB/s で 2 秒と 500 KB/s で 2 秒を、延々と交互に繰り返します)。変更したスケジュールをセッション中に適用すると、
  サイクルは最初のステップからやり直しになります。同じものをもう一度適用した場合や、ほかの設定を変更した場合は、
  サイクルはそのままの位置で続きます。
- **スケジュールは固定の制限より優先されます** - "Schedule" フィールドが空でないときは、
  "Download/Upload" (KB/s) の値は無視されます。スループットはスケジュールのステップから決まるためです。
- **スケジュールは省略できますが、有効でなければなりません** - 空のフィールド = スケジュールなしですが、不正な入力
  (例: `1:100`、`2:abc:0`) はエラーとして報告されます。GUI はセッションを開始せず、CLI はメッセージとともに
  終了します。黙って読み飛ばされるものはありません。
- **フィルター式は検証されます** - プロセス/IP/ポートのフィールドの不正な入力 (例:
  `999.1.1.1`、`2000-1000`、`>chrome`、`re:[`) は、黙って何もしないのではなく、エラーとして報告されます。
  GUI ではフィールドが赤くなって下に理由が表示され、CLI は `error: ...` メッセージとともに終了します。
  アドレスの比較は表記の違いを問いません (IPv6 の短縮形と完全形は同じアドレスです)。
- **肯定の項は足し合わされ、除外は差し引かれます** - `80,443,!8080` は「80 または 443、ただし 8080 は除く」を意味し、
  `!53` だけなら「53 以外のすべて」を意味します。項の順序は関係ありません。詳細とエッジケースは
  [フィルター構文](#フィルター構文-プロセス--ip--ポート)にあります。
- **範囲は両端を含みます** - `8000-8100` は 8000 と 8100 を含み (nmap/iptables と同じです)、
  `80-80` はちょうど1つのポートです。
- **"Target destination" の IP とポートは AND で組み合わさります** - 両方のフィールドを設定すると、**両方**の条件を同時に満たす
  トラフィックに絞り込まれます。
- **非常に低い速度制限 = 本物のパケットロス** - 既定のバッファー (1000 ms) では、制限を超える分はバッファーが満杯になると
  破棄され、**"Rate-limit drop"** の統計に数えられます ("Loss" ではなく別のカウンターです)。これは混雑した回線の振る舞いなので、
  実効的なパケットロスは、設定した "Loss" の割合より高くなることがあります。ツールのキューが上限の **20 000** パケットまで
  増えるのは、`--buffer 0` (無制限のバッファー) のときだけで、その場合、超過分は
  **"Buffer overflow"** として数えられます。
- **Seed フィールドが空 = ランダムなシード** - プログラムは具体的な値を引き、セッションパネルに表示します。
  設定ファイルでは、値 `-1` が「ランダム化」を意味するので、`-1` を単純なシードとして使うことはできません
  (負の数を含め、それ以外の数値は普通に動作します)。
- **プロセスの指定には子プロセスが含まれます** - ソケットは、それを**開いたプロセス、またはその祖先のいずれか**が一致すれば、
  対象のものになります。そのため `chrome.exe` (またはブラウザウィンドウの PID) は、すべての接続を握っているネットワーク
  プロセスも捕捉します。明示的な除外が優先されます。`chrome, !chromedriver` は、親を経由して `chromedriver` を
  巻き込むことはありません。
- **プロセスの指定は、遅いポーリングではなく、ソケットイベントで駆動されます。** WinDivert が渡してくるのはパケットであって
  PID ではないので、パケットは**ローカルポート**でプロセスに対応付けます。Windows では、ツールがシステムのソケットイベント
  (connect / bind / accept / close) をリアルタイムに監視するため、**すでに**対象範囲にあるプログラムの新しい接続や
  **UDP フロー**は、最初のパケットから劣化されます。新しいポートを使う DNS クエリや QUIC も同様です。例外はプログラムの
  *最初の*接続です。少なくとも1つのソケットを所有するまでは、それを見分ける手がかりがないので、その1本の接続は
  手を加えられずに通過します。本物の WinDivert がない場合 (テスト/シミュレーション経路) は、ソケットテーブルを1秒に数回
  スキャンする方式に切り替わり、まったく新しい接続の最初のパケットがすり抜けることがあります。どちらの場合も、監視は専用のスレッドで
  動き、パケットを処理するスレッドでは決して動かないので、トラフィックの欠落につながることはありません。
- **テスト対象のプログラムが再起動する場合は、プロセス ID ではなく名前で狙ってください。** 実測では、終了して
  新しいプロセス ID で戻ってきた対象は、自動で再び捕捉され、再起動で失われるのは接続1本だけ、つまりソケットを所有する前に
  開く接続だけです。**プロセス ID** で狙った場合は、決して回復しません。その ID は終了したプロセスを指していたからで、
  再起動後のものはすべて手を加えられずに通過します。あとで Windows が同じ番号を与えた別のプログラムにも、手は加えられません。
  プロセス ID は、対象を設定した時点でそれを持っていたプロセスだけを意味します。
  コマンドラインでは、それが起きたときに実行中にそのことが通知され、キャプチャしたトラフィックのうちどれだけが実際に
  対象範囲にあったかが最後に表示されます。ウィンドウでは、プロセスのフィールドの下の赤い注記です。
- **除外だけを指定すると、ツールが識別できないものもすべて対象になります。** プロセスのフィールドの `!chrome` は
  「chrome 以外のすべてを劣化させる」という意味で、この「すべて」には、所有プロセスを特定できなかった接続が含まれます。
  ツールが開けない保護されたシステムプロセスや、ポーリング方式のフォールバックでは、まったく新しいソケットの最初のパケットです。
  **そのため、アプリケーションを保護する目的で除外を使わないでください。** 手を加えたくないアプリがある場合は、
  壊したいアプリのほうを名指ししてください (`--target thatapp`)。そうすれば、識別できないものは手を加えられずに
  通過し、安全な側に倒れます。これは、後述のポートでの `!53` と同じ考え方です。
- **何も捕捉しない対象指定は、何も壊しません** - 一致するプロセスが接続を1つも開いていなければ、トラフィックは
  手を加えられずに通過します。これには、実行されていないプログラムと、実行されているがアイドル状態のプログラムが含まれます。
  そのようなプログラムが接続を開くと、ツールは数ミリ秒以内にそれを追加するので、その接続の最初のパケットは手を加えられずに通過し、
  残りが劣化されることがあります。プログラムはそのことを明示します (フィールドの下の赤い注記とログへの記録)。
  「何も壊れなかった実行」は、「アプリが耐えた」ことと見分けがつかないからです。
- **名前だけのプロセス指定は部分文字列です** - `chrome` は `chromedriver.exe` も捕捉します。これは、
  古い設定との互換性のために意図的に残してあります。厳密にするには、`re:^chrome\.exe$` か、
  除外の `chrome, !chromedriver` を使ってください。
- **すべてのプログラムを指す対象は、何も絞り込みません** - `*.exe`、`exe`、`*` は、接続を持つほぼすべてのプロセスに
  一致するので、そのような実行には、対象をまったく指定しない実行と同じ開始時の警告が出ます。
- **Statistics と Connections は、既定では取得した全トラフィックを表示します** - "Traffic to
  modify" フィルターを通過したものすべてです。対象指定 (プロセス / IP / ポート) が決めるのは**何が壊されるか**だけで、
  テーブルやカウンターに何が見えるかではありません。Settings の **"Scope"** カードにある2つのスイッチがそれを変えますが、
  両者は同じものではありません。
  - **"Show only the targeted traffic"** は、カウンター、スループットのグラフ、Connections テーブル、接続の CSV を、
    対象指定が選んだものに絞り込みます。変わるのは目に**見える**ものだけで、取得されるものも、劣化されるものも変わらず、
    いつでも切り替えられます。
  - **"Capture only the targeted traffic"** は、*キャプチャそのもの*を絞り込みます。ドライバーが宛先のトラフィック以外を渡さなくなるので、
    ほかに対象にするものがなく、各タブはそのトラフィックを対象にします。セッションの開始時に固定され、ドライバーのフィルター言語で
    表現できる宛先、つまり単純なアドレス、リスト、範囲、CIDR にしか使えません。ワイルドカード、`re:` パターン、プロセスだけの
    対象指定は押し下げられず、その場合、このオプションは何もしません。Scope カードは、2つのうちどちらが適用されるかを
    START を押す**前**に教え、ログは開始時にもう一度それを伝え、Session パネルの **"Capture"** 行は、その実行について記録します。

  どちらがオンの場合でも、**カウンターと Connections テーブルの上にある注記が、それらの数値が実際に何を対象にしているかを伝えます。**
  キャプチャが絞り込まれていて*かつ*プロセスの対象が設定されている場合も含みます。このときツールは、すべてのプロセスの宛先のトラフィックを
  キャプチャし、そのうち1つのプロセスの分だけを劣化させるので、カウンターは劣化の対象より広い範囲を対象にします。
  **"Show only" がオンでも、3つのカウンターは全トラフィックのままです。** "Queue overflow"、"Dropped
  at stop"、"Send failed" は*このツール*が失ったパケットを数えたもので、対象にしていないトラフィックも含みます。
  それらを隠すと、ツール自身が与えた損害を隠すことになるからです。統計 CSV も "Show
  only" スイッチには従いません。追記型のログなので、2つの合計を別々の列に持ちます。ただし "Capture only" は
  `capture_narrowed` に行ごとに記録します。これは、そもそも何が数えられたかを変えるからです。再現レポートと `--format json` には、
  常に両方の数値が含まれます。
- **速度制限が整えるのは平均です** - トークンバケットは短いバーストを通すので、
  "Download/Upload peak" (1 秒のウィンドウで平均したもの) は、設定した制限より少し高くなることがあります。
  重複は制限に含まれます (2つ目のコピーも回線を通るからです)。
- **ウィンドウには最大サイズがあり、最大化できません** - レイアウト (2列 + ログバー) は 4K に引き伸ばすと意味をなさなくなるので、
  サイズに上限を設け、最大化ボタンを取り除いています。
- **Duration は START から数えます** - セッション中にフィールドを変更しても何も起きません (トラフィックフィルターと同じです)。
  上限に達すると、プログラムは単に STOP し、結果を画面に残します。
- **STOP は、遅延キューで待っているパケットを破棄します** - セッションの終了は即時です。`latency` が大きいと、
  これは一度きりの「空白」として現れます。バグではありません。
- **セッション中の障害は、必ずネットワークが復元された状態で終わります** - キャプチャまたは再注入のスレッドが死ぬか、10 秒間進捗がなくなると、
  エンジンは自分で STOP し、誰も到達できない開いたハンドルを握り続ける代わりに、ドライバーを解放します (*フェイルオープン*)。
  これは、「ユーザーが突然インターネットを失う」本物の経路でした。理由はログとイベントログに記録されます。STOP の後も
  詰まったままのスレッドは、待たずに置き去りにされ、次の START でログにそのことが記録されます。
- **プログラムを閉じると、WinDivert ドライバーが解放されます** - セッションのたびにではなく (セッションの再開始は
  即座であるべきです)、**終了時に1回だけ**です。ドライバーが読み込まれている間、カーネルは exe の隣にある
  `WinDivert64.sys` を開いたままにします。すると、**プログラムのディレクトリは、空に見えても削除できません** (Windows は
  ハンドルが開いているファイルを削除させてくれます。一覧からは消えますが、*削除保留*のまま残り、ディレクトリをブロックします)。
  何かが残った場合に、再起動せずに救出するには、`BeanNetworkTester.exe --cleanup-driver` (または `sc stop WinDivert` +
  `sc delete WinDivert`) を使います。終了時、プログラムが触れるのは自分が読み込む `WinDivert` サービスだけで、このプログラムの別のコピーが
  使っている間は、読み込まれたまま残します。`--cleanup-driver` は、ほかのプログラムがインストールする
  `WinDivert1.4` と `WinDivert1.1` も停止します。
- **"Duration" と "Traffic to modify" が考慮されるのは START 時だけです** - そのため、セッション中は両方とも**ロック**されます
  (何もしない編集可能なフィールドは、グレーアウトされたものより悪いからです)。

## SmartScreenとウイルス対策ソフトについて

**0.5.0 から .exe は署名されています。** 証明書の秘密鍵は、メンテナーの机から決して出ないハードウェアカードにあるため、
Windows は「不明な発行元」と表示する代わりに発行元の名前を表示します。これが何を保証し、何を保証しないかは理解しておいてください。
新しい証明書にはまだ SmartScreen の評価がないので、しばらくは警告が出ることがあり、
管理者権限を求めてネットワークドライバーを読み込むプログラムに対して、一部のウイルス対策ツールが誤検知を出すこともあります。
変わるのは、警告に署名者の名前が表示されるようになることです。**WinDivert ドライバー自体は、その作者によって
デジタル署名されています。** リリースの SHA-256 チェックサム (`SHA256SUMS.txt`) を照合して、
ファイルが変更されずに届いたことを確認することもできます。

**ダウンロードに何が含まれているかも、変更されていないことだけでなく、確認できます。** すべてのリリースのアーカイブには、
その中身をすべて列挙した署名つきの声明が付属しています。それは、あなたがダウンロードしたそのバイト列に対して、
このリポジトリ自身のワークフローが作成したものです。

```bash
gh attestation verify BeanNetworkTester-v0.5.0-windows-x64.zip -R donislawdev/BeanNetworkTester --predicate-type https://spdx.dev/Document/v2.3
```

チェックサムが証明するのは、ファイルがリリースページの記載と一致することです。こちらが証明するのは、隣にある部品表が
まさにそのバイト列について記述していること、そしてその声明が、ファイルを手渡した誰かではなく、このリポジトリの
ワークフローによって作成されたことです。

`--predicate-type` は省略できません。これがないと、`gh` はビルドの来歴 (provenance) の声明を探し、`HTTP 404` を返します。
ダウンロードするアーカイブは**メンテナーのマシンで署名された**もので、ランナーでビルドされたものではないからです。署名鍵は、
どのランナーからも届かないカードにあります。来歴が証明されるのは、ワークフロー内の未署名のビルドについてです。
リリースに付属するのは、署名済みのファイルに対する部品表です。

このコマンドは、どの証明書があるかを GitHub に問い合わせます。この証明は**ファイルとしても**、
`BeanNetworkTester-vX.Y.Z.sigstore.json` として同梱されているので、アーカイブと一緒に届いた証拠でアーカイブを確認できます。

```bash
gh attestation verify BeanNetworkTester-v0.5.0-windows-x64.zip --bundle BeanNetworkTester-v0.5.0.sigstore.json --repo donislawdev/BeanNetworkTester --predicate-type https://spdx.dev/Document/v2.3
```

2つの追加フラグはどちらも必要で、飾りではありません。`--repo` は、署名者の身元が一致しなければならないリポジトリを指定します。
`--predicate-type` が必要なのは、このバンドルが **SBOM** の証明であり、別の指定がない限り `gh` はビルドの来歴の証明を探すからです。
これがないと "no attestations found with predicate type" と表示されますが、それはツールが壊れているのではなく、厳密に動作しているということです。
ファイルが問題なければ何も表示せず、終了コード 0 で終わります。1バイトでも変えれば、終了コード 1 になります。

3つの声明があり、それぞれ異なる問いに答えることを知っておく価値があります。**署名**は、誰がそのファイルを保証しているかを伝えます。
**上のバンドル**は、このアーカイブそのものをその部品表に結び付けるもので、署名の後に、あなたがダウンロードしたバイト列に対して作成されます。
**ビルドの来歴**は、署名されたビルドを作ったのがどのコミットとどのワークフローかを伝えます。署名はバイト列を変えるので、
これは必然的に未署名のビルドについて記述するものであり、ダウンロードの中ではなく、このリポジトリの証明書ストアにあります。

### ダウンロードの中身と、その確認方法

すべてのリリースには **SBOM** が付属します。これは標準の SPDX 形式のリストで、ビルドに含まれるすべてのサードパーティコンポーネントを、
バージョン、ライセンス、ソースの所在とともに載せています。`BeanNetworkTester.exe --license` が出力するのと同じリストを、
ツールが読める形にしたものです。

SBOM は、それが記述する**アーカイブに対して署名されている**ので、両者を切り離すことはできません。

```bash
gh attestation verify BeanNetworkTester-vX.Y.Z-windows-x64.zip --repo donislawdev/BeanNetworkTester --predicate-type https://spdx.dev/Document/v2.3
```

チェックサムが伝えるのは、ファイルが変更されずに届いたということです。証明書が伝えるのは、*この*部品表が*このアーカイブ*のものであること、
そしてその声明が、このリポジトリのリリースワークフローによって作成されたことです。`--predicate-type` を省くと、`gh` は代わりに
ビルドの来歴の声明を探し、`HTTP 404` を返します。
